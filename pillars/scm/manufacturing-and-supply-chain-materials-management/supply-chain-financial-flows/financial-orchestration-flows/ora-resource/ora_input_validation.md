# Financial Orchestration Flows input validation

## Required Groups

| Requirement Group | Accepted Fields | If Missing | How to Resolve | Applies When | Resolver |
|---|---|---|---|---|---|
| Operation and target | Explicit Agreement create/correction/Insert, PTR/FTR create/correction or PTR deletion intent; AgreementNumber | Ask for operation and exact name | Collect business input; do not require resolved IDs during intake | Every request |  |
| New Agreement | Business process type, EffectiveStartDate, Priority | Ask for missing values | Resolve process meaning/code through the dedicated lookup | Agreement create | resolve_flow_business_process |
| Procurement ownership event | Optional Drop Ship Supplier Ownership Change Event may be ASN from supplier or AP Invoice Match | Leave the payload field unpopulated; do not infer the UI's preselected value | Resolve an explicitly selected event through the Procurement ownership-event LOV before preparing the header | Procurement Agreement create | resolve_flow_procurement_ownership_event |
| Insert | Exact existing name, new effective start date and a different Description | Ask for missing date or changed text | Resolve the version covering the new start date; never invent a change to force an insert | Insert | resolve_flow_agreement_version |
| Correction | Exact existing name and at least one requested Description, Priority, financial qualifier, or Status change | Ask for target or change | Resolve current dated target before preparing data; resolve a supplied Status through the status LOV | Agreement-header correction | resolve_flow_agreement |
| PTR deletion target | Exact AgreementNumber and optional primary route number or shipping/receiving BU pair | Ask for discriminator if more than one PTR exists | Resolve within the selected Agreement, including all children; no financial/create-required inputs | PTR deletion | resolve_flow_ptr_target |

## Field Validation

| Check | What Happens | Applies When | Resolver |
|---|---|---|---|
| Name and text | AgreementNumber is nonblank and at most 100 characters; Description at most 240. Preserve exact names; no fuzzy substitution | Every supplied value |  |
| Priority | Require integer 1 through 99990; reject decimals instead of silently rounding | Create or supplied correction |  |
| Dates | Use valid ISO YYYY-MM-DD dates; supplied end date must be on or after start. Distinguish a target version's existing dates from requested new dates | Every supplied date |  |
| Supported fields | Create accepts AgreementNumber, resolved AgreementType, EffectiveStartDate, optional EffectiveEndDate, Priority, Description, resolved optional QualifierRuleSetId, explicit AutoActiveFlag, optional Status=DRAFT, and resolved DropshipForwardOwnershipChangeEventId only for PROCUREMENT. Corrections accept Description, Priority, optional resolved QualifierRuleSetId, and Status resolved from any exact value in the status LOV when the current correction template exposes Status; otherwise stop as unsupported. Insert accepts a new start date and changed Description, preserving the resolved Priority and DRAFT status; changed Priority, qualifier, ownership event, Status or end date on Insert requires a separately validated contract. Reject other populated fields with a specific unsupported-contract message | Agreement-header operations only | resolve_flow_status |
| Procurement ownership-event value | For PROCUREMENT create, populate DropshipForwardOwnershipChangeEventId only when the user explicitly supplies ASN from supplier or AP Invoice Match and the live lookup resolves one EventDefinitionId. Leave the attribute unpopulated when omitted. Reject a supplied ownership event for any other AgreementType; do not send a null or an event name in place of the ID | Agreement create | resolve_flow_procurement_ownership_event |
| Correction Priority | Every correction must include Priority: use the explicit requested new value when supplied, otherwise resolve and preserve the current value. Missing or unresolved Priority blocks preparation; never invent a value | Agreement-header correction only | resolve_flow_agreement |
| Correction Status | When Status is explicitly requested, accept an exact status LOV Meaning or LookupCode, resolve exactly one matching LookupCode, and send that code in Status. Require Status to exist in the current correction template; if absent, stop as unsupported. Fusion determines whether the requested transition is valid for the selected Agreement version; do not silently substitute another status | Agreement-header correction only | resolve_flow_status |
| Correction effective context | Use RestAction=PATCH and effectiveOf=RangeMode=CORRECTION;RangeStartDate=<existing-start>;RangeEndDate=<existing-end>. Dates identify the selected version, not a new version | Agreement-header correction only | resolve_flow_agreement |
| FTR correction effective context | Use RestAction=PATCH. Include effectiveOf only when the fresh FTR correction template exposes it and the deployed correction contract requires it; then use RangeMode=CORRECTION;RangeStartDate=<selected-FTR-EffectiveStartDate>;RangeEndDate=<selected-FTR-EffectiveEndDate>. If the fresh template does not expose effectiveOf, do not add it. The FTR dates identify the corrected child version; selected Agreement dates are only parent URL-routing evidence and must not replace them | Existing FTR correction | resolve_flow_ftr_target |
| Insert effective context | RestAction=PATCH; keep existing identity dates in EffectiveStartDate/EffectiveEndDate. Put the user-selected new start in effectiveOf=RangeMode=UPDATE;RangeStartDate=<new-start>;RangeEndDate=<existing-end> | Insert only | resolve_flow_agreement_version |
| Loader effective context | Omit effectiveOf entirely for Agreement creates; do not synthesize it from UI headers. Keep ISO business date fields | Create |  |
| Booleans | Normalize explicit AutoActiveFlag to the boolean representation required by live attribute metadata; do not guess Y/N versus true/false | Create with explicit flag |  |
| System and custom fields | Do not accept audit fields, caller-generated AgreementId, CustomSurrogateId or FinancialOrchestrationFlowSurrogateId as business input. Preserve these headers in downloaded templates when present but keep unused values blank | Intake |  |
| Omitted versus cleared | Omitted optional fields remain omitted; explicit null/clear is outside the first-version transport contract | Every request |  |
| Header identity fields | Correction requires AgreementNumber, AgreementId, existing start/end, requested changes, Priority, effectiveOf and RestAction=PATCH; include Status only when requested and exposed by the current correction template. Insert uses the same existing identity plus changed Description, preserved Priority/Status=DRAFT/end, and UPDATE context with explicit new start. Select operation-specific fields from live sample; do not construct a static DAT | Agreement correction/Insert |  |
| Child row scope | For initial PTR/FTR creation, require one selected parent Agreement version and supply PTR inputs and at least one associated FTR for Data Loader preparation. A standalone FTR requires an existing PTR server UniqueId/parent identity. Do not silently discard child rows or fabricate parent-key placeholders | PTR/FTR |  |
| PTR create fields | Require FromBUId, FromLegalEntityId, ToBUId, ToLegalEntityId and the route effective dates. Retain the selected Agreement composite key as lookup evidence, but do not add AgreementEffectiveStartDate or AgreementEffectiveEndDate unless the fresh deployed template explicitly requires them; preserve the registered Agreement composite-key URL resolution. Require PrimaryTradeRelationNumber while the deployed registration marks it mandatory. Never generate UniqueId. For SHIPMENT, never populate or resolve a Selling Trade Organization, FromTradeOrganizationId or ToTradeOrganizationId on PrimaryTradeRelation | PTR create planning | resolve_flow_child_target |
| FTR base fields | Require FromBUId, ToBUId, PricingId, TradeAccountingRuleSetId, SequenceNumber and FTR effective dates. For Nonshippable Sales, leave both FTR trade organizations blank. For Internal Transfer, leave the first FTR FromTradeOrganization blank; resolve each later FTR selling organization from its selling BU DefaultTradeOrganizationId. Resolve each FTR buying organization except the last from its buying BU DefaultTradeOrganizationId; leave the last buying organization blank. A single-FTR route has neither trade organization populated. For Procurement, resolve every omitted selling organization from the first eligible entry in that FTR's selling-BU LOV. Default an omitted buying organization from its buying BU on each FTR except the last; leave the last FTR buying organization blank, including on a single-FTR route. For Shipment, leave an omitted first selling organization blank. Outside Internal Transfer, Procurement and Nonshippable Sales, resolve every omitted buying organization from its buying BU default and inherit later omitted selling organizations from the preceding resolved buying organization, verifying each in its selling BU. Preserve and validate explicit FTR trade organizations. When ChargeAccount is supplied as a display combination, resolve it to ChargeAccountCodeCombinationId in the buying ledger and populate only the resolved ID; never send the display combination in ChargeAccount. Never put these FTR attributes on a SHIPMENT PTR | FTR create planning | resolve_flow_child_target |
| FTR correction row | Include only the selected FTR identity and key fields required by the fresh correction template, its existing EffectiveStartDate and EffectiveEndDate, RestAction, requested resolved changes, and any template-mandated retained context. Include effectiveOf only when it is exposed and required by the fresh deployed correction contract. Preserve current FromBUId, ToBUId, receivables invoice type and credit-memo type when the fresh template or accounting-document readiness requires them; re-resolve only values invalidated by a requested BU, date or country change | Existing FTR correction | resolve_flow_ftr_target |
| Standalone FTR correction artifact | Emit exactly one FinancialTradeRelation METADATA section and its selected FTR MERGE row. Do not include PrimaryTradeRelation or financialOrchestrationTradeAgreements METADATA or MERGE sections: the selected PTR and Agreement are lookup and URL-routing context, not source rows for this operation | Existing FTR correction | resolve_flow_child_registration |
| FTR invoicing terms | Require ReceivablesInvoiceType, ReceivablesCreditMemoType and PaymentTermsId if a selected-rule document is enabled true/Y, TaskType AP or PO, and overlaps the FTR interval (end >= FTR start and start <= FTR end). Unknown document visibility/flag blocks requiredness decision. Explicitly supplied fields are resolved even if optional | FTR create/correction with selected rule or interval | resolve_flow_accounting_documents |
| Child generated and optional fields | Never generate AgreementId, AgreementPrimaryTradeRelationId, AgreementFinancialTradeRelationId, UniqueId, audit fields, DFF identity fields, or empty optional tax/classification/incoterm fields. Include optional fields only when supplied and applicable to the agreement type | PTR/FTR create planning |  |
| PTR deletion fields | Require resolved selected PTR identity and only operation/key fields required by fresh delete metadata; RestAction=DELETE. One PTR deletion, zero populated Agreement/FTR rows. No pricing/accounting/payment/create fields | PTR deletion | resolve_flow_ptr_target |
| Child key schema | Require every selected registered key field with matching PTR ObjectUserKeys/FTR ParentUserKeys values. Preserve registered Agreement composite-key resolution. Keep Agreement/PTR/FTR dates separate; never fabricate PtrEffectiveStartDate/PtrEffectiveEndDate or Agreement date helpers merely because a template contains them | Child operations | resolve_flow_child_registration |
| Derived FTR parent-date helpers | When the fresh FTR correction URL has ParentEffectiveStartDate and ParentEffectiveEndDate placeholders and each is a verified foreign-key derivation from AgreementId, Data Loader derives the values before URL formation. If the fresh FTR template exposes either helper column, retain it with a blank row value; if it does not expose the column, do not add it. Never send ISO dates, numeric substitutes, or FTR dates in a present helper column. If either derivation, parent key, datatype or URL mapping is absent or inconsistent, block preparation | Existing FTR correction with deployed parent-date helpers | resolve_flow_child_registration |
| Existing child identity | Require server identity or a deployed lookup scoped to the selected Agreement/PTR/version. A route number alone is not unique across Agreements; FTR sequence alone is not unique across PTRs or dates | Existing PTR/FTR correction or deletion | resolve_flow_ptr_target |
| Changed lookup context | A BU change invalidates LE, party, ledger, trade organization, receivables and dependent terms/registrations. A country change invalidates country-dependent tax selections; dates invalidate date-sensitive lookups; environment changes invalidate all IDs. Re-resolve affected fields with the owning lookups, preserve unaffected values | FTR correction |  |
| Empty optional fields | Distinguish omission from explicit clear; preserve existing values when omitted. Explicit clear requires a supported loader null-value contract; otherwise block it. Truncated names/addresses need a unique live candidate or full user text | Correction |  |
| LOV datatype | Compare resolved mapped value with fresh attribute datatype. Receivables types use Name; pricing/accounting/payment use IDs; concatenated classifications use their returned codes; products use CategoryId; payable sequence categories use DocumentSequenceAssignmentId as text despite Code suffix | Supplied FTR values |  |
| Legal entity | A supplied PTR legal entity must equal the resolved BU relationship. FTR side LE/party/ledger are lookup context and cannot be assumed writable attributes | PTR/FTR BU inputs | resolve_flow_route_bu |
| Identity end date | For a null returned Agreement end date, use the end component of its verified composite context key; do not guess. Retain AgreementId,start,end order and ISO format independently of business-date changes | Correction/Insert | resolve_flow_agreement |
