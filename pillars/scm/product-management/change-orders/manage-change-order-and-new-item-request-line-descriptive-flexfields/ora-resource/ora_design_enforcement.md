# Change Line DFF Design Enforcement

Evaluate the intended change together with retained properties from the verified current baseline. Input shape belongs to ora_input_validation.md; lookup mechanics to ora_reference_lookups.md; eligible selector defaults to ora_defaulting_rules.md. These rules do not silently correct configuration.

## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Scope and identity | Confirm supported line scope and EGO_CHANGE_LINE |
| 2 | Context design | Validate only membership-applicable requested Context Codes and Context Sensitive Segment associations against InternalName; disable-only uses existing baseline identity |
| 3 | Context Segment design | Evaluate selector properties and the impact of an actual selector delta separately from requested-code membership, using requested changes plus retained baseline values |

## Design Rules

Selector rows apply when the Context Segment is requested or its readiness is needed for requested Context/Context Sensitive Segment setup changes. They are not extra requirements for a Global-Segments-only request or a standalone check of allowed Context Code values. That standalone check establishes membership only, not existing Context configuration or setup readiness. Evaluate changed properties together with the verified retained baseline; an out-of-scope correction requires review, not an automatic write.

For a segment- or Context-disable-only update, preserve the selector without applying its configuration/defaulting rules or requiring an unrelated selector repair. Required current-baseline, exact-target, protection, impact, preservation and shared artifact checks still apply. For enabled-state-only disable of an existing Context or segment, baseline identity remains mandatory but current InternalName membership is not a prerequisite. A retired or absent change-type association alone must not prevent disabling its existing DFF definition; do not recreate or remap that association. Explicit allowed-code checks still return actual membership without turning a nonmember result into a disable-only blocker. Mixed requests retain every rule applicable to their additional changes and require a reviewed combined delta.

Requested membership scope includes Context Codes explicitly checked, Contexts created or modified, and the selected Context of each created or modified Context Sensitive Segment. It includes an existing Context when the user targets a membership-applicable change; it excludes enabled-state-only disable and unrelated Contexts and children retained unchanged. Do not add preserved nonmembers to the allowed set, rewrite them, or require a project-specific exception or extra runtime reviewer approval merely because they are absent from InternalName. Repository merge reviews remain separate from runtime setup approvals.

Selector-impact assessment is not a second membership sweep. For an actual selector delta, compare the proposed and baseline settings and use documented target behavior and shared validation evidence to assess effects on retained configuration. Unchanged rows alone do not prove unchanged behavior, but absence of a preserved Context from InternalName alone does not prove a compatibility failure. Report a concrete incompatibility or the specific evidence needed to resolve a material impact; do not classify the requested Context as invalid because of another Context.

For Default Type Parameter, the selector's stored Default Value remains PRODUCT_CONTEXT; Product Context is only a display label. Derivation Value is optional, and equality with Default Value is not mandatory. The defaulting resource owns its PRODUCT_CONTEXT proposal for eligible omissions. An explicit request to leave it blank is not a missing-input blocker; preserve existing values on unrelated partial updates. If the user supplies Product Context as the derivation parameter, use the exact PRODUCT_CONTEXT token after confirming that mapping. Validate other explicit derivation choices against verified target metadata rather than silently replacing them or rejecting them solely for differing from Default Value. Verify the target export's field mapping before packaging; do not conflate the two properties or invent an extra archive column. These rules apply to both Redwood and non-Redwood, not to child-field defaults. Explicit Redwood requires List of Values; explicit non-Redwood requires Hidden. An unspecified UI follows the existing eligible display-default policy without assuming the UI.

Deployment execution and its preflight, approval and status gates belong to the shared core DFF workflow selected in the task skill. This design node evaluates configuration rules; it neither requires a human deployment operator nor authorizes deployment or establishes live success.
