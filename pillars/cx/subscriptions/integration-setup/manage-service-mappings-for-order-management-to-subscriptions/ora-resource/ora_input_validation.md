# Input Validation

|---|---|---|---|---|---|

| Mapping assessment request | Business requirement, requested business outcome, and current Service Mapping XML; source or target entity and attribute context when known | Stop assessment | Supply the missing business outcome or current XML; when the source is unknown, use only documented entity-level metadata discovery | Every request to assess an existing or missing mapping |  |
| Describe metadata evidence | A documented current-release FOM describe path and a metadata response when source discovery or compatibility confirmation is needed | Return a prerequisite only after the documented describe route is absent, unavailable, or yields no single compatible candidate | Use the documented Sales Orders for Order Hub header describe path, the documented header EFF path when applicable, or supply the documented current-release path for another source entity | The validated XML does not establish the needed source attribute, queryability, or compatibility | resolve_order_mapping_source_metadata |
| Subscription target metadata evidence | A documented current-release entity-level describe response when the XML lacks any requested target entity, attribute, or correlation | Return a target-metadata prerequisite only after the exact entity or child branch describe has been inspected or no documented route is available | Resolve the exact requested entity and its documented branch, then inspect the response for field identity, type, capability, and correlation evidence. ## Dependency-Aware Validation

| Applies When | Result | Next Action | Resolver |
|---|---|---|---|
| A Service Mapping XML is supplied | Valid only when its root transformContext has contextName equal to OMIntegration | Stop before reviewing entities, attributes, mappings, joins, or transformations when the value is absent or different |  |
| A mapping assessment is requested | Valid only when the requested business outcome can be inspected against the validated XML, or source and target describe routes support candidate discovery | Inspect the XML first; when any requested standard source, target, or conditional fallback value is absent, run the documented describe route for that entity before returning missing-input rows or mapping status. Return describe matches as candidate evidence until OMIntegration revalidation |  |
| A candidate metadata response is supplied | Valid only when the candidate is a single scalar attribute with compatible Type and the capability required by its role: queryable for a search requirement or updatable for a target-update requirement | Return the confirmed candidate or request a clarified mapping requirement |  |

## Field Validation

| Check | What Happens | Applies When | Resolver |
|---|---|---|---|
| Service Mapping XML contextName | Accept only OMIntegration; do not treat another integration context as FOM-to-OSS evidence | Every supplied Service Mapping XML |  |
| Source entity and attribute lineage | Start with entities and attributes in the validated XML; use documented describe metadata to discover or confirm a source candidate before asking for a standard source field; do not convert a similarly named candidate into an XML mapping fact | Every mapping assessment | resolve_order_mapping_source_metadata |
| Interface-table correlation | When a requested outcome spans context entities, accept an interface-table bridge only when the XML evidences the interface entity, both correlation attributes, and the joins to the source and target entities. Record the bridge keys and intended cardinality; do not infer an SDO collection name, runtime API, direct assignment, or UI change | Every cross-entity mapping assessment |  |
| Direct target-to-source correlation | When the target entity exposes a source identifier, accept the direct relation only when both target and source key attributes are XML-evidenced and type-compatible. Record it as corroboration only after the required interface-table lineage is established; do not infer a direct relation when the key is absent or use it to replace the bridge | Every cross-entity mapping assessment |  |
| Direct-assignment evidence | Treat an entity's provider/source row and service permissions as availability evidence only. Classify an existing mapping only when the XML contains an explicit source-to-target assignment; otherwise return source_target_available when both ends are exposed | Every mapping assessment |  |
| Custom EFF source path | Accept an EFF source only when its dedicated context entity, owner key, compatible scalar types, source mapping join, and every provider view-object attribute mapping are evidenced. Reject blank, truncated, ambiguous, or unexplained provider attribute mappings | Every Custom EFF source assessment |  |
| Custom EFF service exposure | Accept an EFF source only when its service entity is non-writable input, and accept a custom target only when the target entity and attribute are exposed with write capability. Record the actual flags; do not infer omitted values | Every Custom EFF source or target assessment |  |
| Describe-backed target type compatibility | Capture the REST `Type` for the canonical property and compare it with the selected target entity's extension-attribute type. Accept a direct match only when compatible. A mismatch requires an evidenced conversion contract; do not infer coercion from a source mapping row | A described standard target property is exposed through a Service Mapping alias | resolve_described_field_exposure |
| Describe-backed target three-tab exposure | Accept the standard property as Algorithm-available only when the same alias exists on the selected target entity, maps to the exact provider view-object attribute, and has explicit Services read/write flags appropriate to the Algorithm direction | A described standard target property is absent from OMIntegration and must be exposed | resolve_described_field_exposure |
| Conditional source selection | Accept a primary or fallback source only when its exact scalar type, provider mapping, Services flags, bridge join, absence predicate, and intended cardinality are evidenced. If either standard source is absent from XML, perform current describe discovery before returning a missing-input row. For a repeated source, require a user-supplied or XML-evidenced selection rule; never choose an arbitrary row or aggregate by default. | A requested rule uses primary/fallback, coalesce, or absence-based selection | resolve_order_mapping_source_metadata |
| Requested custom-indicator mapping | Ask for every material source, target, type, conversion, or behavior detail that remains unresolved after XML inspection, documented describe research, and use-case defaults. The source EFF context/entity and indicator segment are common first inputs, not a fixed limit. Derive owner joins, provider rows, Services direction, target candidates, and default Boolean/blank/invalid behavior whenever evidence safely establishes them. | Every custom-indicator assessment | resolve_subscription_target_metadata |
| Custom EFF lineage | For an Order Header EFF, require EFF-to-OrderHeader-to-OSSTransactions-to-Subscription. For a Fulfillment Line EFF, require EFF-to-FullfillLines-to-OSSTransactions-to-Products or ProductReferenced. A direct target-to-source relation is corroboration only | Every Custom EFF assessment spanning context entities |  |
| Mapping status classification | Return only existing_mapping, source_target_available, mapping_gap, metadata_blocked, or incompatible | Every returned mapping assessment |  |
| Algorithm recommendation classification | Return only algorithm_not_required, algorithm_assessment_required, or service_mapping_prerequisite | Every returned mapping assessment |  |
| Mapping assessment output | Return context, source and target entities and attributes, availability and read/write evidence, direct-assignment evidence, candidate metadata, mapping_status, algorithm_recommendation, assumptions, prerequisites, and a per-tab UI change plan directly in chat. Use tables only for the UI change plan and for missing-input rows; present all other findings in prose. For every material independently configurable missing field or decision, return one mapping-information-request row with Required Input, Why Needed, and Usage. Revalidate supplied responses before handing off an approval-ready Algorithm draft, unless the complete plan receives an explicit affirmative response to the prescribed validation-skip question; record that as a mapping gap for the provisional path only. Do not create a human-readable Markdown plan artifact | An assessment is returned to Manage Algorithms |  |
