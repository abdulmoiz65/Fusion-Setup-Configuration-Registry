# Algorithm and Groovy Design Enforcement

## Rules

| Applies when | Required behavior |
|---|---|
| Any advisory, mapping, Groovy, validation, source-resolution, target-resolution, or use-case request starts | Run mandatory preflight first: both current XMLs must be supplied in the same request, algorithm name must match, the absolute highest version must have `ActiveFlag=Y`, and Service Mapping context must be `ARInterface`. Stop on failure. |
| Preflight passes | Classify the prompt as Input Type 1, 2, 3, 4, or 5 using `references/ora_use_case_resolution.md` before source or target resolution. |
| Groovy is drafted | Preserve the required three documented sections: both invoice and credit memo, invoice only, and credit memo only. Each section remains even when empty. |
| A comment-only starter sample exists | Remove that sample before placing new Groovy. |
| Existing executable Groovy exists | Ask whether to replace it or add new logic above it, and whether to format it. |
| Groovy is copied from an earlier version | Copy it to the eligible highest version; ask whether it may be formatted. If not, retain it and place new logic after it. |
| `ARInterface.insert([ ... ])` is added | Add exactly one concise `/* ... */` comment immediately before the block. |
| A normal AR target mapping is added | Use only the confirmed target name, value, context, optional DFF flex context, and confirmed transaction scope. Do not add `XsiType`, `AttributeType`, or other metadata keys. |
| An RA target mapping is added | Resolve the physical target column from the public Oracle `RA_INTERFACE_LINES_ALL` reference and the insert context from the current interface contract. Use `TransactionInterfaceLineDff` and confirmed `FlexContext` only when that contract identifies an interface-line DFF target; do not infer context or flex context from a column name. |
| A scenario omits target columns | Recommend targets in this order: direct documented Standard column match, then a DFF slot by confirmed/described source type and invoice/header scope. Use XML `attributeType` or companion describe type to choose `ATTRIBUTE<n>` for string/varchar/character and Boolean-as-code, `ATTRIBUTE_DATE<n>` for date/datetime, and `ATTRIBUTE_NUMBER<n>` for number/integer/long/decimal/numeric identifiers; use matching `HEADER_` families for header scope. Do not classify `...Id` as numeric unless XML or describe confirms a numeric type. Scan active-algorithm and current Service Mapping DFF usage in the same type family/context and suggest the first unused slot from 1 or the next slot after the highest used same-family slot when gaps cannot be proven. Require implementer acceptance and deployed DFF/context confirmation before Groovy. |
| An `INTERFACE_LINE_ATTRIBUTE<n>` mapping is added | Confirm source origin, flex context, and segment index before drafting. Reject `n` in `1..4` for Subscription Management `Subscriptions Context`, or `1..8` for Order Management `ORA_DOO_ORIGIN_SUBSCRIPTIONS`; stop and request another deployed target. |
| A regular `ATTRIBUTE<n>`, `ATTRIBUTE_DATE<n>`, or `ATTRIBUTE_NUMBER<n>` line-DFF mapping is added | Use `TransactionLineDff` only when confirmed by the current interface contract; do not map it as `TransactionInterfaceLineDff`. Resolve other DFF families separately. |
| A `TransactionInterfaceHeaderDff` mapping is added | Resolve the physical `HEADER_ATTRIBUTE*` target from the public Oracle `RA_INTERFACE_LINES_ALL` reference, then use the unprefixed segment name in `ARInterface.insert` (`HEADER_ATTRIBUTE5` -> `ATTRIBUTE5`, `HEADER_ATTRIBUTE_DATE1` -> `ATTRIBUTE_DATE1`, `HEADER_ATTRIBUTE_NUMBER1` -> `ATTRIBUTE_NUMBER1`). Keep the confirmed transaction-header DFF `FlexContext`; do not apply this alias to Standard, line-DFF, or header-GDF targets. |
| A confirmed Receivables `DATE` target is mapped | Use `AttributeValue: toDate(<date_expression>)`, keeping any requested offset inside the expression. When the complete confirmed value is `now()`, use `AttributeValue: now()` and do not wrap it in `toDate(...)`. |
| A skip-line control is required | Use the confirmed control contract: `AttributeName: 'SkipBillLines'`, `AttributeValue: 'true'`, `AttributeContext: 'SubscriptionsSetup'`, and a confirmed `TransactionType`. Resolve the transaction class expression from the current Service Mapping XML; for both invoice and credit memo scope use the resolved expression, and for invoice-only or credit-memo-only scope use a mutually exclusive guard and matching transaction type. Do not add `FlexContext` or metadata keys. |
| A skip-line condition is drafted | Keep the condition request-specific. Do not replace a confirmed skip control with `BillLines.SkipFlag = true` or with silent omission of normal inserts. |
| A normal AR mapping includes `TransactionType` | Resolve the transaction class expression from the current Service Mapping XML by locating the attribute mapped to `viewObjectAttribute="TransactionClass"` and using that exposed alias in Groovy. Do not assume the alias name is `TransactionClass_Custom`; it may be any Service Mapping attribute name. |
| Scope is both invoice and credit memo | Put one insert in the both-scope section with `TransactionType` set to the resolved transaction-class expression. Do not create duplicate hardcoded `INV` and `CM` inserts for the same mapping. |
| Scope is invoice-only or credit-memo-only | Keep it within its matching documented section and guard it with `if` / `else if` using the resolved transaction-class expression, for example `<resolved_transaction_class_alias> == 'INV'` or `== 'CM'`. |
| A contained alias is dereferenced | Derive access behavior from the selected action's `contain(...).cardinality(...)` declaration. `ZeroOrOne` requires `?.` on every direct property access in generated Groovy, including inside guarded blocks and `ARInterface.insert` values. A non-null guard does not permit later `<alias>.<attribute>` dereferences; use a local variable derived from `<alias>?.<attribute>` if direct reuse is needed. Direct property access is permitted only for confirmed `One` aliases or local variables. Do not hardcode entity names. |
| A described business attribute exists in multiple source families | Resolve the functional owner before Groovy. Prefer an explicitly stated source object; otherwise prefer the source family that owns the business concept. Treat copied, denormalized, or convenience fields in other families as alternatives requiring explicit acceptance. Do not choose a required or primary alias merely to avoid null-safe handling on an optional owner. |
| A Groovy source is absent from the current Service Mapping XML | Return to the companion for the matching read-only describe and an implementer source decision. Do not use an assumed alias in Groovy. |
| A source entity, source attribute, or RA target is omitted from the use case | Inspect the current `Algorithm_BO.xml` for candidate mapping patterns, use the general Subscription reference and current official Oracle documentation only as supporting discovery, then validate source candidates through the companion and target context through the RA reference and current interface contract. Present the named recommendation with alternatives and limitations; do not reuse a historical alias, target, context, or flex context by similarity alone. |
| A source attribute is stated without an object | Do not default it to any context entity. Scan current exports for exposed candidates, run permitted describe across relevant Subscriptions AR source objects, use public Subscription documentation only as business-context support, and require implementer acceptance of one describe-backed candidate before Groovy. |
| Groovy is submitted for review | Show the complete proposed Groovy directly in chat. Persist an identical project artifact for traceability, but do not require the implementer to open it. |
| Groovy approval is requested | Identify the exact chat-visible Groovy being approved. Do not create or modify `Algorithm_BO.xml` before explicit approval. |
| Groovy is placed in XML | Modify only the highest version with `ActiveFlag` `Y`, after explicit implementer approval. |
| XML handoff is prepared | Compare the changed XML action expression with the explicitly approved Groovy and block on a difference beyond line endings. |
| Approved local XML has been created | Persist the companion's Service Mapping configuration handoff with the selected sources and remaining configuration prerequisites. |
| Final implementation handoff is prepared | Include a source-target table for every mapped value: source object, source attribute, Service Mapping alias, target `RA_INTERFACE_LINES_ALL` column, `ARInterface.insert` `AttributeName`, `AttributeContext`, `FlexContext`, transaction scope, and confirmed-or-assumed status. |
