# Service Mapping Lookup Handoff

After mandatory preflight passes, classify the request as Input Type 1, 2, 3, 4, or 5 using `references/ora_use_case_resolution.md`. Use that classification to decide whether the source is already explicit, whether only the source object is known, whether only a source attribute or business term is known, or whether both source and target are missing. The classification does not replace the companion call for Service Mapping concerns.

Source-attribute discovery, REST describe selection, compatible mapping types, view-object alignment, and mapping publication are owned by the Manage Service Mappings companion skill. When the source XML lacks an attribute but the business requirement identifies its object, the companion must use that object's describe, present relevant candidates, and obtain implementer confirmation. Route those questions before drafting Groovy and use only the returned confirmed source aliases, alternatives, assumptions, and prerequisites.

If the companion cannot complete a required describe because the runtime environment connection, OAuth/authentication, privilege, transport, or describe endpoint is unavailable, stop the algorithm workflow instead of guessing. Tell the implementer describe is not working, include the observed failure category, and ask whether to resolve the runtime environment connection and rerun describe or proceed only with explicitly named, unconfirmed assumptions for review. The assumption path does not create a describe-confirmed source and does not bypass source-resolution, DFF/context confirmation, Groovy approval, or XML approval.

When the business requirement states a source attribute or business term without identifying the source object, do not default it to any context entity. Inspect the current `Algorithm_BO.xml` and Service Mapping XML for exposed candidate aliases. For Type 5, read the general Subscription reference first to classify the business area; if it still cannot identify a likely object and attribute, use current official Oracle documentation or web sources for discovery only. Then route to the companion to run permitted environment describe checks across every relevant Subscriptions AR source family: `PricingSubscriptions`/subscriptions, `PricingProducts`/subscriptionProducts, `PricingBillLines`/billLines, `PricingCharges`/charges, and `PricingARAssociations`/coveredLevels (ProductAssociations). Treat all document and export evidence as discovery only, and obtain the implementer's decision before using any source in Groovy.

When the companion returns same-name or semantically similar candidates from multiple source families, require a source-resolution record that names the functional owner and lists alternatives. Prefer an explicitly stated source object; otherwise use business ownership from the requirement and general reference as discovery context, then require implementer acceptance. Do not replace an optional functional-owner alias with a required or primary alias just to avoid null-safe Groovy.

When the missing item is an RA target, use the public RA table reference to identify direct Standard-column candidates by business meaning and source type. Derive the source type from current Service Mapping XML `attributeType` or the companion describe result before selecting a DFF family. If no Standard target directly fits, inspect the active algorithm and current Service Mapping XML for used DFF contexts and slots, then recommend a candidate from the appropriate DFF family and scope: `TransactionLineDff` for line-visible values, `TransactionInterfaceHeaderDff` for transaction/header values, and `TransactionInterfaceLineDff` only when explicitly requested or required by the current contract and not reserved. Within the selected scope, use `ATTRIBUTE<n>` for string/varchar/character and Boolean-as-code, `ATTRIBUTE_DATE<n>` for date/datetime, and `ATTRIBUTE_NUMBER<n>` for number/integer/long/decimal/numeric identifiers; use matching `HEADER_` families for header scope. Do not infer numeric from an `Id` suffix unless XML or describe confirms a numeric type. Start at segment 1 when usage is clear; otherwise suggest the next slot after the highest used slot in the same type family. Require the current interface contract, deployed flex context, and implementer acceptance before Groovy.

Named assumptions are reviewable recommendations only. They cannot bypass source-resolution records, target-context confirmation, or explicit Groovy and XML approval.
