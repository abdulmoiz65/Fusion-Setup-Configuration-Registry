# Use-Case Resolution

Use this reference when a business requirement states an intended outcome but omits a Subscriptions source entity or attribute, or a Receivables target column.

## Mandatory preflight

Before classifying or resolving any prompt, confirm that the current request supplies both the current `Algorithm_BO.xml` and the current Service Mapping source XML. The Service Mapping filename may vary. Reject the request and ask for corrected attachments when either export is missing, when `Algorithm_BO.xml` is not for `Subscription Management and Account Receivables Integration`, when the absolute highest `VersionNum` does not have `ActiveFlag=Y`, or when the Service Mapping source XML does not have `contextName="ARInterface"`. Do not use chat cache, previous project artifacts, remembered paths, or assumptions to pass this gate.

## Input type classifier

Classify every prompt after mandatory preflight and before source or target resolution:

| Input type | Prompt pattern | Required next step |
|---|---|---|
| Type 1 | The `RA_INTERFACE_LINES_ALL` target column and the Subscriptions source object plus source attribute are clear. | Scan the current Service Mapping XML for the stated source alias or a semantically matching exposed attribute. Validate the RA target through the RA reference and the current interface contract. If the source is exposed and target context is confirmed, proceed to Groovy review; otherwise call the Service Mapping companion for the missing source exposure and require implementer confirmation. |
| Type 2 | The RA target column is clear, and the Subscriptions source object is given, but the source attribute is unclear, wrong, or not exposed. | Scan the current Service Mapping XML under the stated source object. If no exposed attribute matches, call the Service Mapping companion to run that object's permitted describe, show exact and semantic candidates, and require the implementer to select a candidate, provide exact names, or accept one named recommendation. Validate the RA target separately before Groovy. |
| Type 3 | The RA target column is clear, and a source attribute or business term is given, but the Subscriptions source object is missing. | Scan all exposed ARInterface Service Mapping entities for exact or semantic matches. Read the Subscription general reference to classify the business meaning, then call the Service Mapping companion to run permitted describe across every relevant source object before recommending an object. Require implementer acceptance of one source candidate and validate the RA target before Groovy. |
| Type 4 | Neither the RA target column nor the Subscriptions source object and attribute are clear. | Scan the current Service Mapping XML for relevant exposed values, read the Subscription general reference for business fit, consult current official Oracle documentation only if needed, call the Service Mapping companion for permitted describe-backed source candidates, and run target suggestion from `RA_INTERFACE_LINES_ALL`. Require implementer confirmation of both source and target before Groovy. |
| Type 5 | Only a business use case is provided, such as needing values visible on an invoice. | Treat it as Type 4 plus an explicit outcome-level decision. Determine whether the desired result is invoice header, invoice line, credit memo header, credit memo line, or both invoice and credit memo scope. When no source object is named, read the Subscription general reference first to classify the business area; if it still cannot identify a likely object and attribute, use current official Oracle documentation or web sources for discovery only. Based on that analysis, call the Service Mapping companion to run environment describe for every relevant source object family: `PricingSubscriptions`/`subscriptions`, `PricingProducts`/`subscriptionProducts`, `PricingBillLines`/`billLines`, `PricingCharges`/`charges`, and `PricingARAssociations`/`coveredLevels` (ProductAssociations). Present candidates by object fit, then require describe-backed source confirmation and RA target/DFF context confirmation before Groovy. |

## Evidence sequence

1. Inspect the current `Algorithm_BO.xml`, including the selected active action, for existing source aliases, `ARInterface.insert` patterns, and already-used DFF target slots that might satisfy the outcome. Record each candidate's source alias, target, context, flex context, transaction scope, and DFF family when present.
2. If an attribute or business term is stated without an object qualifier, do not attach it to a default alias. Scan the current Service Mapping XML across all exposed ARInterface context entities for exact or semantic matches.
3. Before recommending any source object for an objectless attribute, invoke the Service Mapping companion to run the permitted read-only describe checks across the relevant Subscriptions AR source objects. Present exact and semantic candidates from describe, including object, attribute name, type, queryability, and mapping implications.
4. When exact or semantic matches appear in multiple source families, make a functional-owner decision before any Groovy proposal. Prefer the object explicitly named in the request; if none is named, prefer the source family whose business responsibility owns the term. Treat copied, denormalized, or convenience attributes in another family as alternatives that require explicit acceptance. For example only, a term that belongs to a detail/charge concept should not be moved to a line-level candidate solely because the line-level alias is easier to dereference. If the owner is unclear, stop and request the source object or a selected candidate.
5. Read [Subscription Management General Reference](ora_subscription_management_general_reference.md) only as supporting business context to classify terminology or prioritize candidate objects. For Type 5 with no source object, this generic reference must be consulted before any external documentation lookup so the source search starts from Subscription business meaning rather than a default alias. Public Subscription documentation cannot confirm that a source alias exists, is exposed, is published, or is safe to use in Groovy.
6. If the evidence is still insufficient, consult current official Oracle documentation or web sources to identify likely Subscription objects, attributes, or physical Receivables columns. Use the current release whenever it is available. Documentation and web results are discovery only; they cannot replace the current XML preflight, describe validation, or implementer acceptance.
7. For a source candidate, the Service Mapping companion's permitted read-only describe must validate the business object and provide candidate name, type, mapping effect, and access prerequisites. If describe fails because runtime connectivity, OAuth/authentication, privileges, transport, or the describe endpoint is unavailable, stop and tell the implementer describe is not working; ask whether to resolve the runtime environment connection and rerun describe or proceed only with named unconfirmed assumptions for review.
8. For a target candidate, use [RA Interface Lines Target Reference](ora_ra_interface_lines_all_reference.md) to validate the physical column. Use the current interface contract and deployed DFF configuration to validate `AttributeContext` and any `FlexContext`.
9. Present a named recommended functional match, its evidence, alternatives, assumptions, and unresolved limitations. Proceed only after the implementer accepts that named candidate or provides exact source and target names.

## Type 5 source-object discovery when no source object is named

For a pure business use case, do not pick a source alias by intuition. After the mandatory XML preflight and current XML scans, classify the business term through the Subscription general reference first. If that still does not identify a likely object and attribute, use current official Oracle documentation or web sources only to discover candidate Subscription object families. Then route to the Service Mapping companion for environment describe against each relevant family from this fixed coverage set:

| Candidate business area | Service Mapping object / REST describe family |
|---|---|
| Subscription header, contract, customer, lifecycle, or agreement-level value | `PricingSubscriptions` / `subscriptions` |
| Subscription product, product line, item, quantity, product lifecycle, or product-level value | `PricingProducts` / `subscriptionProducts` |
| Billing line, invoice schedule, bill-from/bill-to, bill amount basis, or bill-line value | `PricingBillLines` / `subscriptionProducts?partialDescription=billLines` |
| Charge, recurring charge, one-time charge, price, charge component, or pricing value | `PricingCharges` / `subscriptionProducts?partialDescription=charges` |
| Covered level, covered asset, covered item, or product association value | `PricingARAssociations` / `subscriptionProducts?partialDescription=coveredLevels` (ProductAssociations) |

Describe only the object families that fit the analyzed use case. If several families could fit, describe all relevant families and present the object-fit reasoning. A Type 5 recommendation must name the source object, source attribute, evidence source, Service Mapping exposure or missing-exposure status, RA target candidate, DFF/context status, and whether each point is confirmed or assumed. Do not draft Groovy until the implementer accepts the named source and target proposal.

## Target suggestion when the target is omitted

Use this path only when the customer gives a business scenario or source value but does not name the Receivables target column.

1. Classify the source value by business meaning, desired invoice visibility, transaction scope, and data type: character, date, number, Boolean/code, or amount. Prefer the concrete source type from the current Service Mapping XML `attributeType`; when the source is missing from the XML, use the companion describe candidate type. If neither XML nor describe provides a type, label the target recommendation unconfirmed and ask for the source type or permission for a named assumption.
2. Check the public `RA_INTERFACE_LINES_ALL` catalog for a documented Standard column whose meaning directly matches the value. Recommend a Standard target only when both the public catalog and the current Subscriptions AR interface contract support that target as Standard. Omit `FlexContext` for a confirmed Standard target.
3. If no Standard target is a direct match, suggest DFF candidates rather than inventing a target. Use `TransactionLineDff` for line-visible values unless the requirement is clearly transaction/header-level; use `TransactionInterfaceHeaderDff` for transaction-level values; consider `TransactionInterfaceLineDff` only when the implementer or interface contract specifically asks for that family and the reservation rule passes.
4. Choose the physical DFF column family by the confirmed/described source data type, not by the business label alone:
   - `string`, `varchar`, `character`, display identifiers, codes, and Boolean-as-code values: `ATTRIBUTE<n>` or `HEADER_ATTRIBUTE<n>`.
   - `date` or `datetime` values: `ATTRIBUTE_DATE<n>` or `HEADER_ATTRIBUTE_DATE<n>`.
   - `number`, `integer`, `long`, `decimal`, and numeric identifiers: `ATTRIBUTE_NUMBER<n>` or `HEADER_ATTRIBUTE_NUMBER<n>`.
   - Amounts should first be checked against documented amount/currency Standard columns before a DFF is suggested.
5. Treat names ending in `Id`, `ID`, or `_ID` as numeric only when the current XML or describe confirms a numeric type. If the source is a varchar identifier, display number, code, or custom text value, recommend the character DFF family (`ATTRIBUTE<n>` or `HEADER_ATTRIBUTE<n>`). If the target recommendation uses a named assumption because describe was unavailable, explicitly state the assumed type and the matching DFF family.
6. Scan the active algorithm and current Service Mapping XML for used DFF contexts and used slots in the same type family, context, and flex context. Do not let usage in `ATTRIBUTE<n>` consume an `ATTRIBUTE_NUMBER<n>` or `ATTRIBUTE_DATE<n>` slot, and do not let number/date slot usage consume character slots. Start suggestions at segment 1 and choose the first unused slot when the existing usage is clear. If gaps might be deployed elsewhere or cannot be proven from the exports, suggest the next slot after the highest used slot in that same type family and state that deployed DFF setup must confirm availability.
7. For `TransactionInterfaceHeaderDff`, show both the physical RA column and the Groovy insert name after stripping the leading `HEADER_` prefix.
8. Present the candidate as a recommendation with evidence and limitations, including the source type evidence used to choose the DFF family. Do not draft Groovy until the implementer accepts the named target and supplies or confirms the deployed DFF context.

## Boundaries

- Existing custom Groovy is evidence of prior configuration, not proof that an alias, target, context, or flex context is correct for a new requirement.
- General product documentation explains business behavior. It does not establish current Service Mapping exposure, runtime values, deployed DFF segments, or an `ARInterface.insert` contract.
- Official documentation can identify candidates but cannot replace describe validation for a missing source or the current interface contract for a Receivables context.
- Objectless source attributes require describe-backed object resolution before Groovy. If describe is unavailable because the runtime environment connection, OAuth/authentication, privileges, transport, or describe endpoint is not working, stop and ask whether to fix the connection and rerun describe or proceed only with named unconfirmed assumptions for review. If describe runs but is ambiguous across objects or lacks a viable scalar candidate, stop and request the exact source object and attribute.
- Duplicate source labels across object families are not interchangeable. Select the functional owner or get an implementer decision; do not select a primary/required alias merely to avoid null-safe access on an optional owner.
- Do not invent aliases or silently select a target by column-name similarity. When evidence is inconclusive or only a target recommendation is possible, present the candidates and request an implementer decision.
- "Go with assumptions" means the implementer permits named, evidence-backed recommendations to be presented in a reviewable proposal. It never bypasses mandatory XML preflight, source-resolution records, deployed DFF or interface-context confirmation, chat-visible Groovy review, explicit Groovy approval, or the approval gate before creating `Algorithm_BO.xml`.
