## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Direct read-only lookup | Use repository-approved authentication and the shared REST client; record the method, relative path, normalized inputs, requested fields, result count, exact match, and redacted request identifier |
| Common Lookup resolution | Invoke hcm.workforce-scheduling-management.workforce-scheduling-common.manage-common-lookups before presenting a Work Pattern Templates configuration result. Pass the documented lookupType only; retain provider-returned eligible LookupCode values and Meaning as evidence. Retain provider before-state, recommended-state, validation, and gap evidence. The provider owns Common Lookup execution and CRUD. |
| Work Pattern Templates are listed | Retrieve every collection page before presenting results; keep each template's opaque identifier internal for selection and later item lookup, and do not require an identifier to start the list operation |
| A template is requested by exact name | Use the exact-name collection resolver to obtain one selected record; keep its identifier private and pass it to the item-detail resolver rather than requiring the user to provide it |
| Relevant templates are compared with the request | Display each template's classification as Suitable for reuse, Suitable for duplication, or Unsuitable, followed by the business differences that support the classification. Never recommend reuse when any compared behavior or value differs. |
| Lookup code and meaning are both supplied | Verify that they identify the same returned row; retain the code for processing and the meaning for business-facing output |
| A display meaning is supplied without a code | Use it only to locate candidates; continue only after one exact result supplies the documented code |
| Shift details are supplied without an Enterprise Shift selection in a flow that supports Enterprise Shifts | Search all pages of active Enterprise Shifts and compare only supplied configuration and behavior details. Select exactly one complete match automatically. Return selection_required only when multiple complete matches exist, after presenting all complete matches for user selection. When no complete match exists, return resolved with supplied local values; do not prompt for an Enterprise Shift and do not create one. Do not perform this lookup for Duration or Flexible days and times |
| The user selects a suggested Enterprise Shift | Resolve the selected shift exactly and verify it remains active before using its configured values |
| The user chooses to create a new shift | Hand off to the separate Enterprise Shifts task and resume Work Pattern Templates only after that task verifies the new active shift; do not encode or execute the other task inside this task graph |
| A LevelTypeCode changes | Discard any previously resolved LevelObjectId and resolve the object again from the correct provider |
| A Data Loader update is prepared | Retrieve WorkPatternCode explicitly because compact template responses can omit it; retain the exact returned value only for the update artifact and do not create one from a name |
| A Data Loader deletion is prepared | Use the verified WorkPatternTemplateId as the deletion identity; do not require or retain WorkPatternCode for the deletion artifact |
| A new Shift and its Breaks are prepared | Allocate one unique Data Loader-only WorkPatternShiftId correlation value for the new Shift; use it only to associate new child Break rows, and do not attempt a prior Fusion lookup for that value |
| DayOfWorkPattern is generated | Map Sunday to 1, Monday to 2, Tuesday to 3, Wednesday to 4, Thursday to 5, Friday to 6, and Saturday to 7 after the day lookup resolves |
| Authentication or authorization failure | Stop; a 401 or 403 is not evidence that the template, lookup, shift, or assignment object is absent |
| An approved asynchronous request is accepted | Immediately start the task-authorized Data Loader status request. If it reports in progress, automatically issue follow-up status requests to a terminal result. Automatically monitor the documented Data Loader status to a terminal result only through those task-authorized status requests. Do not require separate user status approval. On terminal success, complete the exact-template read-back and return the verified terminal summary; on terminal failure, timeout, or mismatch, return the sanitized failure summary and safe resume action. |
| Component-private contract is unresolved | Do not invent the publicWorkers base, an HCM Rules delete URL, private condition-builder response fields, or component-internal query details |
