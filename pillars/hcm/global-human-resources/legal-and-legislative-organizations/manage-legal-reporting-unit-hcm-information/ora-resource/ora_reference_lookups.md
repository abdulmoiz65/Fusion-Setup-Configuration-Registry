# Legal Reporting Unit HCM Information Reference Lookups

## Purpose

Defines deterministic, read-only target, metadata, context, value-set, and
history resolution. The advanced-search action is retrieval-only even though
its HTTP method is POST. Classification writes are owned by the registered
Core Data Loader business-object contract, not by a lookup.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| A lookup requires authentication | Use core.auth.fusion-oauth-authentication |
| A Fusion REST request runs | Use core.fusion-api.rest-api-client and send REST-Framework-Version 9 as a header when required; do not use core.data-loader for reads |
| Advanced search executes | Use the current action describe, requested Name, supported display and search fields, required header, and complete bounded paging. Every request body must include `filters` as an array, even when the action describe marks it optional. When no filters are supplied, include `"filters": []` immediately after `displayFields`; never omit `filters` or send null. Apply this requirement to the initial search, every pagination request, and every refresh or reconciliation search. Its POST is read-only retrieval. Confirmed environment evidence: omitting `filters` returned HTTP 400; the same request with `"filters": []` returned HTTP 200 |
| Both classification properties are I, null, or absent | Treat both branches as inactive and ask both business-facing classification Yes/No questions when classification is required |
| One exact LRU is selected | Reuse a successful terminal ManageLegalReportingUnit synchronization for the same normalized identity and environment from this session when it is no more than 24 hours old; otherwise use the registered object through Core Data Loader once and poll it to terminal status. Refresh advanced search. For classification, resolve OrganizationId from organizationsLOV by exact Name plus ClassificationCode=HCM_LRU even when its status is inactive. Resolve TRU and Reporting Establishment roots by exact EstablishmentId only after their properties are active. Do not treat synchronization approval as classification approval or reuse evidence across sessions |
| A read omits an effective date | Resolve EffectiveReadDate to today's system date and append &effectiveDate={EffectiveReadDate} to every top-level applicable-root GET |
| A read explicitly supplies an effective date | Normalize it to YYYY-MM-DD as EffectiveReadDate, append &effectiveDate={EffectiveReadDate} to every top-level applicable-root GET, and follow the child links returned by that response |
| Both classification Yes/No answers are supplied | A clear `Both` or `Yes to both` response to the two pending questions is explicit Yes/Yes. Do not ask again. Resolve OrganizationId through resolve_lru_classification_organization, map both answers internally, resolve the live ManageLegalReportingUnitHcmClassifications loader contract, and immediately hand one classification-only archive to core.data-loader for its preview and approval gate; do not repeat ManageLegalReportingUnit or treat the classification answer as upload approval |
| Classification load response is missing or uncertain | Reconcile once through advanced search; continue only when both properties match the approved active/inactive targets and never replay automatically |
| One or both properties are A | Resolve each A branch independently using the exact current EstablishmentId query and retain that root's returned OrganizationId |
| Root CategoryCode is localized or base | Use the exact returned value in polymorphicType; do not append a suffix |
| Generic TRU details request | Show Tax Reporting Unit details, then `EFF Name: Tax Reporting Unit HCM Information`; retrieve only contexts mapped by current metadata to Tax Reporting Unit Details. Confirmed request evidence includes TRU Type, Associated Legal Employer, and Currency contexts, but runtime metadata is authoritative. Under each context heading show configured segments and display values only, or `No configured segments` when its mapped context has zero rows |
| Generic Reporting Establishment details request | Show Reporting Establishment details, then `EFF Name: Reporting Establishment HCM Information`; retrieve only contexts mapped to Reporting Establishment Details. Confirmed request evidence includes Organization Manager Information, but runtime metadata is authoritative. Under each context heading show configured segments and display values only, or `No configured segments` when its mapped context has zero rows |
| A context is rendered for View | Render its business label as a heading and list only configured business segments using display values; do not expose technical names, identifiers, or audit fields |
| Currency segment is requested | Resolve it through the TRU Currency context in Tax Reporting Unit Details; current confirmed request contract maps it to truCurrencyCode and creates the context when absent |
| Reporting Name segment is requested | Resolve it through Organization Manager Information in Reporting Establishment Details; current confirmed request contract maps it to _REPORTING_NAME and creates the context when absent |
| Another category is explicit | Retrieve only contexts assigned to that exact business category |
| Value-set metadata exists | Resolve only the describe-declared LOV resource and exact filter under /fscmRestApi/resources/{resolvedVersion}:9/; do not invoke an EFF value set under /hcmRestApi. When the declared value set is table-validated, follow its returned validation-table or validation-view contract. For `FromClause=fnd_lookup_values_vl` with `WhereClause` identifying `lookup_type`, use `/fscmRestApi/resources/{resolvedVersion}:9/commonLookupsLOV?finder=LookupTypeFinder;LookupType={lookup_type}`; match the requested display value exactly against `Meaning` and write the returned `LookupCode`. Do not use `standardLookupsLOV` for this contract. For another returned table or view contract, resolve the exact displayed value to its configured stored value and continue automatically to loader preparation. Stop only after that returned contract produces zero, multiple, inactive, or type-incompatible matches; display the label and write the typed stored value |
| Runtime rv LOV URL is returned | Follow a fresh server-returned /fscmRestApi/rest/rv:{runtimeId}/en/{resolvedVersion}:9/ URL only in the current authenticated runtime; treat the runtime ID as token-scoped and do not construct, cache, persist, or reuse it |
| Internal search or synchronization runs | Emit no user-facing endpoint, identifier, raw loader field, payload, progress, or log narrative; Core Data Loader owns the synchronization preview and every later mutation preview separately |
| Root or EFF traversal needs child links | Do not use onlyData=true; retain and follow the fresh opaque links returned by the service |
| A mutation precheck runs | Complete applicable read-only lookups before Core Data Loader source preparation; never construct or execute a direct REST write |
| DE Delete selection runs | Fetch complete history and applicable roots before Core Data Loader preview; bind loader approval to the selected range and immutable source |
| Edit operation mode is required | Compare the requested operation EffectiveStartDate with the affected taxReportingUnitsEFF or reportingEstablishmentsEFF top-level organization's current EffectiveStartDate. Equality selects CORRECTION and ModifyOrganizationUnitForChildCorrect; a later date selects UPDATE and SplitOrganizationUnitForEFFUpdate; an earlier date is invalid. Apply the same comparison when the EFF child context is new. OrganizationEffectiveStartDate and classification dates are locators and must not select the mode |
| An existing EFF child is edited | Use the fresh selected row's current OrgInformationId, EffectiveStartDate, and EffectiveEndDate as its child identity without alteration. Use the requested operation date only in fields where the selected live contract requires it. Different dates across top-level, existing-child, and new-child rows are valid; do not substitute the requested operation date for a current child date, force the rows to match, invent a locator column, or infer the generated REST path |
| A new EFF child is created | Use RestAction POST. Leave OrgInformationId, EffectiveStartDate, and EffectiveEndDate blank. Populate only the available parent locator set—OrganizationId, OrganizationEffectiveStartDate, OrgUnitClassificationId, OrgUnitClassEffectiveStartDate, and OrgUnitClassEffectiveEndDate—from fresh state; use the requested operation date only in effectiveOf and the embedded action |
| Parent date-effective delete is required | Use the current OrganizationId and selected complete-history EffectiveStartDate as organizationId and effectiveStartDate in DeleteOrganizationUnitForDTDelete; do not substitute an EFF child date or add EFF/root locator identifiers |
| Core Data Loader completes | Refresh applicable roots, contexts, and history only after completion; treat those calls as verification and require the requested values and effective boundaries |
| LRU HCM Information history is requested | Use only HcmLeLruOrganizationHistoryDef with the current validated organizationId; do not substitute EnterpriseHistoryDef |
