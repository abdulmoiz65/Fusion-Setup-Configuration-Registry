# Legal Reporting Unit HCM Information Dependency Readiness

## Purpose

Defines identity, classification changes, active branches, EFF context,
effective history, and the Core Data Loader route required before EFF mutation.
Application Profile Option, Lookup, Value Set, Flexfield, REST API, Common
Applications, Legal Entity, Business Unit, and Legal Jurisdiction and Authority
skills must already be available; this task never changes them automatically.

## Required Dependency Order

| Sequence | Dependency | What Must Happen |
|---|---|---|
| 1 | Authorized Fusion environment | Resolve one environment, identity, and required read or Data Loader privileges |
| 2 | Unique LRU | Run read-only advanced search and select one exact Name match |
| 3 | Organization synchronization | Reuse a successful terminal ManageLegalReportingUnit synchronization for the same normalized LRU identity and environment from this session when it is no more than 24 hours old; otherwise use it through Core Data Loader once and poll to terminal status. Refresh advanced-search facts. Never reuse evidence across sessions |
| 4 | Classification readiness | Inspect refreshed properties and ask both business-facing classification Yes/No questions when a classification change is required |
| 5 | Pre-classification identity | When classification is required, resolve one OrganizationId from organizationsLOV using exact Name and ClassificationCode=HCM_LRU. Do not wait for an active TRU or Reporting Establishment root; those roots are created by classification |
| 6 | Classification change | Resolve only ManageLegalReportingUnitHcmClassifications and hand the exact archive to Core Data Loader. When classification is a prerequisite for a pending explicit Get or Edit, poll that accepted load to terminal status as this task's continuation step, refresh properties, resolve the active branch roots and requested contexts, and resume the pending operation; otherwise return the accepted standalone classification initiation response |
| 7 | Applicable roots | Resolve taxReportingUnits, reportingEstablishments, or both from refreshed active classification facts only after classification completes |
| 8 | Localized metadata and current data | Use each root's exact CategoryCode, expand its EFF envelope, follow returned links, and resolve value sets |
| 9 | Edit or delete boundary | Resolve context-row existence, every affected top-level organization's current EffectiveStartDate, and each selected parent EFF row's complete locator key for Edit, or complete HcmLeLruOrganizationHistoryDef history for DE Delete |
| 10 | Core Data Loader route | Select only ManageLegalReportingUnitHcmClassifications for a classification change; select taxReportingUnitsEFF, reportingEstablishmentsEFF, or both from affected branches for EFF work and pair them with ModifyOrganizationUnitForChildCorrect for a correction or SplitOrganizationUnitForEFFUpdate for a dated update; select only DeleteOrganizationUnitForDTDelete for parent deletion; require current loader metadata support |
| 11 | DAT operation contract | For synchronization, require current establishmentId and RestAction POST. For classification, map both Yes/No answers internally and require the organizationsLOV-derived organizationId and advanced-search establishmentId plus RestAction POST. For every EFF context mutation, including a new child, compare the operation date with the top-level organization start and require ModifyOrganizationUnitForChildCorrect when equal or SplitOrganizationUnitForEFFUpdate when later. An existing child preserves its fresh current OrgInformationId, EffectiveStartDate, and EffectiveEndDate. A new POST child leaves all three child fields blank. Both forms populate the available parent locator set—OrganizationId, OrganizationEffectiveStartDate, OrgUnitClassificationId, OrgUnitClassEffectiveStartDate, and OrgUnitClassEffectiveEndDate—from fresh state. Validate rows independently and populate only fields declared by the exact selected object's live template. For parent deletion require one DeleteOrganizationUnitForDTDelete row with RestAction POST and its five current template fields |

## Dependency Classification

| Result Category | When Used | Can Run Lookup/Create? |
|---|---|---|
| Satisfied | Every applicable dependency has exact authoritative evidence | No |
| Lookup | A documented resolver can resolve an applicable dependency | Read-only lookup only |
| Verify | Existing evidence must be confirmed without creating or changing setup | No |
| Not Applicable | A dependency condition is false | No |
| Needs Input | A required selector, date, scope, or row key is missing | No |
| Unresolved | Identity, classification, metadata, row, loader support, or approval evidence is absent or ambiguous | No |
