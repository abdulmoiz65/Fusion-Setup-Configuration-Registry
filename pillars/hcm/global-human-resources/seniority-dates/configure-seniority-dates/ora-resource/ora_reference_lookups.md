## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| A REST describe LOV declares source-to-target attributeMap | Use that exact resource, filter, source field, and target field; do not substitute a similarly named lookup. |
| Resolving an exact Legal Employer display name | First call `legalEmployersLov` with the documented, URL-escaped equality predicate `q=Name='<exact name>'`, `onlyData=true`, and only the required fields. When Fusion returns one or more matching rows, apply exact-name cardinality rules to that filtered result. If the endpoint rejects the filter or its response cannot establish the requested name, retrieve every bounded page and apply the same exact-name rule locally. |
| A describe field has no LOV | Use only derive_seniority_configuration_tuple when it owns that field; it may apply an approved task default only after current template and schema validation, otherwise stop. |
| A delimited selector contains multiple members | Resolve members independently, deduplicate exact stored values, and serialize only with the comma delimiter declared by describe and accepted by the live Data Loader attribute. |
| A `SelectCollAgreementName`, `SelectLegalEmployerName`, `SelectLegislationCode`, `SelectUnionName`, or `SelectWorkerType` field is submitted through the UI-backed contract | Split a caller's comma-separated values, trim and resolve every member, then serialize one or more values as a JSON array. Never send a scalar value: Fusion requires an array even for one member. For Data Loader source rows, retain compact JSON such as `["Employee"]`; do not stringify it as a Python list such as `['Employee']`. |
| A REST-only Select... attribute is absent from the registered Data Loader schema | Keep it as read or preview evidence and write only its resolved Data Loader ID or code field. |
| Create intake is incomplete | Identify every missing required business-controlled value and ask once for exactly those values. Do not resolve references, check uniqueness, derive a tuple, prepare a source, preview, request approval, or infer compatibility from any lookup display text. |
| Rule, attribute, and level are resolved after complete intake | Treat the independently resolved lookup values as reference validity only. Never parse or compare a code, suffix, naming pattern, or lookup Meaning to infer cross-field compatibility. |
| A create combination has authoritative compatibility metadata | Validate only against a current documented metadata contract that explicitly binds the exact supplied values. Identify that source when it proves a conflict; absence or ambiguity is reported as compatibility could not be established, not a conflict. |
| Technical fields are derived for create | Use the current operation-specific create template as the authority for field presence and requiredness. Use the approved task default map for supported mapped values; never make `SeniorityVersion` mandatory merely because a prior row has it blank or the functional area supports V3. |
| No current row uses the resolved TriggeringField | Continue with current create metadata or a reviewed same-release exact-TriggeringField source; do not require a seed configuration. |
| Only a related attribute has a tuple | Reject it; for example, one attribute's tuple never proves another attribute's tuple. |
| Edit or delete targets an existing rule | Preserve the exact current tuple and keys; do not rederive or replace omitted values. |
| Update or delete target is fresh | Invoke evaluate_seniority_rule_usage before source generation, preview, and execution revalidation. Use only the mapped action result for RecordPresent; never use the configuration row's null or absent field. |
| Multiple applicable resolvers are declared | Run each resolver in graph order in the same turn; continue after every resolved result. |
| A returned configuration row is displayed | Resolve SeniorityDateCode, TriggeringField, LevelCode, Active, DisplayInUI, Cumulative, and AllowEdit through their declared current lookup types. When a displayed detail includes Seniority Basis or Source Field, resolve them through `ORA_PER_SENIORITY_SETUP_BASIS` and `ORA_PER_SRC_FIELDS`. Require exactly one exact current match for each code and report missing or ambiguous display values without guessing. |
| An all-configured-rules response is rendered | Retrieve every bounded page from `commonLookups/{LookupType}/child/lookupCodes` for `ORA_PER_SENIORITY_ITEMS`, `ORA_PER_TRIG_FIELDS`, `ORA_PER_SENIORITY_LEVELS`, and `YES_NO` before resolving returned codes. For an explicit detail field, retrieve every bounded page for its declared lookup type, including `ORA_PER_SENIORITY_SETUP_BASIS` and `ORA_PER_SRC_FIELDS`. A parent `expand=lookupCodes` response may be a default-sized subset and must never be treated as an exhaustive lookup catalog. |
| An unqualified list request | Return only parsed rows with `Active=Y`. When the collection API cannot filter `Active`, discard inactive rows before resolving lookups, creating artifacts, or composing the response. |
| An explicit inactive-rules request | Return only parsed rows with `Active=N`. When the collection API cannot filter `Active`, discard active rows before resolving lookups, creating artifacts, or composing the response. |
| An explicit all-configured-rules request | Return every parsed configuration row, including inactive, UI-hidden, blank, and `N`-flag rows. |
| Multiple explicit read filters are supplied | Retain only rows satisfying every supplied filter, together with the resolved Active, inactive, or all-rules scope. |
| Visibility details are requested | Render Active and Display in Guided Flows separately in addition to the standard six display columns. DisplayInUI is UI visibility, not worker-data access control. |
