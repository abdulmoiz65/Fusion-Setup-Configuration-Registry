# Areas of Responsibility Template Reference Lookups

## Purpose

Defines deterministic, read-only reference resolution for this task. Use each
resolved value only while authoring a source from the current live Data Loader
template; do not turn this reference into a fixed DAT header or value registry.

## Read Reconciliation and Presentation

For every resolved parent read, treat direct `AoRTemplateScope` and `AoRTemplateCriteria` values as stored keys, not user-facing display text. Reverse-resolve each static stored ID, code, or code-plus-set through the same registered attribute-specific LOV or Common Lookup contract used for authoring. For consolidated comma-separated criteria values, resolve and display each value independently. Present the human-readable value first and show the stored ID, code, and set only as supporting evidence. Retain the exact keys in the run state for future update/delete targeting. If an exact reverse lookup returns zero or multiple rows, display `Unresolved persisted value` with the raw stored key and resolver name; never guess a meaning, rewrite the stored data, or use a partial match. For the supported dynamic scope sentinel (`DefaultValueNumber=-999`), display Dynamic Value enabled and do not invoke an LOV resolver.

## Dynamic Scope Reconciliation

- For GET and post-load reconciliation, treat a scope as Dynamic Value enabled when `DynamicValueFlag=Y`, or when `AttributeName` is `AOR_BUSINESS_UNIT`, `AOR_DEPARTMENT`, `AOR_LEGAL_EMPLOYER`, or `AOR_LOCATION` and Fusion returns `DynamicValueFlag=null` with `DefaultValueNumber=-999`. Normalize this as `DynamicValueEnabled=true`, omit `DefaultValueNumber` from the static value display, skip any LOV resolver, and preserve dynamic mode for later updates unless the user explicitly changes it.
- Do not interpret `DefaultValueNumber=-999` as dynamic for another attribute. Preserve it as an unexpected persisted value and report that reconciliation warning.

## Contains Search Regression Check

- A contains search for `AOR FDOS Basic` must call `fusion_rest_client.py` with `--header 'REST-Framework-Version: 9'`, `q=TemplateName like '%AOR FDOS Basic%'`, and a bounded `limit`.
- Exact TemplateCode, exact TemplateName, TemplateId, parent-item, and child-collection GETs must not gain that header.
- This GET-only search must not invoke HDL/DAT generation or a Data Loader workflow.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| A lookup requires authentication | Use core.auth.fusion-oauth-authentication. |
| An exact target or reference is required | Accept exactly one eligible result; stop on zero or multiple results. |
| A collection is requested | Use bounded limit and offset pagination and follow hasMore or the next page only to the declared bound. |
| A LOV rejects an exact display-name `q` filter | Use a supported identifier filter when available (for example, Department `OrganizationId`); otherwise use the bounded collection fallback and trim only incidental outer whitespace before exact comparison. |
| Multiple applicable resolvers are declared | Run each resolver and map its result to the exact registered source field in graph order in the same turn. Return only resolved or a concrete blocker; never return pending. |
| A scope or criterion has an attribute and value | Resolve the attribute and its value independently. Persist the requested value, resolver, matched display value, stored key, and target source field in the approval mapping; write only the resolved stored key to the source workbook. |
| A resolver uses a live response | Do not persist returned tenant identifiers or display values in reusable skill guidance; retain them only in the current run evidence and source workbook. |
| A bulk request has invalid rows | Do not generate or upload an archive. Report each invalid row and failed field, retain resolved valid rows in the current request state, and ask whether to continue with only those rows. Generate a fresh valid-only archive only after explicit approval. |
