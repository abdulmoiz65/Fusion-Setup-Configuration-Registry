## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| `payGenericRestQuery` finder is assembled | Send one `finder` query parameter in the form `finder=findByWord;PayRestName=<PVO>,AdditionalViewCriteria=<criteria>,ParameterKeys=<keys>,ParameterValues=<values>,DisplayAttributes=<attributes>`. The semicolon appears only after `findByWord`; commas separate all remaining finder inputs. Do not send `PayRestName`, `AdditionalViewCriteria`, `ParameterKeys`, `ParameterValues`, or `DisplayAttributes` as separate URL query parameters. Encode `&#124;&#124;` as `%7C%7C` only in a rendered URL. |
| Lookup source is not documented | Keep the resolver with TBD contract fields and block preview |
| Legal reporting availability is requested | Route the POST through `core.fusion-api.rest-api-client`, take the host from `core/auth/fusionEnv.properties`, and obtain any required browser `rv:` route identifier from the active environment rather than a stored capture |
| Legal reporting availability returns one or more rows | Return only `Legal Reporting Unit names:` and every candidate `Name`, one name per line in response order. Do not number names or expose technical fields by default; retain them internally |
| Legal reporting availability returns multiple rows with downstream card intent | After returning the names-only list, wait for the user to select one before TRU or card lookup; do not auto-select by similarity. A list-only request needs no selection |
| TRU launch scope is parsed | Treat the parsed establishment ID and display value as launch context; resolve sourceId and LDG through OrgTaxReportingUnitPVO before execution |
| User-confirmed TRU parity is used | Verify the first read-only getCardDetails response returns sourceType=TRU before preparing HDL |
| User supplies IDs directly | Treat them as optional hints only; independently resolve and validate them from business context. Never ask a functional user for an ID |
| OrgTaxReportingUnitPVO returns OrganizationId and LdgId | Use OrganizationId as calculationEntries sourceId, LdgId as legislativeDataGroupId, and sourceType=TRU |
| User supplies legislation code, LDG ID, or PSU ID for TRU or Legal Reporting Unit Org Cards | Call OrgTaxReportingUnitPVO with the matching AdditionalViewCriteria and ParameterKeys: findByLegislationCode/pLegislationCode, findByLdgId/pLdgId, or findByPsuId/pPsuId. Combine multiple criteria, keys, and values with &#124;&#124; in the same order. Return only names for list-only requests and keep IDs internal |
| OrgTaxReportingUnitPVO returns LdgId and the LDG name is requested or needed for HDL | Pass LdgId unchanged to resolve_legislative_data_group_name; do not derive the name from the TRU name, parent legal entity, legislation, or naming convention |
| legislativeDataGroupsLOV returns exactly one matching row | Return `Legislative Data Group name:` followed by the exact Name; retain LegislativeDataGroupId and LegislationCode internally unless technical details are requested |
| legislativeDataGroupsLOV returns zero rows, multiple exact matches, an ID mismatch, incomplete paging, or an authorization error | Stop the owner-to-LDG chain and report the lookup failure without guessing or treating authorization denial as absence |
| HDL existing-card discovery is requested | Use owner-scoped getCardDetails mode=G without dirCardId, retain the unique returned ID internally, and repeat exact drilldowns needed to prove current/future/history state. Zero across complete state selects mode=ADD; a single-date miss or failed lookup does not prove absence |
| Generic REST DisplayAttributes are serialized | Use the runtime double-pipe separator between attributes; URL-encode it as %7C%7C only when representing the finder as a URL |
| Name lookup returns no match or multiple matches | Do not choose a value; return the candidate issue to the user |
| Lookup is claimed to be local | Accept local authority only when the source explicitly identifies the local task-context source |
| payrollGenericLOV response includes ResultValue fields | Map ResultValue columns according to the DisplayAttributes order from the finder |
| payGenericRestQuery returns count zero for ComponentContextPVO | Treat context metadata as absent for that component; do not invent context fields |
| A card has different override fields than another card | Treat the card's getCardDetails override metadata as authoritative and ignore non-returned fields |
| Existing card, component, override/FLEX/value, assignment/association, or related row is found | Keep returned keys internally, disclose business names/value/intervals, and ask for Update or Correction. Never auto-update, apply new-row defaults, or emit unresolved placeholders |
| Current/default component flexfield values are requested | Select one exact component and keep only `overrideType=FLEX` rows. Return `Flexfield values:` and one `Name: Value` line per row; use `title` before `name`, render null or empty as `Blank`, and return `None` when no FLEX rows exist |
| An LOV-backed current flexfield value contains a stored code | Resolve one display meaning from the metadata-declared dataSource when possible. If zero or multiple meanings match, return the stored value and do not guess; this fallback is for read-only display and does not validate the value for future HDL |
| Allowed or available flexfield values are requested | Run the metadata-declared LOV option-list lookup. Do not replace the current/default value list with an allowed-values list unless the user asks for options |
| Override dataSource references a value set | Call payrollGenericLOV with the value set and required binds extracted from metadata |
| Override dataSource references a dependent bind | Resolve the parent field or context value first, then call the child resolver |
| Override metadata lacks a usable dataSource for an LOV | Block the LOV value instead of guessing the resolver |
