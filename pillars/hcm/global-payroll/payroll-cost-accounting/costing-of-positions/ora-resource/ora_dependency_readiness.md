# Position Costing Dependency Readiness

## Required Dependency Order

| Sequence | Dependency | What Must Happen |
|---|---|---|
| 1 | Legislative Data Group | Run resolve_legislative_data_group for user-facing LDG Name text and confirm_legislative_data_group for the chosen candidate or an already known internal ID before LDG-scoped Position search. Pause for ambiguous candidate selection; keep the ID internal. For Create/Add, stop here if the confirmed LDG has a null or blank CostAllocationIdFlexNumber. |
| 2 | Position discovery and selection | Resolve an optional Position Type and local Status, then search_position_costing_by_criteria with an explicit search date or today's default. Ask for PositionName before considering any technical PositionCode; resolve LDG Name and Type through their upstream filters. Lists may return zero or many complete rows. Use resolve_position_source for exact detail/HDL; a no-costing candidate remains valid. Resolve_position_business_unit is an additional HDL-only dependency: complete its two stages under ora_reference_lookups.md, binding the Position-derived BusinessUnitId and resolved BusinessUnitName to the sealed source, date and environment. |
| 3 | Runtime Costing KFF | Resolve metadata and validate values only for segment input/display or physical account layout; candidate lists do not need KFF or account fan-out. |
| 4 | Account sequence | For Create and effective-dated Update, ignore a supplied sequence, assign SubTypeSequence 1 to the first supplied account row, and increase by 1 for each following row. For Correct MERGE, use a positive REST-resolved value when present; otherwise ask the user for the exact positive HDL value. Physical DELETE operations do not require or invent a sequence. |
| 5 | Current state and history | Resolve parent and accounts for Update or Correct. A Correct child DELETE must use one sealed Generic Costing request and its exactly one terminal source-bound parent response; select its child only from that sealed state. For End Date or Zap, create an immutable request/response envelope for each PayCostSearchVO page, require returned offset and limit to equal the sealed request, aggregate constant-limit contiguous offsets beginning at zero through final hasMore=false, then obtain one identity-matching Generic Costing detail result for every history occurrence. |
| 6 | Current template | Validate CostAllocationV3 and CostAllocationAccountV3 source/schema with core.data-loader. |
| 7 | Approval | Bind Task Hook validation and fresh approval to the immutable ZIP SHA-256 and target environment. |
| 8 | Status and verification | After accepted initiation, return pending. Use loader status and matching Generic Costing GET only when the user explicitly asks to check status. |

## Dependency Classification

| Result Category | When Used | Can Run Lookup/Create? |
|---|---|---|
| Satisfied | Exact input or resolved evidence is already present. | Yes |
| Lookup | A documented read-only REST resolver can resolve the value. | Yes |
| Selection required | LDG or Main Search Position discovery needs the user's choice among complete distinct candidates. | No downstream lookup or mutation until selected; candidate presentation is allowed and the chosen Position returns through source validation. |
| Verify | Current template, state, or approval evidence must be checked. | Yes |
| Blocked | Identity, KFF, template, or approval evidence is absent or ambiguous, or a generated sequence is invalid. | No |
