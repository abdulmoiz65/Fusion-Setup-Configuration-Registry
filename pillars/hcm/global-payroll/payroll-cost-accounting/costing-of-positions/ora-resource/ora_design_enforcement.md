# Position Costing Design Enforcement

## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Select route | Route supported mutations only to HDL. Route read-only requests to their documented GET resources; Position-bound Business Unit enrichment follows the existing resolve_position_business_unit dependency and its resolve_business_unit stage. |
| 2 | Resolve identities | Confirm LDG before Position discovery; for Create/Add, stop immediately if its confirmed CostAllocationIdFlexNumber is null or blank. Select one source only for detail or HDL. Lists need neither BU nor account metadata. HDL additionally resolves BU; account input/display resolves KFF and values. Preserve existing sequence rules for Create/Update and Correct. |
| 3 | Validate source | For HDL only, complete core.data-loader source/schema review against current CostAllocation templates. Steps 4 through 7 also apply only to HDL, not Query. |
| 4 | Build archive | Build one immutable archive with only the members required by the operation. |
| 5 | Gate side effects | Bind Task Hook validation and fresh approval to the exact archive SHA-256. |
| 6 | Report initiation | After accepted loader initiation, return pending and explain that the load can take several minutes. |
| 7 | Check on request | Only when the user requests status, use the declared loader status route and then use matching read-only GET after terminal success. |

## Design Rules

| Applies When | Severity | Required Lookup | Blocking Condition | Recommendation | Fix Allowed? |
|---|---|---|---|---|---|
| Read-only discovery | Error | search_position_costing_by_criteria | Incomplete results are presented as complete, no-costing Positions are rejected for blank allocation fields, or BU/HDL prerequisites block a list. | Use the complete finder and source-selection contract; distinguish candidate existence, costing presence and active status. | Yes |
| LDG-scoped operation | Error | confirm_legislative_data_group | A candidate was not confirmed, ambiguity was silently resolved, or blank returned LDG fields were filled as if a costing association existed. | Confirm LDG independently; preserve absent association and compare populated associations. | Yes |
| Create/Add LDG cost structure | Error | confirm_legislative_data_group | The exact confirmed legislativeDataGroupsLOV item has a null, empty, or whitespace-only CostAllocationIdFlexNumber. | Stop before Position discovery, account validation, DAT rendering, archive creation or loader handoff. Show the exact LDG-specific error from ora_error_handling.md; do not invent a flex number or request one from the user. | No |
| Create absence preflight | Error | query_position_costing | Search absence alone is treated as proof that no date-specific allocation exists. | Require the normalized exact-source GET to prove absence before Create preparation. | Yes |
| Account validation and display | Error | resolve_cost_account_segment_meanings | Hardcoded columns/LOV resources, first-page absence, discarded leading zeros, wrappers interpreted as accounts, or parent fields wrongly required on children. | Normalize complete parent/account/KFF state and resolve runtime columns and values. | Yes |
| Create | Error | resolve_position_business_unit | Existing allocation, ambiguous Position/Business Unit/LDG, invalid KFF, a supplied SourceType other than POS, a #NULL account segment, a generated SubTypeSequence that is not positive and consecutive from 1, or total above 1. | Correct source data and generate 1 through N in supplied account-row order before building the parent and account members. | Yes |
| Update | Error | query_position_costing | Missing exact state, invalid effective date, missing SET PURGE_FUTURE_CHANGES N, invalid account distribution, a supplied SourceType other than POS, a #NULL account segment, or an invalid generated sequence for a new account collection. | Begin the parent DAT member with SET PURGE_FUTURE_CHANGES N, generate 1 through N for a new collection, and validate the live template. | Yes |
| Create or effective-dated Update preparation | Error | | A successful lookup, render, archive, or validation step is treated as an intermediate pause. | Continue through defaults, state checks, DAT render, source/schema validation, immutable ZIP, and Task Hook preview before requesting fresh approval. | Yes |
| End Date | Error | query_position_costing_history | PayCostSearchVO history is not an immutable request/response page sequence with returned offset and limit matching each request, constant-limit contiguous offsets from zero ending in explicit hasMore=false; a Generic Costing detail is missing or extra; parent ID/date/sealed source identity disagrees; PositionCode, LDG name, or BusinessUnitName differs from sealed source evidence; the selected parent is not the last effective parent; a later split exists; requested end date precedes start or extends past that parent's current end date; or ReplaceLastEffectiveEndDate=Y is missing. | Build a parent-only HDL MERGE only after complete sealed history, exact detail fan-out, identity-bound parent keys, interval-bound validation, and component-support validation. | Yes |
| Correct physical DELETE | Error | query_position_costing | Missing a sealed current Generic Costing GET request and terminal exactly-one parent response, Position/LDG/source/date mismatch, missing physical IDs, record ID, POS source type, effective date, source subtype, runtime segment layout, stale state, invalid KFF, ambiguous account scope, #NULL in an account segment, or blank/null/#NULL target clear intent. | Build one non-composite HDL account package for one child action only after resolving it from source-bound current state. Do not accept a caller identity or raw account dictionary. A physical DELETE uses complete resolved technical identity and populated segments with its runtime layout without inventing a sequence. Do not enable a segment clear until a current template-validated HDL contract exists. The fresh immutable-ZIP approval is the sole execution approval; do not require or attempt a REST mutation or fallback approval. | Yes |
| Correct MERGE sequence | Error | resolve_correct_sub_type_sequence | A positive SubTypeSequence is missing, invalid, inferred, or conflicts with the REST-resolved value; or required account, KFF, template, or approval evidence is missing. | Use the REST-resolved sequence when present. Otherwise ask the user for the exact positive HDL value, then render one MERGE action. | Yes |
| Multi-account Correct | Error | query_position_costing | More than one sibling action is in an archive, intermediate state is not accepted, intermediate total exceeds 100%, or prior stage is unverified. | Submit only the next stage after fresh validation and approval. | Yes |
| Zap | Error | query_position_costing_history | Missing immutable complete history, returned offset/limit validation for every history page, explicit terminal paging, exact Generic Costing detail fan-out, sealed parent source identity, parent PositionCode/LDG name/BusinessUnitName matching that evidence, complete child physical identities/layouts, JSON boolean true destructive confirmation, or parent/history evidence. | Resolve and validate every history detail, bind the destructive parent keys to source evidence, then confirm the exact archive with boolean true. | Yes |
| Loader status | Error | | An initiation response is treated as terminal success or status is polled without a user request. | Return pending after initiation. Check status only on explicit user request. | Yes |
| Delete (ED Split) | Error | | The requested operation lacks a documented standard HDL contract. | Stop; do not substitute REST or a generic business object. | No |
| HDL mutation | Error | | Immutable ZIP, Task Hook envelope, or fresh approval is missing. | Do not hand off to the loader. | Yes |
