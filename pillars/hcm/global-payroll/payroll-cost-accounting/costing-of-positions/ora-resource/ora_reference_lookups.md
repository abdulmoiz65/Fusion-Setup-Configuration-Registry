# Position Costing Reference Lookups

For every payrollGenericLOV invocation, use the selected environment origin with /hcmRestApi/resources/latest/payrollGenericLOV; captured /rv/ paths are not execution routes. The service path alone does not determine whether a call is an upstream filter or the Main Search: classify each invocation by PayRestName, finder, parameters and how its returned values are used. DisplayAttributes order defines ResultKeyN and ResultValueN positions for that invocation (first attribute maps to suffix 1, second to suffix 2, and so on). Check that order before interpreting a ResultValueN; when ResultKeyN is returned, verify that it agrees. A fields projection may return ResultValueN without ResultKeyN, so absent unrequested keys are not an error.

For every executable payrollGenericLOV GET, construct one `finder` URL query parameter. Its value contains the resolver's finder clauses followed by `PayRestName=...`, `DisplayAttributes=...`, and `SortBy=...`, separated by commas inside that value. Do not send those three names as separate URL query parameters. Keep `q`, `fields`, `limit`, `offset`, and `onlyData` as separate parameters when specified. Before dispatch, verify that the assembled URL has exactly one `finder`, that each of the three required clauses occurs exactly once with a nonblank value inside it, and that none occurs as a standalone query parameter. If the resolver has no supported SortBy, stop that resolver until its SortBy is established; do not invent one. The corrected Position Main Search composition returned HTTP 200 with one terminal row in the configured tenant; sending the three clauses separately returned HTTP 400.
