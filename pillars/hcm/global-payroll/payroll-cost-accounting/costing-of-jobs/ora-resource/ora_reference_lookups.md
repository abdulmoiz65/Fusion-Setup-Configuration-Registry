## Costing Shared Create Existence Actions Contract

Canonical owners: FSCR - Costing of Jobs (operation flow), FSCR - Costing Shared REST Usage Catalog (CostingSourceId = JobId), and FSCR - Costing Shared REST Actions (wire contract). These two ADF POST actions are specifically governed read-only decisions, not mutation routes. Use core.fusion-api.rest-api-client only after exact Job, jobsLov, LDG with positive flex number, and the normalized date are sealed. Create KFF, Job qualifiers, and account Value Set requests follow both absence decisions. Send `Content-Type: application/vnd.oracle.adf.action+json` and `REST-Framework-Version: 9`; never use a display ID or a caller-supplied source ID.

1. Active existence: POST `/hcmRestApi/resources/latest/genericCosting/action/findExistingRecord` with JSON body `{"effectiveDate":"<YYYY-MM-DD>","legislativeDataGroupId":<sealed LDG ID>,"sourceId":<sealed JobId>,"creatorId":null}`. Require HTTP 200 with one JSON object whose result is exactly JSON boolean `true` or `false`. Boolean true blocks Create; boolean false proves active absence and alone permits the future action. A string, null, missing result, malformed body, or request failure fails closed.
2. Future existence: only after active result JSON boolean `false`, POST `/hcmRestApi/resources/latest/genericCosting/action/futureRecordExists` with JSON body `{"effectiveDate":"<YYYY-MM-DD>","legislativeDataGroupId":<sealed LDG ID>,"positionId":<sealed JobId>}`. The parameter name positionId is fixed by the action contract; the source remains Job. Only HTTP 200 with an exact JSON object `{"result":null}` proves no future record; this shape was observed live and confirmed by the user for this environment. A JSON object with a result string that is a valid YYYY-MM-DD date means a future record exists: retain its date and block Create before KFF. An empty HTTP 200 body, missing result, empty object, string "null", boolean result, another object shape, or request failure fails closed. Do not coerce values.

HDL preparation requires both active absence and future absence. Neither JobCostSearchVO without_costing nor genericCosting collection GET proves Create absence.

| Action | HTTP and Response Body | Decision | Next Allowed Step |
|---|---|---|---|
| findExistingRecord | HTTP 200; JSON result boolean true | Active record exists; block Create. | None; do not call futureRecordExists, KFF describe, Job qualifiers, Value Sets, or HDL. |
| findExistingRecord | HTTP 200; JSON result boolean false | Active record absent. | Call futureRecordExists with the same sealed JobId, LDG ID, and YYYY-MM-DD effective date. |
| findExistingRecord | String true/false, null, missing result, malformed body, or non-200/API failure | Fail closed; do not coerce. | None; do not call futureRecordExists or start KFF. |
| futureRecordExists | HTTP 200; exact JSON object {"result":null} | Future record absent. | Resolve runtime KFF, Job qualifiers, and account Value Sets in order. |
| futureRecordExists | HTTP 200; JSON result is a calendar-valid YYYY-MM-DD date string | Future record exists; retain its date and block Create. | None; do not start KFF, Job qualifiers, Value Sets, or HDL. |
| futureRecordExists | Empty HTTP 200 body, empty object, missing result, string "null", boolean result, other unsupported shape, or non-200/API failure | Fail closed; do not coerce or infer absence. | None; do not start KFF, Job qualifiers, Value Sets, or HDL. |

This task-local projection supplies the validated fields and profiles needed at runtime; the Live Lookups rows above select when to use it.

Construct one logical finder value before URL encoding. After findByWord;, separate finder arguments with commas. Substitute <criteria>, <keys>, <values>, and <attributes> from the chosen profile, positional base values, and exact DisplayAttributes line below; the angle-bracket placeholders are never sent. Pass finder only once. AdditionalViewCriteria, ParameterKeys, ParameterValues, PayRestName, DisplayAttributes, and SortBy are inside finder; q, limit, and onlyData are separate top-level query parameters. Use the governed core.fusion-api.rest-api-client with GET, repeated --query arguments for those top-level parameters, and Accept-Language only as the optional request header. Do not use UI rv: paths or add a fields parameter.

~~~text
endpoint=/hcmRestApi/resources/latest/payrollGenericLOV
finder=findByWord;AdditionalViewCriteria=<criteria>,ParameterKeys=<keys>,ParameterValues=<values>,PayRestName=JobCostSearchVO,DisplayAttributes=<attributes>,SortBy=JobName
DisplayAttributes=JobName||JobCode||SetCode||LdgName||Status||EffectiveStartDate||EffectiveEndDate||CostAllocationId||JobId||LegislativeDataGroupId||JobEffectiveStartDate
base ParameterKeys=pCostingFilter||pSelectedDate
base ParameterValues=<all or discovery-only without_costing>||<requested YYYY-MM-DD>
q=PayRestName = 'JobCostSearchVO'
limit=10000
onlyData=true
~~~

Use `all` by default. `without_costing` may replace only the pCostingFilter value for Job discovery; it never proves Create absence, and the exact Job must still be resolved and passed to both governed existence decisions. Use exactly one of these validated individual profiles. Append each profile's key and value to the base keys and values with ||. For Active-only, keep just the base keys and values and include the empty AdditionalViewCriteria argument.

| Profile | AdditionalViewCriteria | Appended key | Appended value | Required source |
|---|---|---|---|---|
| Job Name/search text | findBySearchString | pSearchStr | Literal Job Name search text, without a manufactured wildcard | User's Job Name/search text |
| Job Code | findByJobCode | pJobCode | Exact JobCode, preserving whitespace | User's exact JobCode |
| Job Set | findBySetIds | pSetIds | Technical SetId | Resolve display Set Name through list_job_search_sets; never use SetName or SetCode as pSetIds |
| Legislative Data Group | findByLegislativeDataGroupIds | pLegislativeDataGroupIds | Technical LegislativeDataGroupId | Resolve and confirm the user-facing LDG through resolve_legislative_data_group |
| Active-only | empty value | none | none | Append AND ResultValue5 = 'Active' to top-level q; Status is in position 5 of this request's DisplayAttributes |

The only validated multi-finder combination in this contract is LDG + Job Set + Job Code + Active. Use one finder and the following exact positional order; resolve both technical IDs first.

~~~text
AdditionalViewCriteria=findByLegislativeDataGroupIds||findBySetIds||findByJobCode
ParameterKeys=pCostingFilter||pSelectedDate||pLegislativeDataGroupIds||pSetIds||pJobCode
ParameterValues=all||<requested YYYY-MM-DD>||<resolved LegislativeDataGroupId>||<resolved SetId>||<exact JobCode>
q=PayRestName = 'JobCostSearchVO' AND ResultValue5 = 'Active'
~~~

Do not infer another combined criterion order from the individual profiles. For an unvalidated combination, run supported individual searches, require terminal paging for each, and cross-check the returned JobId, JobCode, Set context, and LDG context before exact selection. A top-level q-only filter remains outside finder; do not duplicate it as a finder bind. If a user supplies a clear Job Name with a parenthesized Set display name, use the literal Job Name for pSearchStr and resolve the Set display name through the governed Set lookup only when the Set filter or disambiguation needs it. Never insert the display name into pSetIds.

For each response, split that same request's DisplayAttributes on || and map ResultValueN by one-based position; do not use an independent global ResultValue map. This request's list therefore places JobName, JobCode, SetCode, Status, CostAllocationId, and JobId at their respective listed positions. Check Code against the mapped JobId and Meaning against the mapped JobName when present. Require JSON boolean hasMore=false before sealing an exact Job; a missing/string flag or hasMore=true cannot establish uniqueness. Select one exact JobCode when supplied or one exact returned Job Name with governed Set/LDG disambiguation. If legitimate candidates remain, present them for selection. Seal the profile, finder field order, JobId, JobCode, and selection evidence. The search SetCode is context only: resolve_job_hdl_identity must still fetch effective-dated jobsLov and supply the authoritative HDL SetCode. Neither Status, without_costing, nor the search CostAllocationId proves Create absence; the two governed existence decisions are authoritative for Create.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Read-only transport | Use core.fusion-api.rest-api-client for GET lookups and only the two specifically governed read-only ADF POST decision actions in the Create Existence Actions Contract. Arbitrary POST, PATCH, PUT, DELETE, and ADF business-object mutations are prohibited. |
| Job finder | Use only the JobCostSearchVO Request Contract in this file. Build one finder value before percent encoding and pass q, limit, and onlyData as separate top-level query parameters. Use validated individual profiles or the exact validated combined profile; for other combinations, perform supported individual lookups and cross-check returned identities rather than inventing finder order. |
| Derived SourceId | Derive the JobId position from the same request's DisplayAttributes and require its nonblank value from a sealed exact JobCostSearchVO row; then derive lookup SourceId = JobId. Bind it with the sealed exact LDG and jobsLov identity before history paging. Never use an inferred, display, or user-supplied technical SourceId. |
| Job Set for HDL | After resolve_job_source seals JobId and JobCode, GET jobsLov at the requested effective date with q=JobId={job_id}. Require exactly one matching effective row with explicit hasMore=false and render only jobsLov.SetCode. The Job search SetCode, SetName, and SetId are selection or cross-check facts, never HDL SetCode. |
| Create lookup order | Normalize the unambiguous effective date in input preflight before date-dependent GETs. After JobCostSearchVO, jobsLov, and the exact LDG, call check_active_job_costing_record. Only its JSON boolean false permits check_future_job_costing_record with the same sealed JobId, LDG ID, and date. Only exact {"result":null} then permits resolve_runtime_costing_kff, resolve_costing_job_segment_qualifiers, and validate_costing_segment_value in that order, followed by account validation and HDL preparation. On an active true or future date, stop without any Create KFF, qualifier, Value Set, or HDL work. Other operations keep their existing resolver order. |
| Registry readiness | A compiled task status of ready means the authored node graph is structurally complete. It does not prove live Job, jobsLov, LDG, existence, KFF, account, template, or approval evidence. JCP.RESOLVE_REFERENCES may return resolved for Create only after its operation-specific ordered evidence is sealed. |
| Allocation presence | Status, blank LDG display values, CostAllocationId display, and without_costing do not establish Create absence. Use check_active_job_costing_record then check_future_job_costing_record for Create; use query_job_costing for supported current-detail or verification work. |
| Generic Costing Proportion | For Create and effective-dated Update comparison or verification after an explicitly requested successful-status check only, require a returned numeric percent from 0 through 100 and divide it by 100 once before comparing it with the fractional HDL Proportion. Do not apply this normalization to Correct, End Date, Zap, or Delete (ED Split). |
| Pagination | LDG Name discovery requests only offset 0 with limit 11; exact returned Name wins, otherwise eleven rows or hasMore=true requires narrower text, never another page. Set filters may use their documented offset paging. Exact JobCostSearchVO and jobsLov require explicit hasMore=false before uniqueness. PayCostSearchVO history starts at offset 0 and aggregates contiguous pages through explicit hasMore=false. Expanded CostAllocationAccounts fails closed on hasMore=true. Value Set paging remains governed by the KFF Runtime Contract. |
| History-to-children traversal | For Correct, End Date, and Zap, seal the complete PayCostSearchVO page aggregate first, then map each sealed Code and ResultValue1 pair to a Generic Costing item GET with CostAllocationAccounts expansion. The number of GETs is the number of unique history splits, not a fixed example count. Bind every response to its allocation ID, start date, sealed LDG, sealed JobId-derived SourceId, JOB source type, CostAllocationRecordId, and complete child expansion, then seal the complete detail set. |
| Correct MERGE sequence | Use a positive SubTypeSequence from sealed REST state when available. When REST omits it, ask the user for the exact positive HDL value on the MERGE action. Never infer it or introduce another REST operation. A Correct child DELETE instead selects its returned child from sealed detail evidence and has no sequence field. |
| Verification timing | Run verification GET for a query-only request or only after the user explicitly asks for a status or verification check and core.data-loader reports terminal success. Do not poll automatically after handoff. For Zap, compare the complete pre-request logical history and require no remaining parent. |
