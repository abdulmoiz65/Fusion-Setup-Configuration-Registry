# Costing of Payment Sources HDL Design Enforcement

## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Select HDL route | Use only the documented HDL Create, Update, End Date or Zap route. If Correct is requested, stop because no source-backed HDL Correct contract exists; never select a REST fallback. |
| 2 | Preserve template contract | Keep the current validated discriminator headers and identity fields. For CASH, CLRNG and LBLTY writes, require the live Full Flexfield results and render ConcatenatedSegment only, with no populated Segment columns. |
| 3 | Apply operation rule | Use MERGE for Create and effective-dated Update; apply the operation-specific account-order and sequence defaults, and prepend the update-only future-change instruction to every Update member. |
| 4 | Gate the handoff | Require the immutable archive preview and current approval before core.data-loader submission. |

The HDL enforcement node is reached only for a requested Create/Update after
search, when needed, and HDL input validation. Search terminates independently;
it neither expands supported write operations nor requires upload approval.

## Design Rules

| Applies When | Severity | Required Lookup | Blocking Condition | Recommendation | Fix Allowed? |
|---|---|---|---|---|---|
| A search result is used for HDL preparation | Blocker | search_payment_sources | An ambiguous/partial search is treated as a resolved target, a name or generic LOV Code is relabeled as an HDL key, or Without Costing is treated as complete-history absence | Retain source-field provenance, resolve one candidate, and require the current HDL template's identity and operation validation | Yes |
| Any supported operation consumes a source-parent association | Blocker | resolve_organization_payment_method_code | A parent LOV row alone, supplied keys, user confirmation, stale context or a user-filtered ambiguous match is treated as relationship evidence; or parent keys substitute for child keys | Require the automatic parent-binding gate's joined-source and unique-LOV evidence. Do not ask for association confirmation. Retain separate child and parent identities and the remaining source-code requirement; this policy does not enable unsupported operations or new mutation routes | Yes |
| Every Create, Update, End Date or Zap | Blocker | | A mutation route other than HDL through core.data-loader is selected. | Use the approved HDL archive workflow. Read-only lookup GET is not a mutation route. | Yes |
| A supported HDL operation includes CostInfoV3 flags | Blocker | | The requested flag choices are lost or changed between input validation and preview, current-state search values overwrite desired values, or CostableType substitutes for a checkbox | Preserve the normalized requested flag set from ora_input_validation.md through the core.data-loader preview. Unselected is explicit N; omission is not permission to change a flag | Yes |
| Any runtime task operation | Blocker | | Execution requires the original authoring attachments or asks the user to provide reference captures/metadata exports to rediscover a mapping already embedded in the skill | Use the packaged mappings and lookup contracts. Request only business inputs, selection or normal workflow approval. An unsupported contract is an authoring maintenance gap, not a reference-file intake step | No |
| Create/Update includes Liability, Cash Clearing or Cash account rows | Blocker | | Any rendered row deviates from its role mapping or fixed Proportion in Standard Defaults, treats those constants as user-overridable, or distributes a combined proportion across the three roles | Apply ora_defaulting_rules.md per row and preserve the validated account role. These task-wide constants cannot be waived by an operation-level request or approval; reject a conflicting input before archive preparation | No |
| Create/Update Full Flexfield accounts | Blocker | validate_payment_source_full_kff_values | Account preparation uses missing, incomplete, stale or invalid runtime/LOV evidence, or substitutes user confirmation for segment validation | Resolve the exact LDG structure and current runtime descriptor, validate every supplied account component and use validated_full_kff_accounts before archive preview | Yes |
| Correct | Blocker | | This task has no source-backed HDL Correct contract. | Stop as unsupported. Do not invoke or require a REST write, a prior REST failure, a reconciled-failure flag, or fallback approval. | No |
| Create or effective-dated Update HDL member | Blocker | | The source omits the PM identity, changes METADATA order, or invents a GUID, source key, segment, subtype, percentage, or a sequence outside the documented consecutive default. | Preserve the source-backed identity and validated template; use the operation-specific order in Standard Defaults for the new account collection. | Yes |
| Create or effective-dated Update preparation | Blocker | | A successful prerequisite check, render, archive, or validation step is treated as an intermediate pause. | Continue through defaults, DAT render, source/schema validation, immutable ZIP, and Task Hook preview before requesting fresh approval. | Yes |
| Task validation scope, all operations | Blocker | | The workflow adds GL/Cash Management account correspondence, GL combination-existence or costing-hierarchy certification as a task check, pending warning, prerequisite or user confirmation | These checks are outside Costing of Payment Sources. Payment costing uses this source's accounts, not the hierarchy of other costing levels. Do not query banks, ledgers, COA or SLA rules, compare accounts or request evidence/approval for these excluded checks. Preserve Payroll identity, dates, flags, required account presence, fixed role/proportion rules, Full Flexfield validation and the HDL approval gate. Successful setup is not a guarantee of later accounting results | Yes |
| Update | Blocker | resolve_payment_source_update_state | Live baseline, aligned new dates, requested changes, preserved accounts/flags or SET PURGE_FUTURE_CHANGES N is missing | Use the input-validation member contract and prepend SET PURGE_FUTURE_CHANGES N to every included Update DAT before METADATA. Keep earlier values and future periods; no DELETE, physical-child Correct, direct REST write or implicit account removal | Yes |
| Update unchanged inputs | Blocker | resolve_payment_source_update_state | The user must repeat or certify retrievable current accounts, flags or end dates, or a previous payload substitutes for live state | Resolve the baseline automatically and apply only the requested delta. No change in the resulting business values means a verified no-op, not a new split or import | Yes |
| Update preapproval and resume | Blocker | resolve_payment_source_update_state | A preview lacks complete source/schema validation, loader preflight, Task Hook results, unchanged preapproval baseline or an immutable fingerprint | Finish preparation and freshness checks before the single core.data-loader approval. On approval resume the intact preflight and Task Hook approve/verify contract without new GETs, source rereads or archive rebuilds; changed artifacts/context require new preparation and approval | Yes |
| End Date scope | Blocker | resolve_payment_source_end_date_state | The exact supplied start is not the last interval, history/detail is incomplete, the requested inclusive end precedes the start or extends the current end, CostInfo is misaligned/shared, or an unrelated interval changes | Close only the last aligned CostInfo/CostAllocation slice, preserve its start and all earlier history/accounts/flags, and keep the source/method setup. F=E returns verified no change without an archive. Do not reinterpret this as Update, Correct or Zap | No |
| End Date component coverage | Blocker | | Either CostInfoV3 or CostAllocationV3 is omitted from the archive, the objects are split into separate imports/approvals, preserved CostInfo flags are omitted, or accounts are rewritten | Include both MERGE members in one archive and one load request. CostInfo retains live flags and child PaymentMethodId; both retain S and set F plus ReplaceLastEffectiveEndDate=Y. No CostAllocationAccountV3 member. Do not infer atomicity, internal processing order or success from ZIP order; require both component results and final read-back | No |
| End Date special-attribute boundary | Blocker | | Component support is inferred from ordinary template presence/absence or another component, the special attribute is removed/replaced with SET, or a rejected shared-validator result is presented as passed | Confirm each component's date-effectivity capability through the governed loader workflow. Preserve the special attribute and report missing capability evidence or shared-validator rejection before any upload; do not modify core services or bypass validation. Documentation describes conditional support, not blanket approval for all date-effective components | No |
| End Date preparation and resume | Blocker | resolve_payment_source_end_date_state | The combined source lacks validation, baseline freshness, persisted preflight or Task Hook preview; approval belongs to a single-object archive or different dates, bytes or context | Prepare one immutable archive containing both objects and use one core.data-loader approval, without a duplicate pillar approval. Resume intact controls without GETs/rebuilds. After acceptance, only explicit status/verification resumes the same run; never initiate another import from a status request | No |
| Before submission | Blocker | | The immutable archive or exact approval is absent, stale, or scoped to another environment or operation. | Recreate the preview and obtain fresh approval. | Yes |
| Zap scope | Blocker | query_payment_source_costing_history | Only one effective split is deleted, unrelated allocation history is included, or source/payment-method setup is targeted | Zap means delete the selected logical costing allocation's complete history, its aligned CostInfo and physical accounts. Preserve the payment source and parent method. Do not reinterpret End Date, Delete (ED Split), account-only Delete or ambiguous Delete as Zap | No |
| Zap three-component coverage | Blocker | query_payment_source_costing_details | In a new full Zap, any CostInfo, parent allocation or physical account target is omitted or a cascade is assumed | A CostInfo-only recovery may omit only components already proven successful under PM CostInfo-Only Recovery; it is not a cascade. Otherwise require explicit deletion of CostInfoV3, CostAllocationV3 and all resolved CostAllocationAccountV3 targets. Only proven absence of accounts permits omitting their member; no assumed cascade or broad source-level purge | No |
| Zap read completeness | Blocker | query_payment_source_costing_details | History/detail evidence is partial, CostInfo dates differ from its parent, IDs are fabricated, or a CostInfo target also belongs to unselected allocation history | Recovery applies PM CostInfo-Only Recovery reconciliation instead of requiring a deleted parent to exist. Stop before preview; resolve the exact complete target set. Supplied source names and confirmed mappings do not replace live identity-bound history evidence | No |
| Zap loader contract | Blocker | | Metadata presence is treated as proof of DELETE support or ZIP file order as cross-object load order | Require core.data-loader validation of the included component contracts, exact keys and dependency processing. Use the authored CostInfoId plus child PaymentMethodId contract; missing or rejected published metadata blocks. Do not invent SourceId columns, try alternate live DELETEs or fall back to REST | No |
| Zap destructive approval | Blocker | | Approval is missing, stale, or omits a component, historical period or changed archive | Complete the Zap preparation and resume gates below, including persisted preflight, exact-byte Task Hook preview and preapproval freshness, then use the single core.data-loader approval as explicit destructive confirmation for all targets. No duplicate pillar approval; no automatic retries after uncertain or partial submission | No |
| Zap verification | Blocker | query_payment_source_costing_history | Submission acceptance, one object's success or empty current-date search is reported as complete deletion | Require all submitted components to succeed and apply the saved-scope verification contract. Disclose the nested CostInfo read-back boundary rather than claiming independent orphan verification | No |
| Zap load-request preparation | Blocker | | Approval feedback is presented with only a DAT or validation ZIP, without a persisted core.data-loader preflight envelope and the exact artifact's Task Hook preview | For a requested execution, complete core.data-loader preflight using its task-routed upload preparation without approval; then evaluate Task Hook rules and retain its preview. Persist and verify both required control artifacts before asking once for approval. Never fabricate a preflight envelope or copy one from another load | Yes |
| Zap validation-only request | Blocker | | Prepare/validate-only intent is treated as upload authorization or the validation helper's ZIP is represented as submission-ready | Return the core.data-loader validation report and deliverables without upload or an approval prompt. If execution is later requested, complete the load-request preparation gate first; the validation-only result does not replace preflight | No |
| Zap approval resume | Blocker | | An intact approved artifact is rebuilt, rules or live metadata are rerun, source files are reopened, or a second pillar approval is requested | Resume the saved loader gate. Use Task Hook approve-data-load-preview and verify-approved-data-load-archive; persist the returned taskValidationEnvelope unchanged. Invoke core.data-loader with its approved preflight and task envelope for those exact bytes, checking only integrity and bound environment/Run Book context. Missing, modified or mismatched control artifacts block and require fresh preparation and approval | No |
