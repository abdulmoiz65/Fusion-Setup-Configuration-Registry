## Confirmed Location Search Finder

The brackets below mark optional aligned additions; brackets are notation and are not transmitted.

```text
findByWord;AdditionalViewCriteria=findBySearchString[||findByLegislativeDataGroupIds][||findBySetIds][||findByLocationCode],ParameterKeys=pCostingFilter||pSelectedDate||pSearchStr[||pLegislativeDataGroupIds][||pSetIds][||pLocationCode],ParameterValues=all||<YYYY-MM-DD>||<location-search>[||<ldg-ids>][||<set-ids>][||<location-code>],PayRestName=LocationCostSearchVO,DisplayAttributes=LocationName||LocationCode||LdgName||Status||SetCode||EffectiveStartDate||EffectiveEndDate||CostAllocationId||LocationId||LegislativeDataGroupId||LocStartDate,SortBy=LocationName
```

The finder has exactly one semicolon, immediately after findByWord. Every later top-level clause is comma-separated. Each inner list uses two vertical-bar characters. Optional criteria, keys, and values are added in the same order and cardinality. SortBy=LocationName is inside the finder and is never an outer query argument.

The outer q is PayRestName = 'LocationCostSearchVO'. Append AND ResultValue4 = 'Active' only when an Active filter is requested. The fields argument is Code,ResultValue1,ResultValue10,ResultValue11,ResultValue2,ResultValue3,ResultValue4,ResultValue5,ResultValue6,ResultValue7,ResultValue8,ResultValue9. Use Accept: */*, the selected Accept-Language, Content-Type: application/vnd.oracle.adf.resourceitem+json, and REST-Framework-Version: 9.

Only the captured modes are supported. A Location-name search puts that name in pSearchStr and may add the confirmed LDG, but it does not combine Set, Location Code, or status. A list or filter-chip search uses the system-supplied percent wildcard in pSearchStr and may add LDG IDs, Set IDs, one Location Code, or the Active q predicate. User-supplied wildcard or arbitrary typed-search syntax is not inferred.

## Confirmed PayCostSearch History Finder

```text
findByWord;AdditionalViewCriteria=findByLegislativeDataGroupIdSourceIdSourceType,ParameterKeys=pSourceId||pSourceType||pLegislativeDataGroupId,ParameterValues=<LocationId>||LOC||<LDG_ID>,PayRestName=PayCostSearchVO,DisplayAttributes=EffectiveStartDate||EffectiveEndDate||HistoryComments||LastUpdatedBy||LastUpdateDate,SortBy=EffectiveStartDate DESC
```

This finder is one logical query value. SortBy remains inside it. The outer query has only finder, onlyData=true, limit, and offset; it has no q or fields argument.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Request representation | Give core.fusion-api.rest-api-client a bare relative endpoint and separate unencoded logical query key-value arguments. The client performs the only percent-encoding pass. Do not split a generated URL back into query arguments and do not encode an already encoded value. |
| Request headers | Send the selected Accept-Language, Content-Type application/vnd.oracle.adf.resourceitem+json, and REST-Framework-Version 9 on HCM resource GETs; the Location search also sends Accept */*. The runtime KFF describe GET sends the selected Accept-Language and Accept application/json. Authorization remains the governed client's responsibility. |
| Location finder safety | Keep SortBy inside the single finder. Reject an unescaped user value containing a finder delimiter for which the supplied source has no escaping contract. |
| Collection envelope | For LOV, search, and history endpoints, require a JSON object with an items array. Validate count and paging fields when requested before applying cardinality or match rules. |
| Singular Item Normalization | If a response has items, require it to be an array and unwrap exactly one item; zero becomes not_found and more than one becomes ambiguous. If items is absent, treat the top-level JSON object as the item. Validate required child fields only after this normalization. |
| HTTP boundary | Preserve the actual HTTP status before parsing and emit any normalization failure as response_contract_mismatch without changing that status. Error classification belongs to ora_error_handling.md. |
| Pagination | Follow only documented paging. Never infer completeness from one page when hasMore is true or missing where required. |
| Mutation boundary | Every lookup uses GET through the governed client. No lookup dispatches POST, PATCH, PUT, DELETE, Data Loader, or browser mutation. |
