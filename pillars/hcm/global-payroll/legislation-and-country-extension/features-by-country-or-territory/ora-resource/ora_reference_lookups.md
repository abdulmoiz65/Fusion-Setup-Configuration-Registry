## Finder Construction and Response Mapping

| Situation | What Happens |
|---|---|
| Endpoint and environment | Use the active workflow's selected environment with /hcmRestApi/resources/latest/. Captured hosts, rv routes, sessions, credentials, and revisions are not reusable runtime input. GET has no request body. |
| Outer query parameters | Place finder, q, fields, limit, offset, and onlyData outside finder when needed and supported. Main Search uses expand=all. |
| Finder arguments | Keep PayRestName, AdditionalViewCriteria, ParameterKeys, ParameterValues, DisplayAttributes, and SortBy inside finder when the specific lookup declares them. A semicolon separates findByWord from its arguments; commas separate arguments; double-pipe separates list entries. Omit unused arguments instead of sending None. |
| Query encoding | Build finder first and encode it once as a query-parameter value. Table URLs spell double-pipe as %7C%7C to preserve columns; do not double-encode that representation. URL encoding differs from literal escaping within expressions. Treat user text only as a value, never an attribute or grammar fragment. Unsupported literal escaping remains a T14 test gap; do not guess a quoting rule. |
| Full generic-LOV response | DisplayAttributes order defines positions. ResultKeyN identifies the attribute; ResultValueN contains its value. Check the mapping before interpreting values; unexpected mappings are unknown evidence. |
| Legislation response | DisplayAttributes order: TerritoryCode, TerritoryShortName. Preserve both canonical fields; partial search text is not the canonical name. |
| Selected Extension response | DisplayAttributes order: LookupCode, Meaning. Keep internal codes separate from current-environment labels. |
| Address Style response | DisplayAttributes order: StyleCode, StyleName. Retain the target or US context associated with the result. |
| Address Validation projected response | DisplayAttributes order: LookupCode, Meaning, Description. The HAR verifies fields=ResultValue1,Meaning and returns N/No or Y/Yes through those fields. Do not require ResultValue2 or ResultKeyN in this projection. A changed projection/mapping requires contract verification. |
| Reverse-label lookup | Match the documented underlying code in the authoritative response. Do not invent universal q=Code syntax. For null Selected Extension, use PER to obtain Meaning only and retain original null. |
| Language and presentation | Use labels from the current environment. Conversation language does not prove backend locale. Names and localized meanings are primary; meaningful business codes may accompany them. T12 remains unverified. Preserve unresolved internal values and disclose missing labels instead of inventing authoritative translations. |

## Main Search Query Rules

| Situation | What Happens |
|---|---|
| Blind Search | Omit q and retrieve the required complete collection with expand=all. |
| One resolved value | Confirmed pattern: (TerritoryCode='AL'). |
| Multiple resolved values for one attribute | Confirmed pattern: (TerritoryCode in ('AL','US','MX')). |
| Different criteria | Parenthesize each criterion and combine with and: (TerritoryCode='AL') and (PayrollLicense='PAY'). |
| Multiple values and another criterion | Confirmed pattern: (TerritoryCode in ('AL','US','MX')) and (PayrollLicense='PAY'). |
| Filtered Search | Use the five mapped attributes and resolved internal values. Apply supported criteria server-side; do not substitute full-collection local filtering. Lookup display-match predicates are not Main Search expressions. |
| Named-target existence/verification | Query resolved target codes, preferably as one logical query. Do not include desired PayrollLicense, AddressStyleCode, or AddressValidation; different current values do not make a target absent. |
| Existing identity | Retain ApplicationId and LegislationCode from the exact current record as composite identity. TerritoryCode is the lookup/existence value. Do not assume all existing ApplicationId values equal the Create value 801 or choose arbitrarily among identities. |
| Query size limits | Oversized sets may need supported batches; maximum URL length and batch-size contracts are not established. Confirm those operational limits before implementing batching; do not invent a threshold. |

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Phase-specific execution | The runbook supplies read phase/scope. FBCT.RESOLVE_REFERENCES executes only that phase's applicable resolver subset. It does not trigger Search, baseline, final pre-approval validation, and post-verification together. A lookup node does not authorize a later mutation. |
| Candidate resolution | Finish the lookup before classifying each supplied value. Preserve name/code context and canonical results. Report zero and multiple matches separately; do not choose, discard, or invent targets. |
| Request-scoped reuse | Reuse an exact resolved value only within the same request and applicable environment, territory, and phase. An old baseline does not replace a required current reread during final read-only validation before approval. |
| Complete-read policy | Main Search's observed default is limit=25 and offset=0. The source permits limit=500, which never proves completeness. Follow response pagination until hasMore=false for the required logical result set. Apply the same rule to filtered results, LOV candidates, existence, and verification. |
| Page progression | Preserve logical query, finder, projection, and environment while progressing offset using the response page extent. Require valid pagination and forward progress. Missing pagination, repeated pages, malformed items, or interruption yield unknown results. |
| Failed reads | Authentication, authorization, transport, malformed response, missing items, incomplete pages, or missing required fields cannot establish invalid input, absence, deletion, or defaults. Return unresolved evidence to error handling. |
| Available Legislations for Create | Read complete LegislationVO and configured Main Search collections, then calculate the difference by resolved TerritoryCode. The two live authorities supply the data; this is not a new local lookup. |
| Finite target set | Read only resolved target codes, consolidating the logical query when possible. One logical query may require several HTTP requests for pagination. Complete it before classifying missing or ambiguous identities. |
| Final pre-approval read-only validation | Use find_features_by_criteria for exact planned targets/current business values before core.data-loader approval. Return fresh evidence to the owning preservation/concurrency gate. After approval, core.data-loader permits integrity checks only: do not repeat live reads merely to submit. ora_error_handling.md owns the precise approval boundary and changed-plan return path. Do not invent locking headers or Data Loader version columns; D07 remains open. |
| Post-operation phase | Use find_features_by_criteria for the complete targeted result set by identity. Return actual identities and all required business fields to the owning result gate. Missing, duplicate, unexpected, or incomplete records are distinct discrepancies. |
| Expanded child/audit data | expand=all may return InstalledLegislationDDF and audit/version fields. Keep them separate from the ten business fields; use child data only if required. No child-write, additional child-lookup, seeded-label, or DDF display contract is inferred; D10 remains open. |
| Deferred decisions | D01 null/PER behavior and D02 complete cross-territory style discovery are unresolved lookup contracts. D06 visibility/exact-identity policy and D09 broad-filter write selection belong to policy gates. Successful historical reads do not resolve them. |
