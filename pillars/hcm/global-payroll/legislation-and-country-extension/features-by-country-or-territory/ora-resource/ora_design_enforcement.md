## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Identify phase | Use the runbook's preparation, final pre-approval validation, or separate verification phase. This node never starts a loader, polls a process, or grants mutation authority. |
| 2 | Separate intent and evidence | Keep target selection, resolved identity, current values, requested changes, desired values, and authorization distinct. Supplied text does not establish local authority. |
| 3 | Consolidate targets | Resolve aliases and existing records; preserve per-target intent; resolve invalid, ambiguous, conflicting, or excluded groups before write planning. |
| 4 | Classify actions | Apply operation-specific policy, resolve switches, omit proven no-op Updates, and assign at most one write per target. |
| 5 | Evaluate desired values | Consume branch-specific values and confirmation results from ora_defaulting_rules.md; enforce validity, preservation, editable scope, Delete eligibility, and applicable country policy. |
| 6 | Retain unresolved gates | Apply Open Decisions and canonical TBD fields without inventing authorities, lookups, labels, or policy. |
| 7 | Validate final baseline | Re-read when intervening changes are possible at the last read-only validation before core/data-loader approval. Rebuild changed plans. After approval follow the loader's integrity-only gate; known material change requires fresh validation and approval. |
| 8 | Return phase result | Return to FBCT.CHECK_EXECUTION_BOUNDARY. Verification uses separately routed post-load evidence. Passing preparation proves neither submission nor load success. |
