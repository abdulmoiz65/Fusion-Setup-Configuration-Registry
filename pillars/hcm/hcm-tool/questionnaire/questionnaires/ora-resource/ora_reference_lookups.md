# Reference Lookups

Local lookup authority begins with a current approved target setup export or exact target readback supplied in task context. When that evidence is absent or stale, obtain it through the matching declared read-only `resolve_live_questionnaire_*` lookup using `core.fusion-api.rest-api-client`. The supplied FSM package is baseline evidence only. Do not invent product-reference endpoints beyond the declared live lookups.

## Live REST Transport Contract

Send header `REST-Framework-Version: 9` on every declared live request to `/hcmRestApi` or `/fscmRestApi`, including each pagination request and every returned `@context.links`, item, child, detail, or template link followed by a resolver. With the shared client, pass `--header "REST-Framework-Version=9"`. Do not apply this header to OAuth requests or local/export evidence, and do not silently omit or downgrade the value. A target rejection of version 9 is an environment-compatibility blocker rather than permission to retry without the header.

### Questionnaire REST state and mutability resolution

The public `questionnaires` REST resource documents `LatestVersionFlag` and the projected lifecycle, privacy, owner, version, and identity fields above. It does not document `UpdateAllowed` or `UpdateAllowedFlag`; do not request either name from this REST resource or treat an HDL attribute with a similar name as REST evidence. Template linkage remains separate declared-resolver and current HDL evidence rather than part of this identity/state projection.

For an update, keep links in the collection response by using `onlyData=false`. If the one exact collection item includes a non-null `LatestVersionFlag`, bind that value to the readback. If it omits the field or returns null, retain the item's returned links and GET only a returned `self` link, or a returned `canonical` link when no self link is available, using `REST-Framework-Version: 9` and the same explicit field projection. Do not construct an item URL from `QuestionnaireId`, follow an action or unrelated link, or substitute `Status`, `InUse`, or successful cardinality for the missing latest-version value.

If the item-link response still omits `LatestVersionFlag`, returns it as null, or cannot be reached through a returned self/canonical link, classify update-state evidence as MISSING and block the update. A true `LatestVersionFlag` is necessary but not sufficient: current target Data Loader metadata must also register root `MERGE`, and the requested root and child changes must independently pass the existing per-field/per-component mutability and lifecycle/usage rules.

### Questionnaire Data Loader catalog filter

For `resolve_questionnaire_hdl_contract`, set `questionnaire_business_object_filter` to the following single `q` value and let `core.fusion-api.rest-api-client` encode it. Follow [HDL Metadata Discovery](../../references/hdl-metadata-discovery.md) for the separate unchanged shared-loader gate:

```text
(BusObjTopDiscriminator LIKE '%Questionnaire%' ESCAPE '\' OR TemplateFileName LIKE '%Questionnaire%' ESCAPE '\' OR UIName LIKE '%Questionnaire%' ESCAPE '\')
```

The server-side filter narrows discovery; it does not authorize a fuzzy registration match. Do not add a `ProductAreaCode` predicate to pillar-authored discovery requests: a valid cross-product registration can have that value absent, and product area is not part of the Questionnaire business-object identity. Paginate the filtered result to completion, retain sanitized candidate identities, then apply the exact discriminator/template rule from the resolver. Do not retry with an unfiltered first-page scan and do not infer `Questionnaire` from a `QuestionnaireTemplate` candidate returned by the broad `LIKE` predicate.

The shared helper owns its internal filter and is not rejected solely because that filter narrows product area. Require its actual validation to resolve the same exact registration and complete current contract. If pillar discovery succeeds but the shared lookup completes with no exact registration, report `shared_loader_registration_mismatch`, not an unregistered business object, and stop. Preserve request failures as auth/authz, transport/environment, or Fusion API errors rather than registration mismatches. Never request ProductAreaCode from the user, rewrite the shared helper, or bypass core validation.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| A product-reference endpoint is not documented | Use only a current approved target export or exact readback supplied in task context; otherwise classify the dependency as MISSING rather than inventing a request |
| Current project subscriber evidence is absent | Run only resolve_live_questionnaire_subscriber through core.fusion-api.rest-api-client; do not use its result as authority for category, template, question, or create-state checks |
| Current project reference evidence is absent | Run only the matching declared resolve_live_questionnaire_* fallback through core.fusion-api.rest-api-client; retain each resolver's stated partial or composite limitation and do not use it outside its documented scope |
| A required read-only dependency has no current project evidence | Invoke its declared live resolver during preflight before classifying it as MISSING or ambiguous; persist only sanitized match, status, and timestamp evidence |
| A declared suggestion-capable value has zero exact matches | Retrieve and fingerprint only its declared bounded candidate catalog, apply subscriber/parent/capability restrictions, rank at most three exact returned values, and wait for explicit approval. Multiple exact matches remain ambiguous. |
| A reference-value suggestion is approved | Bind approval under the parent suggestion contract and rerun the original exact resolver plus every compatibility check before a new immutable DAT preview. |

| Live Data Loader metadata differs from supplied DAT or matrix evidence | Use the current live contract for transport and disclose the difference |
| A template is absent | Block only when it was supplied or is mandatory in the current live HDL/subscriber contract; do not turn a route-specific rule into a universal product rule |
| A placement response override is blank | Inherit the reusable question response type and do not resolve or emit an override value |
| A root key is checked for duplicates | Apply operation-aware cardinality; zero target matches is expected for create, not a missing reference |
| A Questionnaire update is prepared | Require one authoritative full-questionnaire and hierarchy readback, bind latest/update/in-use/response state and exact per-field/per-component mutability, classify every submitted child as existing or new, preserve omitted children and template linkage, and reject immutable-key changes or destructive interpretation. |
| A questionnaire is in use or has responses | Permit only exact fields and child operations proven editable by current release-specific evidence. Treat the declared lifecycle REST result as partial; block hierarchy, scoring, template-linkage, status, or lifecycle mutation without complete impact proof. |
| A direct Question is requested | Run resolve_questionnaire_direct_question_contract before rendering. Do not reinterpret a direct definition as a reusable-question reference or emit Questionnaire.dat until the live contract, category, response type, template capability, conditional Answer contract, and approved executable procedure are complete. |
| A surrogate or internal subscriber ID appears in evidence | Retain it only as source evidence; do not use it as the portable key or as a cross-pod LayoutOption rule |
