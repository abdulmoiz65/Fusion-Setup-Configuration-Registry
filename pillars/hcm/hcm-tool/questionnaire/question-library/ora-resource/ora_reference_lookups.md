# Reference Lookups

Local lookup authority begins with a current approved target setup export or exact target readback supplied in the task context. When that evidence is absent or stale, obtain it through the matching declared read-only live lookup using `core.fusion-api.rest-api-client`. FSM evidence from another pod or release is a baseline only. Do not use product-reference endpoints beyond the declared live lookups.

## Live REST Transport Contract

Send header `REST-Framework-Version: 9` on every declared live request to `/hcmRestApi` or `/fscmRestApi`, including each pagination request and every returned `@context.links`, item, child, detail, or template link followed by a resolver. With the shared client, pass `--header "REST-Framework-Version=9"`. Do not apply this header to OAuth requests or local/export evidence, and do not silently omit or downgrade the value. A target rejection of version 9 is an environment-compatibility blocker rather than permission to retry without the header.

## Recruiting Organization Canonicalization

`recruitingOrganizationsLOV` is a discovery and selection view. Its `Name` may be a hierarchy display value such as `ZBEN_Common_Business Unit, ZBEN United Benefits Corporation`; it is not an HDL-safe `QuestionContext.OrganizationName` value. Its server-side `q=Name=...` result is not proof of exact matching and must not be used as the final resolver.

For every Recruiting organization context, complete this sequence before rendering a DAT:

1. Read and paginate `recruitingOrganizationsLOV` with its discovery projection. Apply exact client-side matching and present ambiguous candidates for approval; retain its `OrganizationId` only in memory.
2. Read `organizationsLOV` by that transient ID. Require exactly one active row and a classification compatible with the selected Recruiting candidate.
3. Serialize the returned canonical `organizationsLOV.Name`, not the Recruiting hierarchy display label. Do not split, trim, or otherwise derive values from a comma-delimited display label.
4. Bind the rendered QuestionContext key to one passed `validation_evidence.recruiting_organization_contexts` record with `resolver: resolve_live_recruiting_question_context`, `canonical_source: organizationsLOV`, and an approved evidence ID. Never persist `OrganizationId` in the DAT, build specification, preview, or receipt.

## Status-Only Question Inactivation Route

This exception applies **only** to the Question Library task and the explicit `inactivate` intent. It does not alter create, change, new-version, remove, answer/context changes, template operations, or questionnaire operations.

The dependency result may be classified as `partial_no_visible_usage` and move to `approval_required` only when every condition is true:

1. `resolve_live_question_existing_identity` proves exactly one same-subscriber Question/version that is active, latest, and `UpdateAllowedFlag=true` using the returned-item fallback when necessary.
2. The current live `Question` contract registers `MERGE`, the current template supports the required root attributes, and the requested target status is an exact target-valid inactive value.
3. The changed-field set is exactly `["Status"]`; every other emitted root value is an exact current readback, and no `Answer`, `QuestionContext`, translation, attachment, or other child row is emitted.
4. Every declared visible downstream endpoint above completes successfully for the exact resolved question/version and returns zero matching placements. A request failure, incomplete pagination, a nonzero result, or an identity mismatch is a blocker.
5. No current target evidence returned by the selected identity or usage lookups reports seeded, locked, in-use, or otherwise non-editable lifecycle state.

The partial result is not evidence that no hidden dependency exists. Before building a DAT, show the exact portable key, lookup scope and zero matching usages, the partial-evidence limitation, status transition, template hash, preserved values, and changed-field set. Require an explicit impact-bound business approval for that material scope. Rerun all five checks after approval, then use compare_question_inactivation_review under [the comparison contract](../references/inactivation-review.md). Fresh timestamps, evidence IDs, response ordering, loader-template reference counts, and unrelated template/placement totals do not by themselves invalidate business approval. Changed catalog diagnostics require one complete confirmation scan; retain approval only when the same question-specific scope and zero matching usage are confirmed. A failed or incomplete scan blocks; a material scope change requires renewed review. Do not request repeated approval for diagnostic-only drift. Then generate only the immutable status-only candidate. A separate unchanged-hash Data Loader preview and approval remains mandatory before upload. After a load, require exact readback showing the approved inactive status.

### Complete visible-usage scan

For resolve_live_question_downstream_usage, preserve the same target, SubscriberCode, exact question identity/version, REST-Framework-Version, and query/projection semantics throughout each scan and recheck. Preserve a verified non-secret principal fingerprint when the authentication layer exposes one; otherwise record principal evidence as unavailable. Do not require or claim complete Fusion data-access-scope proof.

- Follow every top-level page from both declared endpoints. Traverse all sections and question placements for every returned functional template, including paginated expanded child collections through their returned links. Top-level hasMore=false alone does not prove child completion. If child coverage or an identity needed for matching is absent, report incomplete coverage rather than counting it as zero.
- Apply exact client-side identity checks using the returned question identity and version; the template collection's SubscriberCode filter alone does not select usages of this question. Reconcile IDs transiently with the resolved portable key. Deduplicate templates and placements by their complete identities and sort before hashing. Do not count page repeats twice or silently skip malformed or cross-subscriber results.
- Store each endpoint's success, top-level and child completion, scope verification, stable request-scope fingerprint and matching portable placement keys. Keep scanned template/placement totals and the sorted template-set fingerprint as diagnostics. Retain sanitized per-page coverage evidence so a reported zero is auditable.
- A stable request-scope fingerprint covers target, endpoint/query/filter/projection semantics and the portable parent key; omit offset, page size, request time, token, returned links and response body. `scope_verified` means that exact request scope was checked; it does not mean the caller has complete Fusion data visibility. When a stable verified non-secret principal identifier is available, hash it separately. Otherwise retain explicit unavailable principal evidence. Never hash or persist a token, credential, or assumed data-access scope.
- Repeated complete scans may legitimately have different unrelated totals. Confirm the exact question-specific result once under the same scope. If scope, page/child coverage, or question-specific evidence cannot be reconciled, stop with a collection diagnostic, not another approval prompt.

Technical Data Loader/UCM Question.dat schema references are HDL contract evidence only. They are not functional questionnaire templates or downstream placements. Bind the selected template content and relevant operation/component contract hashes; report other loader reference counts separately.

### Question mutability projection and returned-item fallback

For `resolve_live_question_existing_identity`, keep `UpdateAllowedFlag` in the `fields` projection; it is a returned state attribute, not a query predicate. Do not place `UpdateAllowedFlag` in `q`, and do not treat omission from Fusion's compact collection representation as `false` or as evidence that the question is immutable.

For an update, first require one exact collection item and verify its portable identity. When that item omits `UpdateAllowedFlag`, read its returned `self` link, or its returned `canonical` link when no `self` link is present, with the same explicit fields projection and `REST-Framework-Version: 9`. Do not construct an item URL from `QuestionId`, follow a link from another item, or use an LOV row as mutability evidence. The item response must repeat the same SubscriberCode, QuestionCode, and VersionNumber. A missing returned item link, rejected projection, identity mismatch, or item response that still omits `UpdateAllowedFlag` is a target REST-contract mismatch and blocks update preview. Never infer `UpdateAllowedFlag=true` from active status, latest-version state, a previous successful update, Data Loader metadata, or a schema default.

### Question Data Loader catalog filter

For `resolve_question_hdl_contract`, set `question_business_object_filter` to the following single `q` value and let `core.fusion-api.rest-api-client` encode it. Follow [HDL Metadata Discovery](../../references/hdl-metadata-discovery.md) for the separate unchanged shared-loader gate:

```text
(BusObjTopDiscriminator LIKE '%Question%' ESCAPE '\' OR TemplateFileName LIKE '%Question%' ESCAPE '\' OR UIName LIKE '%Question%' ESCAPE '\')
```

The server-side filter narrows discovery; it does not authorize a fuzzy registration match. Do not add a `ProductAreaCode` predicate to pillar-authored discovery requests: a valid cross-product registration can have that value absent, and product area is not part of the Question business-object identity. Paginate the filtered result to completion, retain sanitized candidate identities, then apply the exact discriminator/template rule from the resolver. Do not retry with an unfiltered first-page scan and do not infer `Question` from a `Questionnaire` candidate returned by the broad `LIKE` predicate.

The shared helper owns its internal filter and is not rejected solely because that filter narrows product area. Require its actual validation to resolve the same exact registration and complete current contract. If pillar discovery succeeds but the shared lookup completes with no exact registration, report `shared_loader_registration_mismatch`, not an unregistered business object, and stop. Preserve request failures as auth/authz, transport/environment, or Fusion API errors rather than registration mismatches. Never request ProductAreaCode from the user, rewrite the shared helper, or bypass core validation.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| A target reference endpoint is not documented | Use only a current approved target export or exact readback supplied in task context; otherwise mark the dependency MISSING rather than inventing a request |
| Current project subscriber evidence is absent | Run only resolve_live_questionnaire_subscriber through core.fusion-api.rest-api-client; do not use its result as authority for categories, response types, or create-state checks |
| Current project reference evidence is absent | Run only the matching declared resolve_live_question_* fallback through core.fusion-api.rest-api-client; retain each resolver's stated partial or composite limitation and do not use it outside its documented scope |
| A required read-only dependency has no current project evidence | Invoke its declared live resolver during preflight before classifying it as MISSING or ambiguous; persist only sanitized match, status, and timestamp evidence |
| A product Question or Question LOV REST call contains a compound `q` filter | Put the fully prepared `q` expression in the endpoint URL and encode every predicate separator as `%20and%20`; do not pass the expression as a separate query argument that could re-encode its spaces as `+`. This rule excludes Data Loader metadata discovery: resolve_question_hdl_contract passes its declared filter as one `--query` value under HDL Metadata Discovery. |
| An exact Question update lookup omits UpdateAllowedFlag | Keep the mutability attribute out of `q`; follow only the exact collection item's returned `self` or `canonical` link and repeat the explicit fields projection. If the link or flag remains unavailable, classify a target REST-contract mismatch and block rather than treating omission as false or defaulting it to true. |
| A target AnswerCode uniqueness lookup runs | Use only the exact submitted AnswerCode in the declared questionAnswersLOV equality filter, do not add a QuestionId, question version, subscriber, or parent predicate, and do not treat a scoped child-answer lookup as target-wide evidence |
| QuestionType or ResponseTypeName does not match exactly | Resolve the complete current target compatible-pair catalog, then invoke propose_question_response_type_pair. For ranking only, trim outer whitespace, collapse repeated whitespace, compare case-insensitively, and treat spaces, hyphens, and underscores as token separators. Use only returned codes and names plus explicit response-design wording; never rewrite a target value or treat a probable match as valid input. |
| Another declared suggestion-capable value has zero exact matches | Retrieve and fingerprint only its declared bounded candidate catalog, apply all parent/subscriber/capability restrictions, rank at most three exact returned values, and wait for explicit approval. Multiple exact matches remain ambiguous and do not enter suggestion ranking. |
| A reference-value suggestion is approved | Bind the approval as required by the parent suggestion contract, then rerun the original exact resolver and compatibility checks immediately before a new immutable DAT preview. |
| Type-pair suggestion evidence is prepared | Fingerprint the complete source request and the exact ordered candidate set with the same immutable fingerprint procedure used for approval previews. If either fingerprint cannot be produced, do not request or accept approval. |
| A type-pair suggestion is presented | Show the original values, at most three exact target pairs, the supporting reason for their order, and whether one pair is uniquely recommended. Do not modify QuestionType or ResponseTypeName, generate DAT, or claim readiness until the user explicitly approves one exact pair. |
| A type-pair suggestion is approved | Bind approval to the exact pair, target environment, question business key, source-request fingerprint, candidate-set fingerprint, and catalog timestamp. Rerun resolve_live_question_types and resolve_live_question_response_type for the approved exact pair immediately before a new immutable DAT preview. Any changed input, target, candidate set, unpermitted type, or failed exact pair recheck invalidates approval. |
| The live Data Loader metadata differs from a supplied DAT or field matrix | Use the live target contract for transport and record the sample difference as a warning |
| FSM evidence is from another target or is stale | Use it only to understand source content; it cannot prove target existence, allowed values, or current HDL operations |
| A surrogate ID is present in any evidence | Retain it only where the source evidence requires it; never map it into the portable HDL artifact |
| A root key is checked for duplicates | Apply the operation-aware cardinality rule; do not treat the expected zero match for create as a missing reference |
| An AnswerCode is checked for duplicates | Run validate_submitted_answer_code_uniqueness across all Answer rows, then resolve_live_question_answer_code_uniqueness for every submitted code. Create and new update children require zero target matches. An affected existing update child requires one exact same-parent match; any other nonzero match blocks preview and requires a new question-specific AnswerCode or corrected update intent. |
| A Question update is prepared | Bind the exact current root and affected-child readbacks, UpdateAllowedFlag, changed-field set, preserved emitted values, and live MERGE metadata into the request evidence. Reject a portable-key change, incomplete readback, implicit child deletion, or a create collision relabeled as update. |
| An AnswerCode correction is proposed | Present the invalidity reason and exact old-to-proposed mapping from propose_question_specific_answer_code. Do not alter Question.dat until the user approves the exact mapping; after approval, rerun both uniqueness checks and create a new immutable preview. |
