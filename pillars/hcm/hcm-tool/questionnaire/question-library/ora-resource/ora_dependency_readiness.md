# Dependency Readiness

## Required Dependency Order

| Sequence | Dependency | What Must Happen |
|---|---|---|
| 1 | Live Question HDL contract | Resolve the exact current target registration, template, hierarchy, user keys, attributes, and operations before interpreting or rendering DAT content. |
| 2 | Subscriber and delivered values | Resolve one exact seeded subscriber and every required question-type, response-type, status, privacy, and subscriber-specific value. |
| 3 | Category, owner, conditional, scoring, and context references | Resolve only the references applicable to the approved design using current target evidence. |
| 4 | AnswerCode identity and uniqueness | Confirm every submitted AnswerCode is unique across the DAT. Require target absence for create and new update children; allow one exact same-parent match only for an explicitly affected existing Answer in an update. |
| 5 | Existing identity and version state | Apply create, change, new-version, inactivate, or remove cardinality and confirm current latest, seeded, locked, and in-use state. |
| 6 | Downstream usage | Review dependent templates and questionnaires before changing lifecycle-sensitive question or answer behavior. A zero-result visible-usage outcome may use the status-only Question inactivation approval route only under its exact conditions. |

## Dependency Classification

| Result Category | When Used | Can Run Lookup/Create? |
|---|---|---|
| Satisfied | Every applicable dependency has the required exact match and the live HDL contract is current | Yes, artifact preparation only |
| Blocked | Metadata is unavailable, a required reference or target state is missing or ambiguous, or evidence is stale | No |
| Approval required | A declared reference candidate or compatible pair has been proposed but no exact value has been explicitly approved and revalidated | Read-only candidate and exact-reference lookups only; no DAT preparation or upload |
| Approval required | Only for the documented `partial_no_visible_usage` status-only Question inactivation route after all declared visible usage lookups return zero matches | Show the impact-bound approval preview; after approval, rerun all route checks before local DAT preparation. A separate Data Loader approval remains required before upload. |
| Alignment required | A required lookup value or creation route is not owned by this task | No; exclude it and record the owning task or implementation gap |

Only the status-only Question inactivation route uses compare_question_inactivation_review. An approval_retained result follows the existing ready transition with the partial-coverage warning preserved. An approval_required result follows approval_required. A rescan_required result repeats the declared read-only lookup once; if it cannot be reconciled, follow blocked. Other flows retain their existing gates.

## FSM Evidence Order

When an FSM export is used as evidence, validate the Question parent before answer, context, and translation children, using the exact metadata hierarchy and node sequence. Lookup prerequisites must already be cleared. This evidence order does not select FSM as the mutation route and does not define cross-task execution order.
