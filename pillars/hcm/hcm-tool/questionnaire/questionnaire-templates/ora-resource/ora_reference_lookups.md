# Reference Lookups

Local lookup authority begins with a current approved target setup export or exact target readback supplied in task context. When that evidence is absent or stale, obtain it through the matching declared read-only `resolve_live_template_*` lookup using `core.fusion-api.rest-api-client`. The supplied FSM package is baseline evidence only. Do not invent reference-data endpoints beyond the declared live lookups.

## Live REST Transport Contract

Send header `REST-Framework-Version: 9` on every declared live request to `/hcmRestApi` or `/fscmRestApi`, including each pagination request and every returned `@context.links`, item, child, detail, or template link followed by a resolver. With the shared client, pass `--header "REST-Framework-Version=9"`. Do not apply this header to OAuth requests or local/export evidence, and do not silently omit or downgrade the value. A target rejection of version 9 is an environment-compatibility blocker rather than permission to retry without the header.

### Questionnaire template state projection and returned-item fallback

For `resolve_live_template_existing_identity`, use only the documented `questionnaireTemplates` fields in its explicit projection. The resource exposes `InUseFlag` and the documented `AllowFormatChangeFlag`, `AllowInstrChangeFlag`, and `AllowSectionChangeFlag` questionnaire capability controls; it does not expose `UpdateAllowed`, `UpdateAllowedFlag`, or `LatestVersion`. The capability controls describe changes allowed when a questionnaire is created from the template and are not blanket permission to update the template itself. Do not add an invented update indicator to `fields` or `q`, and do not infer update permission from status, in-use state, privacy/editor state, or a capability flag.

For an update, first require one exact full-resource collection item and retain its returned links with `onlyData=false`. If that item omits any required projected identity, state, or capability field, read its returned `self` link, or its returned `canonical` link when no `self` link is present, with the same explicit fields projection and `REST-Framework-Version: 9`. Follow only a link returned by that exact full-resource item. Do not construct an item URL from `QuestionnaireTemplateId`, `QstnrTemplateId`, or `QuestionnaireId`, and do not follow a link from the LOV row or another full-resource item. The item response must repeat the same QuestionnaireTemplateId, QuestionnaireTemplateName, SubscriberCode, SubscriberName, and VersionNumber. A missing usable item link, rejected projection, identity mismatch, or item response that still omits a required projected field is a target REST-contract mismatch and blocks update preview.

A complete REST state readback still does not authorize update. Require the target-registered Data Loader `MERGE` operation, exact per-field and per-component mutability evidence, current-value preservation, and applicable downstream-usage evidence before an update can proceed.

### Questionnaire Template Data Loader catalog filter

For `resolve_template_hdl_contract`, set `questionnaire_template_business_object_filter` to the following single `q` value and let `core.fusion-api.rest-api-client` encode it. Follow [HDL Metadata Discovery](../../references/hdl-metadata-discovery.md) for the separate unchanged shared-loader gate:

```text
(BusObjTopDiscriminator LIKE '%Questionnaire%' ESCAPE '\' OR TemplateFileName LIKE '%Questionnaire%' ESCAPE '\' OR UIName LIKE '%Questionnaire%' ESCAPE '\')
```

The server-side filter narrows discovery; it does not authorize a fuzzy registration match. Do not add a `ProductAreaCode` predicate to pillar-authored discovery requests: a valid cross-product registration can have that value absent, and product area is not part of the QuestionnaireTemplate business-object identity. Paginate the filtered result to completion, retain sanitized candidate identities, then apply the exact discriminator/template rule from the resolver. Do not retry with an unfiltered first-page scan and do not infer `QuestionnaireTemplate` from a `Questionnaire` candidate returned by the broad `LIKE` predicate.

The shared helper owns its internal filter and is not rejected solely because that filter narrows product area. Require its actual validation to resolve the same exact registration and complete current contract. If pillar discovery succeeds but the shared lookup completes with no exact registration, report `shared_loader_registration_mismatch`, not an unregistered business object, and stop. Preserve request failures as auth/authz, transport/environment, or Fusion API errors rather than registration mismatches. Never request ProductAreaCode from the user, rewrite the shared helper, or bypass core validation.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| A product-reference endpoint is not documented | Use only a current approved target export or exact readback supplied in task context; otherwise classify the dependency as MISSING rather than inventing a request |
| Current project subscriber evidence is absent | Run only resolve_live_questionnaire_subscriber through core.fusion-api.rest-api-client; do not use its result as authority for template, question, or create-state checks |
| Current project reference evidence is absent | Run only the matching declared resolve_live_template_* fallback through core.fusion-api.rest-api-client; retain each resolver's stated partial or composite limitation and do not use it outside its documented scope |
| A required read-only dependency has no current project evidence | Invoke its declared live resolver during preflight before classifying it as MISSING or ambiguous; persist only sanitized match, status, and timestamp evidence |
| An exact Questionnaire Template update lookup omits a required projected state or capability field | Keep only documented attributes in `fields`; follow the exact full-resource collection item's returned `self` or `canonical` link and repeat the projection. If the link or field remains unavailable, classify a target REST-contract mismatch and block rather than inventing or defaulting update permission. |
| A declared suggestion-capable value has zero exact matches | Retrieve and fingerprint only its declared bounded candidate catalog, apply subscriber/parent/capability restrictions, rank at most three exact returned values, and wait for explicit approval. Multiple exact matches remain ambiguous. |
| A reference-value suggestion is approved | Bind approval under the parent suggestion contract and rerun the original exact resolver plus every compatibility check before a new immutable DAT preview. |

| Live Data Loader metadata differs from supplied DAT or matrix evidence | Use the current live contract for transport and disclose the difference |
| An existing question cannot be proven for the same subscriber | Block the placement; do not rely on a code-only match |
| A missing question is found while preparing a template | Do not silently create it; require explicit embedded-creation intent, current hierarchy support, full question data, and a new preview |
| A root key is checked for duplicates | Apply operation-aware cardinality; zero target matches is expected for create, not a missing reference |
| A Questionnaire Template update is prepared | Require one authoritative full-template readback in addition to the LOV identity, bind current usage and exact per-field/per-component mutability, classify each submitted child as existing or new, preserve omitted children, and reject any immutable-key change or destructive interpretation. |
| A template is in use | Permit only the exact changed fields and child operations proven editable by current release-specific evidence. Treat the declared direct-usage REST result as partial; block hierarchy or lifecycle mutation without complete impact proof. |
| A surrogate ID appears in evidence | Retain it only in source evidence where required and never map it into the portable HDL artifact |
