## Field Validation

| Check | What Happens | Applies When | Resolver |
|---|---|---|---|

| Rule priorities are intentionally ordered | Continue only after priorities are reviewed; equal priorities have undefined sequential evaluation order | Multiple rules apply to the same task | |
| Rule status and condition type are explicit | Continue only after the rule is active or inactive and either always valid or based on complete primitive or payload conditions | Every rule | |
| IF conditions use complete AND or OR logic | Continue to participant design | Multiple IF conditions are supplied | |

| Live write candidate contains exactly the resolved ruleset | Continue only after candidate JSON has one finalJsonResponse entry matching the fresh resolved ruleset | A live Approval Rules write is requested | |
| Rule-file graph is complete | Continue only after shared IF links to every RULE, every rule has unique ID, position, ruleName, conditionName, linked condition, THEN, and participant nodes, all path targets exist, and source-generated routing wrappers are unchanged | A live Approval Rules write is requested | |
| Payload-attribute condition uses the supplied serialization contract | Continue only after the payload path, Task.payload identifier, Attribute type, flags, quoted String or numeric literal, expression text, and requested operator are complete | A rule condition compares a payload attribute to a literal value | |

## Source Notes

The legacy Configure Rules validation guidance and the supplied serialized Approval Rules JSON examples define the condition, graph, and participant validation rules in this resource. For String payload conditions, retain an escaped quoted JSON-string literal; for numbers, retain the supplied numeric literal. Never hand-build a partial rule graph or infer a missing routing wrapper, node ID, participant field, or path.
