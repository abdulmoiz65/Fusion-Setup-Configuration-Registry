# Candidate Selection Process Dependency Readiness

## Required Dependency Order

| Sequence | Dependency | What Must Happen |
|---|---|---|
| 1 | Target and representation | The generated task target must resolve exactly once before resource guidance is used |
| 2 | Current task baseline export | Run `shared.setup-export.task-level-export` for this exact task, without template-only or scoped criteria, before duplicate classification, custom-object collision checks, package construction, or reconciliation |
| 3 | Export validation | Verify the completed export is fresh, belongs to this exact task, is unscoped, and contains the members needed to build the process, phase, state, and candidate-status dictionaries |
| 4 | Identifier, identity, and status resolution | Use the verified export dictionaries to prove CSP_SUBPROCESS_CODE generation, validate effective CSP_PROCESS_CODE absence, reject definition-code collisions, and resolve each candidate-status identity. Use the user-authorized successful custom-phase package only for its exact settings identifier profile, then use the verified export dictionaries for collision checks. |
| 5 | Custom create-package contract | Validate the source-backed custom phase/state package profile, system-owned rows, routing, and package rules before execution-ready package generation |
| 6 | Authentication readiness | Before the final immutable submission preview, use `core.auth.fusion-oauth-authentication` to confirm the configured environment can obtain a usable local token. Complete interactive login before asking for execution approval when a refresh is required. |
| 7 | Data Loader handoff | Hand the final archive exclusively to `core.data-loader`, which owns immutable preview, SHA-256 binding, standalone approval, upload, initiation, and result verification |

## Custom Package Profile

| Package Area | Required Source-Backed Shape |
|---|---|
| Metadata and baseline members | Preserve `ASM_SETUP_CSV_METADATA.xml` and every expected task member. Members outside the supported profile remain header-only rather than being removed. |
| Process and custom phases | Create one `CSW` Draft/TEMPLATE/inactive process row using the effective CSP_PROCESS_CODE. Create one `CSW_BASIC_PHASE` `ORA_IRC_LC` row using a pattern-proven client-generated CSP_SUBPROCESS_CODE and one `ORA_IRC_LC_PHASE` row using the Oracle-generated PHASE_DEFINITION_CODE for every custom phase. The phase row, its translations, its settings, and its process-routing row must join exactly. |
| Custom states | Create one `ORA_IRC_LC_STATE` row and translations for every distinct custom state using the Oracle-generated numeric STATE_DEFINITION_CODE where the export shows that shape. Route each requested state-to-phase association using the state definition code, owning CSP_SUBPROCESS_CODE, and the export-resolved `PublicStatesCode` and `PublicStatesTypeCode`. |
| Settings | Create one settings row for every custom phase plus Offer and HR. Generate each SettingCode and SettingItemCode only through the user-authorized custom-package profile and collision checks. For each custom phase, create `IsMandatory=N` and `IsRestricted=Y` setting items. The Offer block has the four source-backed setting items; the HR block has the two source-backed setting items. Every settings and setting-item reference must join its parent exact raw Code. |
| Offer and HR | Append generated Offer then HR `ORA_IRC_LC` rows after custom phases, with types `CSW_OFFER_PHASE` then `CSW_HR_PHASE`, each using a pattern-proven client-generated CSP_SUBPROCESS_CODE. Use seeded phase codes OFFER and HR verbatim. Add their source-backed settings and canonical routing fragments; user-supplied Offer/HR properties do not replace them. |
| System routing fragments | Preserve the source-backed Offer start/end and offer lifecycle routing states, and HR start/end and HR lifecycle routing states, together with terminal seeded state codes REJECTED_EMPLOYER and WITHDRAWN_BY_CANDIDATE. Rebind only generated CSP_SUBPROCESS_CODE and settings identifiers; do not transform or invent seeded or Oracle-generated identifiers. |
| Translations | Include source-language rows for each newly created process, custom phase, and custom state. Translation parents must exist as exact raw `Code` and `TypeCode` values in the archive. |

## Dependency Classification

| Result Category | When Used | Can Run Lookup/Create? |
|---|---|---|
| Satisfied | Mandatory resolver confirms the generated target | No |
| Verify | Export evidence must be complete, fresh, exact-task, and unscoped | Read-only through the selected workflow only |
| Lookup | The export, collision check, or candidate-status identity must resolve exactly once | Read-only only |
| Verify | A source-backed custom package profile and its exact joins must validate | Local validation only; no archive submission |
| Handoff required | A final archive requires the workflow-owned `core.data-loader` execution path | No direct pillar import |
