# Input Validation — Parent, Language, Cookie Consent, Filters, and Settings

Require a nonempty `SiteName` (maximum 240 characters), `SiteCode` (maximum 200 characters), an active default language (default `US`), and zero or more additional active initial language codes. Build an ordered, exact-match language set with `DefaultLang` first, then caller-supplied additional codes in their supplied order. Reject empty values and duplicates. Resolve a zero-match exact SiteCode and the next sequence before create-archive generation.

Retrieve the live registration, starter DAT, and parent attribute-details schema afresh through the core Data Loader resolver immediately before each preflight and archive. The live registration must include parent `recruitingCESites` and children `languages` and `cookieConsent`, plus a matching parent attribute-details schema. Require `filters` only when a Filter is requested. Project workbooks, previous DATs, and saved registration JSON are audit artifacts only and must never be reused as live input. Parent `SiteNumber` is a blank DAT column, excluded from REST, and never caller supplied. A DAT with sample values and only `SiteId`, `SiteNumber`, `RestAction`, and `SiteCode` is a technical starter skeleton; do not reject a create because it omits business columns that the fresh live attribute-details schema exposes as selectable. Determine required parent-create inputs exclusively from the registration's explicit `MandatoryOnCreate` list, and require those fields to be present in the fresh live attribute-details schema. Do not treat generic `MandatoryStatus=Yes` or a live mandatory-attribute list containing `SiteId`, `SiteNumber`, or `RestAction` as a create requirement: the first two are Fusion-generated and the workflow supplies `RestAction=POST`.

For the default combined archive, construct the parent header from the ordered live attribute-details schema and include `SiteName`, `SiteCode`, `DefaultLang`, `SequenceNumber`, `StatusCode`, and `TemplateNumber` when they are the published required-create fields. Create one parent row with blank `SiteId` and `SiteNumber`; one Languages POST row per validated selected language; and one Cookie Consent POST row. The Languages rows must contain every selected language exactly once, including `DefaultLang`. Both child rows retain blank generated IDs and `SiteNumber`. If a child header contains `SiteCode`, populate it with the exact parent Site Code even though it is excluded from the REST payload; it is required for same-load parent routing. Cookie Consent business fields remain blank. Populate `RestAction=POST` only when the current live header includes it.

For requested Filters, apply [ora_filters.md](ora_filters.md) before adding a `filters` section and rows. Resolve every requested value through its live type-specific LOV and replace a confirmed display-name choice with the returned ID/code before duplicate checks, preview, or source generation. Stop on zero or multiple exact matches, a failed by-ID confirmation, or an inactive Job Category. In combined create and persisted-parent Filter POST, `ObjectCtxId`, `ObjectId`, and `SiteNumber` are blank; `SiteCode` is the exact requested parent code when its current header contains the field; each row has `DimensionTypeCode` plus exactly one matching business value. `ObjectCtxId` remains blank in both operations and must not be excluded from the live REST mapping.

For a Cookie Consent PATCH, require an existing exact parent, one exact Cookie Consent child, and the `SiteCode`-to-`CookieId` Object User Key. The source contains no parent row. Populate `CookieId` with the resolved existing child ID, `SiteCode`, every explicitly requested nontechnical child business field, and `RestAction=PATCH`; leave `SiteId` and `SiteNumber` blank. Every unrequested child business field is blank. Require at least one requested field, reject duplicates, and validate each field/value against the current child template; routing, audit, generated ID, `RestAction`, and `SourceRef*` fields are never patch targets.

Each text value requires an exact target field. For example, `Accept button label: "Accept"` maps only to `AcceptButtonLabel`, and `Custom category description: "Optional analytics cookies"` maps only to `CustomCategoryDescription`. Never copy one supplied value to `PopUpMessage`, `PolicyMessage`, button labels, category messages, or custom-category fields merely because the user used collective wording such as “custom labels”, “cookie labels”, “all labels”, or “cookie text”. Treat that wording as ambiguous and ask for named field/value pairs. Do not enable a flag because a related text value was supplied; a flag changes only when explicitly requested.

## Cookie Consent UI-state rules

For a PATCH, read the current child first and calculate the **effective state**: the existing value for every unrequested business field plus every requested replacement value. Test the rules below against that effective state, not only the fields present in the PATCH. Treat a text value containing only whitespace as blank. A flag must use the live template's Boolean representation.

| Effective condition | Required validation |
| --- | --- |
| `CookieMessageEnabledFlag=true` | Require nonblank `PopUpMessage`, `AcceptButtonLabel`, and `PolicyMessage`. |
| `DeclineButtonEnabledFlag=true` | Require nonblank `DeclineButtonLabel`. |
| `CookiePreferencesEnabledFlag=false` and `CookieMessageEnabledFlag=true` | Require nonblank `CookieLinkLabel`; the client uses it for the Learn More policy link. |
| `CookiePreferencesEnabledFlag=true` and `CookieMessageEnabledFlag=true` | Require nonblank `PolicyMessage`, `PreferencesButtonLabel`, `PreferencesSaveButtonLabel`, `StrictCategoryMessage`, `FunctionalCategoryMessage`, and `AnalyticalCategoryMessage`. The client opens Preferences instead of the policy-only dialog. |
| `CustomCookieEnabledFlag=true` | Require `CookiePreferencesEnabledFlag=true` and nonblank `CustomCategoryButtonLabel` plus `CustomCategoryDescription`. |

`CookieLinkLabel` is not visible while Preferences are enabled. Custom-category text is not visible while `CustomCookieEnabledFlag=false`; preference text is not visible while `CookiePreferencesEnabledFlag=false`; and all Cookie Consent text is not visible while `CookieMessageEnabledFlag=false`. Do not reject a PATCH solely because it retains such inactive values, but list them as inactive in the immutable preview.

The immutable preview must enumerate only the exact requested business fields as `field: current value → proposed value`. Do not summarize a text change as “all labels” or use a single repeated value for multiple fields unless the user separately named every field and supplied that value for each one.

The web client sanitizes rich text when rendering `PopUpMessage`, `PolicyMessage`, and category descriptions. Do not claim that an arbitrary HTML fragment will render unchanged. Preserve the requested source value, warn that unsafe or unsupported markup can be removed by the client, and rely on post-load editor/read-back verification rather than attempting an incomplete local HTML sanitizer.

## Existing-site language, status, and link validation

Apply [ora_parent_operations.md](ora_parent_operations.md) before any source generation. Resolve one exact existing parent and its expanded language collection. A requested added or default language must exactly match an installed language with `ActivationStatus=ACTIVE`. An add must be absent from the site collection; a default-language change must already be present exactly once. Reject empty values, duplicate language additions, a request to remove a language, or an already-current status change. The Site Editor Copy Link accepts a site-enabled requested language; otherwise use the current default's resolved `LanguageTag` and persisted String `SiteNumber` as `{uiBaseUrl}/CandidateExperience/{LanguageTag}/sites/{SiteNumber}`. Never use `SiteCode` or `SiteURLName`, reverse the language/sites order, or return a `CandExpSecured` route. An inactive site still receives this link with an explicit statement that it works after activation.

For a parent status/default-language PATCH, require the published parent `PatchUrl`, an updateable requested field, and an exact current parent template. For language add, require a published `languages` child POST contract and current child template. A web-client endpoint is evidence for a candidate capability, not authorization to emit a Data Loader archive; stop if the live registration does not expose the operation.

Remove every `SourceRef*` field. Build each included row from a field-name-to-value map and serialize exactly one value cell per sanitized live-header attribute, in header order. Use one operation only: derive `values` by iterating the sanitized header list and looking up each field in the map, then join `MERGE`, the section discriminator, and that one `values` list. Do not append a separator, a blank, `RestAction`, or a routing field after that join. This preserves trailing blank fields without creating an extra value.

Before preview or approval, reopen the exact DAT member that will be zipped and parse every generated `METADATA` and data line. Require matching section discriminators, exact `MERGE|<section>|...` prefixes, and `len(mergeCells) == len(metadataCells)` after splitting on `|`, including trailing blanks. Record the complete header-to-value mapping. This is a hard stop, including when the intended final value is blank; a count mismatch must be reconstructed from the field map, never hand-edited. In a combined source, hard-fail if a child header contains `SiteCode` but its row does not contain the exact requested parent Site Code. The child `SiteNumber` field must be String even when the active operation leaves it blank; a Number-typed field cannot represent values such as `CX_41025` and blocks routing.

## Site Settings validation

Apply [ora_settings.md](ora_settings.md) for any Settings discovery or update. Require an exact existing Site Code and read the current `settings` collection first. Accept named catalog options only, normalize booleans to the Strings `true`/`false`, and reject raw/unknown keys, duplicate selections, invalid enumerations, duplicate or unknown facet-order tokens, mode-incompatible options, and missing text/URL values. The existing setting decides PATCH versus POST; never create a Settings row during initial/combined create.

For a Settings archive, include only required top-level metadata and one `settings` child row per requested key. Populate persisted `SiteNumber`, Site Code, `SettingKey`, normalized `SettingValue`, and resolved `SettingId` only for PATCH. Leave generated `SettingId` blank for POST. Keep `SiteNumber` and `SiteCode` out of the REST body, retain `SettingId` as a key field, and set the appropriate `RestAction`. Apply the standard field-map construction and exact metadata/data cardinality test before preview. Do not read or write `/globalSettings` for ordinary site Settings.
