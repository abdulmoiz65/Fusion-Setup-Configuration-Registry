# Creation-first CAP write assessment

Use the visible FDD rules and current product contracts, not its example names or
counts. One root-only create can proceed through the evidence-gated preparation
and exact-approved shared submission continuation. Sparse basic updates now have
a separate evidence-gated [update contract](update-contract.md); other writes remain unavailable.
Read-only inspection is not create readiness or proof of account grants.

## Supported integration, not a private service

Shared Task Hook intentionally returns a plan for pillar-owned rule evaluation.
After actual executable CAP rules pass against final bytes, its public
build_data_load_preview can build a preview; approve_data_load_preview and
verify_approved_data_load_archive follow only exact user approval. Generic
submission checks task context and exact ZIP; CAP must bind its extra inputs/evidence and derive the
displayed business fields from that same ZIP. A central CAP-specific plugin is
not a requirement. The current read/refusal graph is not a create validation plan.

Shared validate_source_attributes and prepare_archive support prepared DAT
without a spreadsheet runtime. A real template and verified product create
contract remain required. Do not use a synthetic fixture as deployment evidence.
Current Data Loader upload/initiation reaches ordinary urllib.request.urlopen,
not the configured-host redirect guard. No production adapter is established;
test-callable injection is not permission to implement a CAP HTTP client or
multipart encoder. This route uses that unchanged shared transport behavior;
project-specific acceptance is not reusable authorization. Do not reintroduce an
unconditional transport blocker, alter shared policy or disable TLS.
Preparation uses cap_create_handoff; exact-approved submission uses
cap_create_submission and the [frozen submission contract](create-submission.md).

## Sequence and per-operation acceptance

| Operation | Inputs / additional contract needed | Readback and restrictions |
|---|---|---|
| Create isolated root | name, description, verified visibility; generated number/omitted status/date/contributor behavior; current template, grants, duplicate baseline, Run Book, exact immutable approval | One unique new profile, exact fields; system/default/contributor state and loader/CAP processing independently verified; never modify an existing synthetic profile for testing |
| Basic update | canonical key/PATCH mapping, exact diff, writable fields, null/omission/concurrency | Only reviewed changes; number immutable; date flag is not composite-key fix |
| Contributors | verified people resolver, criterion/attachment/parent IDs, exact individual/CSV conversion and add/replace/remove contracts | Parsed, resolved and effective counts distinct; file intake does not establish deployed file format |
| Activate/deactivate | allowed transition, exact key, grants, provider/usage eligibility | Already desired state no-op; no implied restoration of deleted CAP; default deactivation needs eligibility, not blanket prohibition |
| Content defaults | existing seeded type/row keys, typed allowlists, observer replacement and null/reset/inheritance | Update existing rows; no ordinary child create or internal defaultedRow workaround |
| Certificates | existing row and permitted template, enabled/filename/null mapping, grants and inheritance | No guessed filename/upload; rendering and downstream effects need separate acceptance |
| Delete | logical status and replacement/migration route; provider/usage/nonself/default protections | Never delete system default; MERGE_DELETE is not product lifecycle proof; migration completion separately verified |
| Reconcile | verified action, arguments, grant, supported executor/correlation | No invented RestAction; observed ORA_NEEDS_PROCESSING is pending, unknown states unverified |

Each needs safe transport and operation-specific privileges, validation and
exact-change approval. Root POST does not inherit unrelated PATCH or child-key
blockers. Default flags/mandatory markers are not proof of omission behavior.
Template child visibility is not successful contributor-load evidence.

## FDD conflicts and semantic safeguards

FDD mandatory-people wording conflicts with empty-contributor warnings. Accepted
policy permits an empty custom CAP only after its actual effects are verified
and disclosed. Never infer its access from the special delivered default CAP.
Everyone is catalog-manager visibility, not management grants or learner access.
Contributors, functional privileges and central override remain separate.
“Manage Administrator Profile Values” has no verified public service mapping.
Missing attachment is a bounded gap, not permission to invent its requirements.

## Approval and completion

Before an available write: exact environment, operation, inputs, expected effects
and immutable ZIP hash; only later explicit approval authorizes that load.
Use shared services unchanged; no source rebuild/live revalidation after approval.
No automatic retry of uncertain writes or cleanup deletion. Preparation creates
an unapproved preview only after all evidence passes. Submission requires the
later exact-preview approval, verifies frozen inputs/evidence/ZIP/context, uses
the public shared approval and uploader APIs, and records an anti-repeat marker.

An approved initiation is only submitted. A separately requested shared status
step must inspect terminal dataset status, object counts and every required
error endpoint. Then cap_write_contract.verify_root_readback requires a complete
unique exact-number result and compares all supplied approved fields; it reports
root_fields_match, never created-and-complete. ORA_NEEDS_PROCESSING is pending;
all other processing states remain unverified until a sourced terminal contract
and correlated evidence exist. It does not inspect contributors or loader jobs.

Record no raw metadata/internal IDs/person rows in project files. Use sanitized
facts, counts and hashes; account/date/language limits apply to read evidence.
