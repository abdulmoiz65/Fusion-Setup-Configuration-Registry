# Absence Plans Dependency Readiness

## Required Dependency Order

| Sequence | Dependency | What Must Happen |
|---|---|---|
| 1 | Current resource contract | Refresh absencePlans describe metadata before validating parent, child, or flexfield data |
| 2 | Plan type decision | Before every create or captured profile, retain an explicit plan type. If a code is omitted, map one exact user-selected Plan Type Name from the matrix to its code, or classify the supplied policy description and propose a type only for one clear intent. If no policy description is supplied or no unique intent matches, ask the user to choose a plan type before applying defaults or preparing the DAT. |
| 3 | Qualification or No Entitlement policy decision | When unpaid tracking could be Qualification or No Entitlement, require a stated policy direction or an exact answer to the two-way clarification before retaining Q or N, applying a profile, or preparing the DAT. |
| 4 | Balance frequency source and repeating period | When a requester asks for Repeating period, repeating monthly, or a Monthly* period, resolve the balance source and one existing exact period before applying defaults or preparing the DAT |
| 5 | Plan type profile | Resolve a type only after it is explicit or user-confirmed, and after the Qualification or No Entitlement policy decision when applicable |
| 6 | Calendar period anchor | When plan type is Accrual (`A`) or No Entitlement (`N`) and period type is Calendar (`C`), obtain explicit CalendarStartDay and CalendarStartMonth; do not default either value |
| 7 | Legislative scope | For creation require supplied or explicitly confirmed legislation; for read-only discovery retain its documented US default. Resolve it to one territory, then resolve a supplied LDG ID or exact name, or discover authorized LDGs using the selected legislation and supplied organizational context. Require selection when candidates remain ambiguous |
| 8 | Existing plan identity | For a read-only history or mutation request, accept either a supplied primary key or an exact-name lookup scoped by legislation and lookup as-of date; require and validate the selected PlanId with an explicit operation-specific date before a date-scoped mutation, or at its recorded lookup as-of date with explicit complete-deletion scope for the selected logical target for ZAP |
| 9 | Complete plan history | For AC9, traverse every effective-date boundary for the selected PlanId and retrieve the full physical plan record for each discovered slice before deriving the history-only display |
| 10 | Child identity | For any child update, correction, or delete, resolve the exact current child after the parent |
| 11 | Operation-relevant LOV set | For the exact parent or child operation, accept requester-supplied display names, classify every supplied and dependency-affected value through current target REST describe metadata or an existing named REST resolver, require one current/effective compatible result, and retain only the returned code/ID for DAT output while keeping the matched name in the summary |
| 12 | Date-effective loader contract | Refresh the registered UCM template, use a requester-supplied or explicitly user-confirmed current-system-date business date for a create, require an explicit date for a date-scoped non-create, or explicit complete-deletion scope for the selected logical target for ZAP without a range date; derive the operation-specific effectiveOf, and omit physical EffectiveStartDate from parent and included supported sections |
| 13 | Flexfields and final loader contract | Resolve only current flex contexts; core.data-loader separately validates the current template, source shape, preview, and approval |

## Dependency Classification

| Result Category | When Used | Can Run Lookup/Create? |
|---|---|---|
| Satisfied | An explicit required identity or current metadata value is already present and validated | No lookup needed; continue |
| Lookup | A documented read-only resolver can map the supplied value to one current value | Run the read-only lookup only |
| Verify | The current Data Loader sample requires an explicitly supplied target value for which this source set provides no portable default | Verify the sample requirement; do not create or infer a related record |
| Blocked | A required identity, current contract, exact match, or supplied target value is absent or ambiguous | No; stop and request the missing business value |
| Metadata gap | The current target metadata cannot establish a field, context, child, or loader header | No; refresh metadata or obtain the missing product contract before preparation |

## Data Loader Handoff

The current Data Loader template, target LOV enforcement, immutable artifact validation, preview, approval, and any loader diagnostics belong to core.data-loader. This task hands off only after its task-local validation graph succeeds; it does not claim a separate Fusion REST adapter for Data Loader metadata.
