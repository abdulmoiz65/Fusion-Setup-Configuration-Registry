# Absence Plans Defaulting Rules

Source guidance: [Absence Plans Minimal + LOVs](https://confluence.oraclecorp.com/confluence/pages/viewpage.action?pageId=21792518140) and [Absence Plan Setup - REST API Details](https://confluence.oraclecorp.com/confluence/display/FUSIONANC/Absence+Plan+Setup+-+REST+API+Details).

## Defaulting Policy

The source captures document values the client sent in six successful plan creations. They are source-backed preparation candidates, not proven server defaults. Captured policy values are examples only, not permission to fill missing decisions. Except for Pending setup status, an explicitly confirmed creation date, and the documented whole-unit rounding-precision default, require supplied policy values or explicit confirmation of the named setting and value. General permission to use defaults is not confirmation of statutory, pay, eligibility, or other policy decisions. The matching plan type and current template/describe support establish technical applicability only. Core data-loader then validates the live loader contract and business values in its own source review and immutable-preview workflow. Never overwrite an explicit requester value.

## DAT Default Application Contract

Build a normalized parent-value set after `refresh_absence_plans_dataloader_template` and `refresh_absence_plans_describe` have both passed. It must contain every requester value and every applicable omitted default from the tables below. Build the compact parent DAT only from that normalized set plus the required loader controls and derived `effectiveOf`.

For every applied default, add a Task Hook `changes` entry with `path`, `before`, `after`, and `reason`; use the business-facing field label in the reason. The `path` must identify the parent DAT field. A default result is not passed if an applicable default has no corresponding change entry.

Before preview, inspect the exact DAT member in the final ZIP. For each applied default, require one matching parent `METADATA` column and the same nonblank value in its `MERGE` row. Stop if a default is missing, blank, duplicated, changed, or replaces a requester value. Do not include a candidate that the current template or describe contract does not expose; retain that outcome as an explicit issue rather than claiming that all defaults were applied.

The plan-term guard is important: the source page distinguishes AbsencePlanPeriodType A from all other period types. For period type A, the captured UI rule excludes NOT_APPLICABLE; for every other period type it excludes ORA_ANC_MNTLY_ANN_DT. This period-type A is not the Accrual plan-type code A, and it is also distinct from Balance Frequency Source. A Calendar plan term and its calendar anchor do not choose Person primary frequency or a Repeating Period. Core data-loader must validate the final selected code in its current loader workflow.

`DisableEntitlementOverrideFlag` maps to the REST field titled **Disable payment percentage override**. `StatutoryFlag` maps to the REST field titled **Enable concurrent entitlement**. Include each in a compact DAT only for its explicit request or explicit confirmation of that named setting and value; never substitute one for the other.

The captured `AccrualMethodCode` value `I` is evidence only for Incremental. It is not a generic Accrual Method fallback and must not replace an explicit request such as Front-loaded. Resolve an explicit business label to a current target-contract-valid code, preserve that code in the compact DAT, and stop before preview when that mapping is unavailable.

## Conditional Rounding Precision

Resolve the selected Rounding Rule first. When it is Always round down
(`ORA_ANC_RND_DWN`), Always round up (`ORA_ANC_RND_UP`), or Standard rounding
(`ORA_ANC_RND_STND`), `RoundingPrecision` is conditionally required. Preserve an explicit requester value. If it is omitted, apply `RoundingPrecision=0` as the
documented whole-unit default and disclose `Rounding Precision: Whole units (0
decimal places)` in the plain-language summary. Add the normal Task Hook change
entry and verify that both `RoundingRule` and `RoundingPrecision` occur once in
the same compact parent `METADATA` and `MERGE` row. Do not treat a template's
global optional flag as proof that the dependent value can be omitted. For No
rounding (`ORA_ANC_RND_NONE`), do not add a precision merely from this rule;
retain an explicitly supplied current-contract-valid value or omit it.

## Date-Effective Operation Mapping

Treat EffectiveStartDate as a normalized business input, not as a physical parent or child Data Loader attribute. Derive effectiveOf for the parent and every included supported child/DFF row. Never accept effectiveOf as a free-form input. A create may use the current system date for an omitted business effective start date only after explicit user confirmation; do not default a date, range, deletion scope, or destructive choice for a non-create operation.

| Requested operation | RestAction | effectiveOf | Required input |
|---|---|---|---|
| Create | POST | RangeStartDate=<EffectiveStartDate> | Explicit EffectiveStartDate or the explicitly user-confirmed current-system-date proposal when both EffectiveStartDate and RangeStartDate are omitted; omit physical EffectiveStartDate from the DAT |
| Update | PATCH | RangeMode=UPDATE;RangeStartDate=<EffectiveStartDate> | Exact current identity and explicit EffectiveStartDate business input |
| Correction | PATCH | RangeMode=CORRECTION;RangeStartDate=<EffectiveStartDate> | Exact current identity and explicit EffectiveStartDate business input |
| End date | PATCH | RangeMode=END_DATE;RangeEndDate=<EffectiveEndDate> | Exact current identity and explicit EffectiveEndDate business input |
| Delete changes | DELETE | RangeMode=DELETE_CHANGES;RangeStartDate=<EffectiveStartDate> | Exact current identity, explicit EffectiveStartDate business input, and explicit DELETE_CHANGES scope |
| ZAP | DELETE | RangeMode=ZAP | Exact current identity, explicit destructive intent, and immutable Data Loader approval |

Apply this mapping independently to the exact target section. ZAP requires explicit complete-deletion scope for the selected logical target: whole-plan scope only for `absencePlans`, or the selected logical child for a child section. Child ZAP never authorizes parent deletion. For child ZAP, validate the exact parent relationship and child identity at the recorded lookup as-of date without adding a ZAP range date. The current registered section inventory is `absencePlans`, `absencePlanDDFs`, `absencePlanDFFs`, `accrualBands`, `eligibilityProfiles`, `entitlementBands`, `entitlementBandDetails`, and `events`. A direct child-only operation normally uses the root `METADATA|absencePlans|RestAction` marker without a parent MERGE row and the child's own `RestAction` plus derived `effectiveOf`. A child-only create against an existing plan writes the exact returned parent AbsencePlanId and omits the generated local child identifier. A child non-create writes the child's exact returned identity and parent relationship. A same-archive parent-and-child create instead uses the parent create's normalized name-and-legislation relationship because no parent ID exists yet. For an `absencePlanDFFs` update or correction, include the exact existing `absencePlans` row as an identity-only CORRECTION carrier when a carrier-free archive has returned `PARENT key value is required for orphan REST child`: write only AbsencePlanId, correction effectiveOf at the exact target parent slice start, and RestAction, then write the DFF PATCH for that same plan and operation date. Do not copy parent business values or create a new parent effective row. Do not apply DELETE_CHANGES to `absencePlanDFFs`: live Data Loader evidence classifies that child resource as non-date-effective and rejects the date-range operation even when an identity-only parent carrier is supplied. When deletion of a parent plan's future slice is requested, target only the exact parent `absencePlans` row and let Fusion manage its flex child; verify both parent and DFF readback afterward. When the parent plan itself is end-dated or ZAP-deleted, likewise prepare only the exact `absencePlans` parent row: do not synthesize an `absencePlanDFFs` lifecycle row merely to keep the flex child aligned. After completion, verify the parent result and the DFF child result independently; live end-date and ZAP tests confirm that Fusion applies the parent's lifecycle to its flex child. For any standalone nested `entitlementBandDetails` operation, include its exact existing `entitlementBands` parent as an identity-only CORRECTION carrier when the carrier-free archive has returned `Not Found`: write only the band AbsencePlanId, EntitlementBandId, correction effectiveOf at the returned start of the exact parent-band slice selected at the operation date for a date-scoped action or the recorded lookup as-of date for ZAP, and RestAction. Then retain the detail row's originally requested create, update, correction, end-date, delete-changes, or ZAP controls independently; do not copy band business values or create a new band effective row. Never cascade a parent operation into child rows or convert an unsupported child operation into a different operation. Refresh the registered template and stop if the target section lacks the required operation controls. Create defaults apply only to create; update, correction, end date, delete changes, and ZAP preserve unspecified existing values and never receive create-profile defaults.

When a parent UPDATE establishes a new future effective row and direct children are also changed on that date, stage the parent update first. Wait for terminal success and read back the parent plus any auto-provisioned flex rows before preparing child changes. If a mixed batch already partially succeeded, never replay successful rows: use CORRECTION for an auto-provisioned DFF row that now starts on the target date, and retain UPDATE only for a child whose exact readback still shows no target-date row.

## Values That Must Not Be Defaulted From a Capture

| Field or Value | Why It Must Not Be Defaulted | Required Action |
|---|---|---|
| AbsencePlanName | No source profile establishes a name | Require an explicit nonblank name |
| AbsencePlanTypeCode | A policy description may support a proposal, but neither that proposal nor a current describe value is a customer decision | Retain an explicit code or map an exact user-selected matrix Plan Type Name to its listed code. When it is otherwise omitted, use resolve_absence_plan_type_intent to propose one matrix type and ask the user to confirm it. For a possible Qualification or No Entitlement decision, never default Q or N: require stated entitlement-policy direction or the exact answer to No entitlement policy was provided. Is this a Qualification plan or a No Entitlement plan? Set either code only after compatible selection or affirmative confirmation. When no policy description is supplied, or no, zero, multiple, or conflicting proposals result, ask the user to choose. Never default it from a capture, plan name, or current describe response. |
| EffectiveStartDate | The captures transport an effective start context differently from the REST describe input contract | Do not default from a capture. For a create that omits both EffectiveStartDate and RangeStartDate, use the current system date only after explicit user confirmation; otherwise preserve the requester-supplied date. |
| EffectiveEndDate | Fusion derives the terminal end-of-time date server-side on create; an explicit end date is business intent, not a physical DAT field | Do not ask for or synthesize a create end date. Preserve a supplied valid ISO end date in the normalized request and follow the supplied-create-end-date rule in ora_input_validation.md; never silently drop it or emit a physical EffectiveEndDate column. END_DATE requires the explicit business end date and derives RangeEndDate through the operation mapping above. |
| Unpopulated template attributes | The attribute is absent from both the requested values and applicable documented defaults | Omit it from the section METADATA header and MERGE row. Do not emit blank placeholder columns from the complete UCM template; retain only populated values and required nonblank loader control or relationship fields. |
| LegislativeDataGroupId 202 | The value is capture-environment-specific | Resolve a supplied target LDG ID or exact target LDG name within the resolved legislation; when omitted, discover authorized candidates and require selection if ambiguous. Never default the captured ID |
