# Absence Types Error Handling

## Error Situations

| Situation | What Should Happen |
|---|---|
| Required input is missing or invalid | Identify the exact field and stop before Data Loader preparation |
| Pattern intent is ambiguous | Keep the existing ask-for-pattern flow from resolve_absence_pattern: show Generic pattern, Illness or injury, and Childbirth or placement (maternity), and ask the user to choose one; do not apply a default |
| A name/description-based pattern suggestion is pending or rejected | Keep the pattern unresolved; wait for explicit confirmation or ask for an alternative selection. Do not interpret silence as confirmation or proceed to pattern-dependent defaults, DAT preparation, or preview. Pattern selection is not the final immutable Data Loader approval. |
| MAP event intent is unclear, unresolved, or matches more than one row | Retrieve every available event-type page, show only the returned Meanings, and ask the user to select one; do not expose LookupCode or default an event type |
| An LOV returns no match or multiple matches | Show the supplied business value and resolver classification, then request one precise value; for Legislative Data Group lookup, declare no match only after all returned pages are checked |
| A Display Feature or Rules prompt has no unique close lookup match | Stop before DAT preparation. Name the business field and persona when applicable, show only the valid Meanings returned by that field's exact lookup type, and ask the user to select one. Do not guess, choose the first row, or reuse a code from another field/persona lookup. |
| An optional LOV/checkbox attribute is supplied without its prerequisite context | Identify the attribute and missing or incompatible linkage rule, legislation, restriction, action, assignment status, or effective date; stop before Data Loader preparation |
| A supplied action, action reason, or assignment status does not form one valid effective-dated combination | Preserve the resolved identities and effective date; stop without selecting a fallback action reason or assignment status |
| An absence type event condition or response is unresolved, inactive, or ambiguous | Identify the event condition or response and stop before Data Loader preparation. Resolve conditions only from active ANC event conditions and responses only from ORA_ANC_EVT_ABS_ACTIONS. |
| A date-effective operation lacks live-template support or contains a caller-authored control | Identify the requested operation and required effective date; refresh the template and use only its supported columns, or stop |
| The final immutable DAT diverges from the refreshed parent or included child/DFF header | Classify as input validation, identify the affected DAT section, and block preview, approval, upload, and initiation until the archive is rebuilt and revalidated |
| A non-create identity is absent or ambiguous | Stop before DAT preparation and request one exact current absence-type identity |
| A requested plan association has no verified plan handoff, has an inactive or ineffective plan, is incompatible with the type legislation or LDG, has no supplied association date or resolved type EffectiveStartDate, has missing template-required values, or has a missing Priority | Classify as input validation, dependency failure, or template contract failure and stop before type DAT preparation; route exact plan resolution and verification through Absence Plans and exact type GET search. Do not block solely because of the absence type status. |
| Fusion rejects a plan association because the plan or Priority duplicates an existing association | Preserve the redacted Fusion error detail and classify it as a Fusion API or Data Loader process failure. Do not preflight-query the type's plans child or replace the Fusion result with a client-side duplicate check. |
| A plans-child association status is missing, C or P, unavailable from the filtered LOV, ambiguous, or conflicts between supplied code and meaning | Classify as input validation or catalog mismatch and stop before type DAT preparation. Resolve it only through `resolve_type_plan_association_status`; do not use the parent plan or absence type status. |
| The `plans` child contains a generated association ID, unverified plan value, association status not returned by its LOV, unverified statutory display value, missing required value, or invented date-effective control | Rebuild from the current registered plans child header using only verified handoff values, association status returned by its LOV, and requested Priority; do not invent association IDs, display values, or date controls |
| The registered template does not support the requested operation for a selected section | Stop before archive preparation; do not use REST describe or invent a DAT column |
| A date-effective source has a missing or incorrect derived `effectiveOf` value | Classify as source-shape validation. Do not preview or upload. Rebuild the exact member with `RangeStartDate=<YYYY-MM-DD>` for create, `RangeMode=UPDATE;RangeStartDate=<YYYY-MM-DD>` for update, `RangeMode=CORRECTION;RangeStartDate=<YYYY-MM-DD>` for correction, `RangeMode=END_DATE;RangeEndDate=<YYYY-MM-DD>` for end date, `RangeMode=DELETE_CHANGES;RangeStartDate=<YYYY-MM-DD>` for Delete Changes, or `RangeMode=ZAP` for a whole-type deletion. Revalidate the changed archive and obtain new approval before submission. |
| DELETE scope is ambiguous or ZAP intent is absent | Require explicit DELETE_CHANGES or explicit destructive ZAP intent; retain the normal immutable Data Loader approval gate |
| An LOV endpoint or output mapping is TBD | Classify an authoring gap and stop; do not substitute another REST endpoint |
| The live single-persona action remains unavailable after one token refresh with HTTP 401/403/404/405, timeout, or transport/environment failure | For US `GENERIC`, `II`, or `MAP`, automatically use the documented guarded catalog fallback only when one fresh exact live master template proves every locked 3/5/4 catalog row is present in its documented region and each catalog-named fresh live lookup contains exactly one `DO_NOT_DISPLAY` code. Use the locked catalog default and exact lookup type; never derive them from the master template. Persist fallback provenance; do not request a separate production or non-production readiness waiver. Retain the normal exact immutable Data Loader approval gate. Stop when any guard fails. |
| Fusion returns HTTP 401 or 403 for another read-only lookup | Classify authentication or authorization failure; refresh a rejected cached token at most once for that read operation |
| Another read-only request times out or the environment is unreachable | Except for the eligible single-persona fallback handled above, classify transport or environment failure and stop with the target environment and failed resolver |
| Fusion returns another 400-series contract or business-rule response | Except for the eligible single-persona action's 401/403/404/405 fallback handled above, preserve the redacted Fusion error detail, classify the failed stage, and stop |
| An exact-name absenceTypes request used `and`, `AND`, or an unquoted shell semicolon between Name and LegislationCode | Discard that result as invalid lookup evidence. Reissue only the read with the canonical semicolon-delimited q expression, passing the complete URL/path as one quoted CLI argument. The separator may be encoded as `%3B`, but the complete argument must still be protected from shell metacharacters. Do not mutate, replay, or conclude that the type is absent from the invalid request. |
| A Data Loader process times out, fails, or rejects DELETE_CHANGES, ZAP, or END_DATE because of dependencies | Preserve the process or request identifier, official status, and detailed log through core.data-loader; do not resubmit automatically. For dependency rejection, explain the exact application diagnostic without inventing dependencies. Reconcile the target, retained slices, and child state before any next archive. Do not automatically retry, delete dependencies, switch deletion scope, or fall back to UI/direct REST. A changed operation or retry after resolving the dependency requires a new immutable Data Loader preview and explicit approval. |
| A terminal result summary contains only a generic `{MESSAGE}` placeholder | Retrieve and persist the complete detailed object error log before classification. The summary is not row-level evidence and cannot prove success, failure, or all-or-nothing behavior. Do not start the next archive or replay any subset while the detailed log is absent. |
| A mutation reaches terminal `Failed` with zero failed-line errors and one or more data-set object errors whose detailed Messages serialize resulting objects | Preserve the official loader outcome as `Failed`; every serialized object is evidence, not proof of success. Require the detailed object log. Map every intended mutation row and identity-only carrier to an exact readback outcome, and map every returned diagnostic to an intended row or owning top-level object; do not require one diagnostic per DAT row. For a create, treat a serialized root ID only as a candidate read pointer: validate that it and every hierarchy ID are positive decimals no greater than `9007199254740991`, require each to pass `String(Number(id)) === id`, and query `q=AbsenceTypeId=<exact returned ID>` at the intended effective date for exactly one matching item. Then run `reconcile_absence_type_create_result`, including independently paged complete regions/usages/rules and the correctly quoted semicolon-delimited exact-name query with bounded read-only index-lag checks. For every update, correction, end-date, Delete Changes, ZAP, or child mutation, run `reconcile_absence_type_non_create_result` against the exact archive/hash and pre-submit baseline using both exact-ID and canonical business-key reads at the operation date, a post-submit D-1 predecessor read for UPDATE, complete independent child pagination, operation-specific slices, only-requested semantic deltas, and per-row plus batch classification. If every intended row is proved and no partial, extra, unrelated, or ambiguous state exists, report **functional success with a Data Loader reporting false positive**, preserve the official `Failed` status, set `noRetry=true`, and do not replay. If create name discovery remains pending, report **committed by exact ID; name-index reconciliation pending** instead. Any unsafe ID, missing detailed log, absent/extra row, incomplete nested pagination, wrong date or slice, conflicting identity, or mismatch is a real, partial, or ambiguous failure; block the next archive and do not replay automatically. Never infer all-or-nothing success from one serialized row in a multi-row batch. |
| A create reports `Too many objects match the primary key` or a date-effective overlap such as `27127` on child IDs | Run exact-ID-first create reconciliation when the result Message supplies an ID, then perform the bounded exact-name reads. A real failed create/key collision requires both no exact-ID object and no exact-name object after the bounded reconciliation; one immediate zero-result name query is not sufficient. Exactly one target with the complete requested hierarchy is a false-positive candidate only after UI-equivalent exact-ID validation and collection-discovery reconciliation succeed. An exact-ID-complete object whose name discovery remains pending is committed/inconclusive, not a safe retry candidate. A parent with missing or wrong hierarchy is partial success, not a false positive. Multiple exact targets or different IDs between the two read paths is ambiguous. Inspect the immutable DAT for copied pattern IDs, returned Fusion IDs, duplicate LOCAL tokens, unsafe IDs, or bad PARENT linkage. A corrected attempt is permitted only after reconciliation proves no committed or partial target; it must omit the parent `AbsenceTypeId`, use a new immutable archive with revalidated metadata-declared native business keys, and receive fresh approval. Never reuse pattern IDs as target child IDs. |
| A create omits parent `effectiveOf=RangeStartDate`, or sends only physical `EffectiveStartDate`, and readback uses Fusion's server date | Classify the date as a payload mismatch even when the hierarchy is otherwise complete. Do not correct by blind replay. For a disposable dependency-free test object, ZAP only that exact object after approval; then create a new immutable archive with the operation-derived parent `effectiveOf` control, an omitted parent ID, and revalidated metadata-declared native business keys. For non-disposable data, stop and require an approved business correction path. |
| A Display Features load has a serialized Absence Type response but the UI still lacks the requested row | Do not call it a false positive from a raw child record alone. Compare the requested pattern, UI section, `AbsenceRegionCode`, usage code, and all three persona values. A matching usage in `ADDITIONAL_DETAILS` does not satisfy an Additional fields request; rebuild against the pattern's UI-rendered `SCHEDULING` or `SUPPLEMENTAL_DETAILS` bridge. |
| An existing Display Features load reports region or usage `Not Found` | Read back the exact UI-rendered region and usage first to rule out partial success. If unchanged, inspect the immutable DAT for a parent MERGE, region `AbsenceTypeId`, composite `id,date`, `SourceRef*` hierarchy linkage, or a region UPDATE at the requested date. If a parent MERGE and child rows were combined, classify the proven combined-graph loader limitation and split the work into parent-only then metadata-root child archives; do not keep cycling linkage variants. Otherwise rebuild with a metadata-only root, parent-user-key region CORRECTION carrier at the returned region start, and exact usage PATCH at the requested operation date. Revalidate and obtain fresh approval; do not cycle through POST, composite IDs, or SourceRef alternatives. |
| Parent `DELETE_CHANGES` succeeds but Display Features still show the later values | Do not classify the parent operation as failed: parent Delete Changes is section-specific and does not cascade to independently dated usage slices. If the approved intent includes child rollback, refresh the exact hierarchy and submit a separate metadata-root child archive with exact usage `DELETE` rows and `RangeMode=DELETE_CHANGES;RangeStartDate=<child slice start>`, then verify every affected usage. |
| A Display Features load reaches terminal success | Read back the exact region, usage, effective slice, and all three stored persona codes before reporting success. A successful process alone does not prove the UI-equivalent values. |
| Approval and approval-restart both need to change | Do not place a dependent two-row transition in one archive on the assumption that Data Loader preserves row order. Disable restart and reconcile before disabling approvals; enable approvals and reconcile before enabling restart. Change at most one dependency field per persona in each archive and require every intermediate state to be valid. |
| A diagnostic or generated artifact cannot be persisted | Classify artifact persistence failure and stop without claiming readiness |
| A non-idempotent operation has an uncertain or failed result | Do not replay it automatically; reconcile through the approved Data Loader workflow and safe reads |

This serialized-object reporting pattern has been reproduced with complete
`GENERIC`, `II`, and `MAP` create hierarchies and with parent update,
correction, and end-date operations. Apply the classification rule to the
observed error shape and exact readback, not to a particular pattern or
operation name.

## Error Classifications

| Result Category | When Used | Next Action |
|---|---|---|
| Input validation | Required fields, pattern conditions, shape, type, length, or non-writable-field checks fail | Correct the identified input and rerun validation |
| Catalog mismatch | A required pattern or lookup code is absent from its documented LOV | Confirm the target-environment catalog and authoring source before continuing |
| Authentication or authorization | A read-only lookup other than the eligible single-persona action returns 401 or 403 | Correct access or refresh an eligible cached token once; do not retry a mutation |
| Transport or environment | A request other than the eligible single-persona action is unavailable, times out, or returns an environment-level failure | Verify the exact target environment and retry only the read operation when safe |
| Fusion API | Fusion rejects the documented read contract or omits required response fields outside the explicitly eligible unavailable single-persona action | Preserve redacted evidence and correct the contract before another attempt |
| Process timeout | The routed Data Loader process does not finish within its polling window | Report environment, operation, process or request ID, last status, elapsed wait, and next-check path |
| Process failed | The routed Data Loader process reaches a failed terminal status | Retrieve and persist the available process log through core.data-loader, preserve the official Failed status, reconcile exact live state, and distinguish a real/partial failure from a functionally committed state with false-positive reporting; never replay automatically |
| Artifact persistence | A required validation, diagnostic, or run artifact cannot be safely written | Report the intended path and stop without claiming completion |
| Approval blocker | A mutation lacks an exact Data Loader preview and explicit approval | Stop and complete the Data Loader approval workflow |
| Template contract | The registered UCM DAT template is unavailable, mismatched, or does not support the requested operation for an included date-effective section | Refresh the template or remove the unsupported section; do not infer support from REST describe |
| Authoring gap | A required LOV endpoint, output mapping, or runtime contract is TBD | Obtain the missing source contract and re-author before execution |

## Disclosure Rules

| Gate | What Must Be Shown |
|---|---|
| Validation failure | Field, supplied value when safe, violated rule, and one corrective action |
| Pattern decision | Interpreted intent, recommended pattern and code, confidence or ambiguity, and whether user confirmation is required |
| MAP event decision | Inferred or stated intent; recommended or selected event-type Meaning; whether the user confirmed it or requested a change. Do not disclose LookupCode. |
| Lookup failure | Resolver, lookup type or endpoint, requested identity, zero or multiple match classification, and requested correction |
| Data Loader handoff | Exact task and BusinessObject absenceTypes, validated values, defaults applied, unresolved items, target environment, and required approval state |
| Process timeout or failure | Environment, operation, process or request ID, last status, elapsed wait when applicable, diagnostic reference, and safe next action |

## Refusal Rules

| Situation | What Must Not Happen |
|---|---|
| A direct POST, PATCH, DELETE, or upsert is requested from this resource package | Do not execute or author a direct REST mutation; route the request through core.data-loader |
| Pattern intent is ambiguous | Do not silently choose GENERIC or treat any unconfirmed recommendation as a selected pattern |
| MAP is selected and event intent is ambiguous | Do not default an event type, select the first row, or disclose LookupCode; present only the retrieved LOV Meanings and require selection |
| A lookup is ambiguous | Do not choose the first row or infer a code |
| A Display Feature or Rules prompt does not uniquely match its exact lookup | Do not generate a payload or silently substitute a related meaning. Ask the user to choose from the valid returned Meanings. |
| A plan association is requested | Do not perform a type-local plan search, use an unverified plan ID or display value, default Priority, or associate an inactive, ended, or incompatible plan |
| A common-lookup-backed LOV is requested | Do not use an endpoint other than /fscmRestApi/resources/11.13.18.05/commonLookupsLOV |
| An absence type event is requested | Do not derive EventId from a display name or use an Absence Plan event-response lookup for the Absence Type `events` child. |
| LegislationCode is requested | Do not use an endpoint other than /fscmRestApi/resources/11.13.18.05/territoriesLOV |
| Language or EffectiveEndDate is omitted | Do not synthesize either value; let Fusion derive it server-side |
| A prior mutation result is uncertain | Do not retry automatically or claim success |
| A date-effective operation is requested | Do not accept a caller-authored date-control value or default a non-create date/range; derive `effectiveOf` when its refreshed section header supports it and emit only date-control columns returned by that header |
| A Task Hook preview is requested for a date-effective archive | Do not treat caller-provided `ruleResults` as evidence of a valid header or `RestAction`; inspect the final immutable DAT member before passing validation |
| DELETE is requested | Do not infer DELETE_CHANGES versus ZAP, and do not execute ZAP without explicit destructive intent and immutable Data Loader approval |
| A parent Delete Changes, end-date, or ZAP operation completes without its operation-specific parent outcome verified | Preserve the request identifier and readback evidence, do not claim success, and do not retry the mutation automatically. |
| Credentials, bearer tokens, or sensitive payloads appear in evidence | Do not persist or disclose them |
