## Dependency-Aware Validation

### Display Features region validation

Before a Display Features update, resolve the requested UI section, pattern,
and usage as one placement key. Require the target type to contain the
corresponding UI-rendered region and usage: Generic Additional fields use
`SUPPLEMENTAL_DETAILS`; Illness or Injury uses `SCHEDULING` for
`SCHED_II_START_DATE` and `SUPPLEMENTAL_DETAILS` for the remaining Additional
fields; Maternity or Adoption Additional fields use `SUPPLEMENTAL_DETAILS`.
`ADDITIONAL_DETAILS` is not a valid replacement. If the correct region is
missing, stop ordinary usage-update preparation and route a pattern-template
based missing-hierarchy repair through the refreshed Data Loader contract.

Resolve every human-entered Display Feature or Rules label and value before
building a DAT row. A field label must exact-match or have one uniquely
defensible close match among the rows exposed by the selected pattern/UI
section. A value must resolve to one returned `LookupCode` from that exact
field/persona lookup type. Exact and normalized code/meaning matches take
precedence; a semantic match is valid only when one returned Meaning preserves
all material qualifiers. On zero or multiple plausible matches, stop and ask
the user to choose from the returned Meanings. Do not treat `enabled`,
`display`, or another generic word as a universal stored code.

For a new type, set resolved-intent `hierarchyKeyStrategy` to `native-user-keys`. Omit root and child surrogate IDs. Bind direct children with `LegislationCode` plus `Name`; use unique `AbsenceRegionCode` for regions and unique `AbsenceUsageCode` for usages, with each usage carrying its owning `AbsenceRegionCode`. Verify these LOCAL/PARENT user-key alternatives against fresh registered metadata. Fusion allocates the IDs, so no client-generated-ID collision check or global collision endpoint is required. Include exactly one new type per archive. Retain all region and usage persona lookup/display/default fields from the fresh pattern. Omit standard rule rows and verify Fusion-generated rules after load; explicit rule creation is not supported by this key strategy. Existing-record operations continue to use exact returned IDs. Never automatically replay a create.

For an existing usage update, resolve the exact type name and legislation,
the existing region and usage IDs, and the region's returned physical
`EffectiveStartDate`. Require a root metadata-only marker with no parent data
row. Require each identity-only region carrier to omit `AbsenceTypeId`, use
`LegislationCode` plus `Name` as its parent user key, and use CORRECTION at the
returned region start date. Require each target usage row to keep plain
numeric IDs and use the requested operation/date. Reject parent MERGE rows,
composite `id,date` values, `SourceRef*` hierarchy linkage, physical
`EffectiveStartDate` columns, or business changes on a region carrier.

For create, emit the requested date through the validated parent
`effectiveOf=RangeStartDate=<YYYY-MM-DD>` control. A physical parent
`EffectiveStartDate` value is not an equivalent control: live validation may
accept the file while Fusion still uses its server date. Readback of a
different date is a payload mismatch, not success.

## Field Validation

| Check | What Happens | Applies When | Resolver |
