# Absence Types Design Enforcement

## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Interpret the business intent | For create, use resolve_absence_pattern to suggest from the name/description and obtain confirmation, or ask for a pattern when intent is ambiguous; preserve an explicitly supplied pattern subject to validation |
| 2 | Resolve required identities | Resolve legislation, legislative data group, pattern, and the conditional MAP event type through their documented LOVs |
| 3 | Resolve requested plan and reason associations | Require verified Absence Plans and Absence Reasons task output before mapping either child section; resolve a plans-child association status separately |
| 4 | Resolve requested event associations | Require one active Absence Management event condition and one Absence Type event response before mapping the `events` child; do not borrow the Absence Plan response LOV |
| 5 | Apply source-controlled defaults | Apply defaults only from ora_defaulting_rules.md and never overwrite a user-supplied value |
| 6 | Normalize date-effective operation | Validate the selected operation, exact record, and applicable explicit date; never accept a caller-authored date-control string |
| 6 | Refresh registered DAT template | Verify the current parent and included child/DFF headers and use only the date-effective controls that the live template exposes |
| 7 | Allocate create hierarchy keys | For a new type, set resolved-intent `hierarchyKeyStrategy` to `native-user-keys`. Omit root and child surrogate IDs. Bind direct children with `LegislationCode` plus `Name`; use unique `AbsenceRegionCode` for regions and unique `AbsenceUsageCode` for usages, with each usage carrying its owning `AbsenceRegionCode`. Verify these LOCAL/PARENT user-key alternatives against fresh registered metadata. Fusion allocates the IDs, so no client-generated-ID collision check or global collision endpoint is required. Include exactly one new type per archive. Retain all region and usage persona lookup/display/default fields from the fresh pattern. Omit standard rule rows and verify Fusion-generated rules after load; explicit rule creation is not supported by this key strategy. Existing-record operations continue to use exact returned IDs. Never automatically replay a create. |
| 8 | Enforce pattern-specific fields | Keep II-only and MAP-only attributes within the resolved pattern boundary |
| 9 | Enforce server-derived fields | Do not default Language or EffectiveEndDate |
| 10 | Hand off and verify | Submit only through core.data-loader after immutable preview and approval; monitor its terminal result and read back the exact target before reporting success |

## Design Lookup Requirements

**Display Features placement enforcement**

For `GENERIC`, `II`, and `MAP`, enforce the UI section-to-region placement in
`references/display-features-and-rules.md` before preview. A usage-code match
alone is insufficient: `SUPPL_BLOCKED_LEAVE_CANDIDATE` belongs to
`SUPPLEMENTAL_DETAILS` in all three patterns. Reject a proposed Additional
fields update that targets `ADDITIONAL_DETAILS`, even if the row exists there.
When the returned target hierarchy lacks the UI-rendered region, prepare no
ordinary PATCH; require a separately validated missing-hierarchy repair from
the same pattern template.
