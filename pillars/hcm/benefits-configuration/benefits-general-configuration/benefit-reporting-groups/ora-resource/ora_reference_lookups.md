## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Input field omitted | Do not request its LOV solely for that field and do not create a validation error. |
| Name or Description exact-match lookup | Send the supplied value as the declared `q` equality predicate for that field before requesting pages. URL-encode the full query parameter and escape a literal apostrophe using the endpoint's documented query-literal syntax. |
| Common lookup exact-match lookup | Use only the declared LookupTypeFinder request. Read its result pages and compare the supplied value exactly to LookupCode or Meaning; do not send a `q` parameter. |
| Date-effective lookup | Validate and send the child row's EffectiveStartDate through the live endpoint's documented effective-date parameter. Do not inherit a parent or sibling date and do not substitute the current date. |
| Multiple rows or pagination | Read all result pages through the selected shared REST client before deciding zero, one, or many distinct exact matches. |
| Lookup returns HTTP 403 | Record unverified_forbidden for that field without throwing or marking the supplied value invalid. Continue independent checks. Do not treat the field as verified. |
| Lookup returns HTTP 401 | Use the selected client's permitted one-time cached-token refresh, then classify a remaining rejection as auth/authz. |
| Lookup returns another failure | Classify the failure and stop that lookup; do not convert it to a no-match result. |
| No active read-only lookup route | Record an approval or workflow blocker; do not call REST directly or silently mark values valid. |

The REST paths, `q` predicates, and finder syntax above are read-only reference contracts. URL-encode every query parameter when issuing a request. A successful Name or Description `q` request normally needs only one response page; follow later pages only when Fusion reports more results for that predicate. Common lookup resolvers do not use `q` and must read every page returned by their finder. Only the active project workflow may select the live lookup step. For common lookup fields, the request does not specify whether the input uses LookupCode or Meaning; accepting either exact returned representation avoids coercion, but the target HDL metadata must determine which representation can be loaded.
