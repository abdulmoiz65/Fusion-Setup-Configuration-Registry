# Reference Lookups

Before executing any REST lookup below, apply the
[REST version and query compatibility preflight](../../../references/rest-query-compatibility.md)
and the REST request compatibility rule in Lookup Execution Rules. Existing
matching, classification precedence and workflow gates continue to apply.

## Local Lookups

These local maps define valid value sets; they are not a restricted list of phrases that the user must type. Interpret any supplied column intent or business value broadly using codes, UI labels, meanings, descriptions, translations, and surrounding request context. Apply strictness only to the resolution result: identify exactly one applicable CSV column and exactly one member of that column's authoritative valid set. Ask for the smallest clarification only when either result cannot be resolved uniquely. PJF_EXP_START_DAY and PJF_BU_RATE_DATE are static local lookup tables. Build the CSV with the resolved stored code, never the unresolved user phrase.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| REST request compatibility | Before a workflow-selected request, determine framework applicability and the effective REST framework version from the selected core client or workflow. Use compatible query syntax and verify that the outgoing header agrees; never pin an independent pillar version. Apply the linked offering preflight, preserve finder separators and literal values, and stop the affected request on an unresolved version or header/query conflict. |
| Initial validation or RESOLVE_OPTIONS runs before the hierarchy REST nodes | Validate supplied names and required fields without demanding unresolved REST receipts. Defer aggregate hierarchy checks, including start-organization roles, until all six dedicated tree/version/start-organization nodes finish. Initial input failure or any applicable lookup failure blocks before ZIP generation; evaluate complete receipts in RESOLVE_DEPENDENCIES |
| A lookup-backed column or value is supplied in any user-facing form | Interpret it broadly against the resolver's complete authoritative context using codes, UI labels, meanings, names, descriptions, translations, identifiers, and request context. Do not require an exact code or exact label. Continue only when exactly one CSV column and one valid member are confidently resolved; otherwise ask for the smallest clarification needed. |
| A standard-lookup-backed CSV column ends in Code | Write only LookupCode to the final CSV, never Meaning |
| A retained public LOV or hierarchy lookup is used | GET only through the declared Business Units, Rate Type, Accounting Calendar, Default Asset Book, fndTrees, FndTreeVersionVO or projectOrganizationsLOV contract; use configured restBaseUrl through the governed core REST client |
| A hierarchy Tree Name or Tree Version Name is supplied | Hierarchy names use exact matching rather than broad name interpretation. Resolve each applicable display Tree Name first; map technical codes only from its matching fndTrees REST response, unchanged. Never derive, normalize, uppercase, or construct a tree code or tree structure code from a name. Require one exact version-name match under that resolved tree, Status = ACTIVE, and inclusive effective-date bounds covering the current configuration date; never obtain a code from a version name. Record the hierarchy role, supplied name, returned name and source fields in the receipt. Equal tree names may share a verified tree response; different names must be resolved separately, and each supplied version must be checked under its own resolved tree. When resolved tree and supplied version are the same, reuse the same verified ACTIVE/effective response in the same target/configuration date. |
| Option group is omitted | Preserve complete current group |
| Only a project-unit relationship is added | Validate the enabled Project Accounting BU, exact project unit, authorization, current relationship set, and additive delta; do not require separate ledger, legal-entity, currency, or accounting-calendar evidence |
| A relationship removal lacks usage evidence | Preserve it and block removal |
| Feature state differs from sample or source evidence | Follow the current target and report the selected branch |
| Only report schemas are available | Do not declare the generated ZIP import-ready |
| A hierarchy start organization is supplied | Resolve the exact supplied name through its dedicated projectOrganizationsLOV node after tree/version resolution. Use ActiveStatusFlag, FromDate and ToDate from REST, not inferred classification or display-name evidence. Require the validated target business/effective date; do not silently use a different host date |
| Both hierarchy start-organization names are identical | Reuse one successful fully paginated response in the same target/effective-date task run; check PROJECTS and EXPENDITURES independently for the same unique OrganizationId. Different names must be queried separately. Share the task-run collection_cache between the two validator calls; failed or incomplete responses are not cached as valid |
| A projectOrganizationsLOV call is selected | Complete task, identity, read-privilege, target, evidence-destination and client preflight; fetch all pages through core.fusion-api.rest-api-client, preserving the exact query and same configured origin. Supply trusted status, complete, restBaseUrl, organization_name, request_url, pages and evidence_ref to the task-local response validator. Each page retains count, offset and hasMore; do not feed user assertions as independent REST evidence |
| Start-organization validation fails | Follow failure to BUFUNC.RETURN_ISSUES before operation routing, package preparation or approval. Preserve sanitized role-specific diagnostics; no fallback to task exports, the other role, guessed identity or a partial response. Existing auth policy remains with core; do not add blind retries |
| Tree-version response reuse | Share a task-run response_cache between both version validator calls. Key it by configured restBaseUrl, current configuration date, resolved TreeCode and exact TreeVersionName; cache only a fully paginated unique ACTIVE effective result. Different trees, versions, targets or dates require separate reads; never reuse failed, partial, inactive or ineffective results |
| Tree-version validation source | Supply the current target configuration date and successful fndTrees TreeName/TreeCode/TreeEvidenceRef for each role. Fetch all version pages through core.fusion-api.rest-api-client; provide trusted status, complete, restBaseUrl, tree_code, version_name, request_url, pages and evidence_ref to scripts/validate_hierarchy_tree_versions.py. Missing/inconsistent provenance or date blocks; do not substitute host date, derive codes or defer version validity to import |
