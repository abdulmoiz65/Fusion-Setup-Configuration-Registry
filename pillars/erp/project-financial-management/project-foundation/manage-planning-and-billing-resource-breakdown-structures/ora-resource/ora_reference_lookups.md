# Reference Lookups

Before executing any REST lookup below, apply the
[REST version and query compatibility preflight](../../../references/rest-query-compatibility.md)
and the REST request compatibility rule in Lookup Execution Rules. Existing
matching, classification precedence and workflow gates continue to apply.

The complete same-target task export supplies RBS identity, CSV package shape, existing PersonNumber context and the target-enterprise context repeated on exported resource elements; it is not a Project Unit or Organization directory. The supplied live responses confirm Project Unit, Job and Person identity fields. The exported Organization rows plus the supplied classification precedence confirm the Organization projection. Project Unit and Organization reads supply import context, not a pre-import eligibility verdict. A Named Person whose resolved PersonNumber has no consistent context in the complete target export is blocked rather than assigned guessed dates.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| REST request compatibility | Before a workflow-selected request, determine framework applicability and the effective REST framework version from the selected core client or workflow. Use compatible query syntax and verify that the outgoing header agrees; never pin an independent pillar version. Apply the linked offering preflight, preserve finder separators and literal values, and stop the affected request on an unresolved version or header/query conflict. |
| Set collection pagination | Continue through returned pages; an incomplete result cannot establish uniqueness or absence |
| Project Unit context contract | Query by the supplied Name and fixed `ClassificationCode='PRJ_PROJECT_UNIT'`, then copy the confirmed Name, classification and effective-date fields. The classification is part of selecting Project Unit context; do not inspect Status or use the returned dates to decide whether Fusion may import the RBS |
| Job Set missing | Do not list or query Jobs. Ask the customer which Job Set to use; only after its exact SetName and SetCode resolve may the Job lookup run |
| Job lookup and Set scope | Resolve Job Set first, then query jobsLov with both the resolved SetName and selected JobName; require the one returned JobName and SetName to match before copying JobCode and SetCode |
| Person name fallback | Query DisplayName first; query ListName only after zero DisplayName matches. After resolving PersonNumber, require one consistent effective-date and enterprise context across its rows in the complete current export; absence or conflict blocks that person |
| Organization classification precedence | Query PA_EXPENDITURE_ORG, then PA_PROJECT_ORG, then DEPARTMENT, then FUN_BUSINESS_UNIT. Take exactly one row from the first classification with a match; ambiguity blocks and lower-precedence classes are not considered after a match |
| Organization result | Copy Name, selected classification and Organization effective dates to Name5, ClassificationCode1 and date pair 4. Copy the unique target-export enterprise context to Name4 and date pair 5; do not use OrganizationId or reject the row through an FSCR date/status eligibility check |
| Format descendants | Job: Expenditure Category is proven with a resource; Organization: Inventory Item is proven only as a format. Other descendants remain outside the observed create profile |
| Name fields without a live contract | The tested FSM import retained NlrName, ExpenditureTypeName and ExpenditureCategoryName. Do not invent a mandatory pre-import REST directory for them; disclose that arbitrary new names have not been independently tested |
| Unavailable or truncated lookup | Stop before package preview; never use a fixture value or another environment's code as a fallback |
| Local target export | Use it for task baseline and RBS identity; it does not establish Project Unit identity or serve as a directory for other resource references |

## Job Effective-Date Source

Oracle's [Get all jobs REST contract](https://docs.oracle.com/en/cloud/saas/human-resources/farws/op-jobslov-get.html)
documents `EffectiveStartDate` and `EffectiveEndDate` on each Jobs LOV item.
Copy these from the same uniquely matched Job response used for JobCode/SetCode
to satisfy the existing serializer's date-context fields. This completes the
read-to-CSV mapping; it adds no date-eligibility filter, new lookup route or
claim of live import verification. Missing context remains a preparation blocker.
