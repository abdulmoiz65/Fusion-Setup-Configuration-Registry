# Accounting Calendar Input Validation

## Required Groups

| Requirement Group | Accepted Fields | If Missing | How to Resolve |
|---|---|---|---|
| Calendar identity | calendar_name and calendar_start_date | Block | Obtain an import-safe name of 15 characters or fewer and fiscal start date. |
| Duplicate check | Exact `accountingCalendarsLOV` query returns zero matches before package generation and immediately before import | Block | Stop creation on any match, ambiguous result, or unavailable LOV; never infer absence from a failed lookup. |
| Calendar header dates | CalendarStartDate and LatestYearStartDate | Block | Populate both values. For a new single-year generated calendar, use the approved calendar start date for both. |
| Generation design | period_frequency, adjustment_frequency, conditional number_of_adjusting_periods, and naming choice unless period frequency is Other | Block | Apply the documented default naming code when omitted. Require a positive whole-number adjustment count when adjustment frequency is Other. For period frequency Other, obtain the user's selected naming convention. |
| Manual design | manual_period_rows | Block for Other | Supply all required period attributes explicitly. |
| Technical defaults | Documented trusted calendar-code defaults and the approved generic bootstrap profile | Block package generation | Use user inputs and documented codes/defaults; do not invent values outside those sources. |
| Reusable template baseline | Matching task code, target environment, Fusion release, validated template-only export receipt, reviewed artifact path and fingerprint, member/header structure, and each required code mapping | If absent, fetch the template-only package for the first project run; if stale or incompatible, fetch it again | Reuse the persisted baseline across later Codex sessions only while every compatibility and completeness check passes. |
| Template-only source boundary | Template-only package fetched and persisted for the project, or its still-compatible project baseline, plus documented rules and requested definition | Block | Fetch on the first project run or when compatibility fails. Do not request a Data Only Export or derive a new calendar's attributes or periods from populated setup data or an existing calendar. |
| Existing-update current-value source | Complete exact parent and period baseline from the same target environment and release | Block | Reuse a successfully loaded and post-load-verified FSCR creation package only in the current project/session. Otherwise automatically obtain one full task data export and isolate exactly one parent matching both LOV-resolved names and only its linked children. |

## Field Validation

| Check | What Happens |
|---|---|
| PERIOD_SET_NAME and PERIOD_NAME length is 15 or fewer | Reject longer values. |
| Exact UserPeriodSetName lookup returns zero matches before package generation and immediately before import | Reject duplicate or ambiguous calendar creation; do not treat an unavailable lookup as zero matches. |
| Duplicate-calendar LOV query is exact and repeated | Query `/fscmRestApi/resources/11.13.18.05/accountingCalendarsLOV?q=UserPeriodSetName='{calendar_name}'` before package generation and repeat it immediately before import. Reject any nonzero, ambiguous, or unavailable result. |
| Frequency is Monthly, Weekly, Quarterly, Yearly, 4/4/5, 4/5/4, 5/4/4, 4 Week, or Other | Weekly is the finest supported grain. Reject Daily, subweekly generated calendars, or an `OTHER` design whose standard rows implement a daily/finer-than-weekly cadence. |
| Calendar frequency allow-list | Normalize only Monthly (`MONTH`), Weekly (`WEEK`), Quarterly (`QUARTER`), Yearly (`YEAR`), 4/4/5 (`4_4_5`), 4/5/4 (`4_5_4`), 5/4/4 (`5_4_4`), 4 Week (`4_WEEK`), and Other (`OTHER`). Reject every other spelling, code, or pattern—including 4/5/5—before applying defaults or generating rows. |
| Calendar type allow-list | Normalize only `ACCOUNTING` and `COMMITMENT`. Require `COMMITMENT` only for Budgetary control only; require `ACCOUNTING` for an ordinary accounting calendar. Reject an unrecognized type or an invalid type/mode pairing. |
| Adjustment option is a supported UI option | Permit any documented trusted adjustment code when its row shape and compatibility rules pass. |
| Adjustment-policy allow-list | Normalize only NONE, `1_YEAR_END`, `2_YEAR_END`, `1_BEGIN_1_END`, `1_MID_1_END`, `1_MID_2_END`, QUARTERLY, or OTHER. Reject any unrecognized wording, cadence, or code—for example, every month end or every week end—before row generation. |
| Adjustment frequency is compatible with the non-adjusting frequency | Block `1_MID_1_END`, `1_MID_2_END`, and `QUARTERLY` when `NonAdjPeriodFreqCode` is `YEAR` or `4_WEEK`. The provided UI evidence identifies these as the only disallowed adjustment-frequency combinations; all other listed UI adjustment selections remain permitted. |
| Other adjustment frequency has a valid count | When `AdjPeriodFreqCode=OTHER`, require `AdjPeriodsNum` to be a positive whole number. Reject a missing, zero, negative, fractional, or nonnumeric count before row generation. Do not use the budgetary-control-only standard-period count as this value. |
| Non-adjusting dates are continuous and non-overlapping | Reject gaps, overlaps, reversed dates, missing numbers, or nonsequential dates. |
| Period number is unique within period set, type, and year; period name unique within period set | Reject duplicates. |
| Period name, entered name, type, year, number, dates, adjustment flag, and conditionally quarter are present when FSM metadata requires them | Reject incomplete rows. Require `QuarterNum` for an `ACCOUNTING` calendar; require it to be blank/not supplied for a `COMMITMENT` calendar. |
| First period number | Within each fiscal year, sort all standard and adjustment rows by `StartDate`, then by the intended display/order sequence for same-date rows. Require the earliest row to have `PeriodNum = 1`, including when that row is an opening adjustment. |
| Period-number upper bound | For each fiscal year, require every `PeriodNum` to be no greater than `NonAdjPeriodsNum + AdjPeriodsNum`. Apply this to generated and manual rows after header-count reconciliation. |
| Quarter-number range and fiscal assignment | For an `ACCOUNTING` calendar, require every `QuarterNum` to be an integer from 1 through 4. Assign standard rows by fiscal-period ordinal, never by shifted CSV `PeriodNum`; assign an adjustment row to the quarter of its single overlapping standard row. Reject Q0, Q5, blanks, a Gregorian-calendar-quarter shortcut, or a quarter that does not match the documented frequency mapping. |
| First standard period is Quarter 1 | For each fiscal year of an `ACCOUNTING` calendar, sort standard rows by `StartDate` and require the earliest standard row to have `QuarterNum = 1`. |
| Quarter numbers progress in fiscal order | For each fiscal year of an `ACCOUNTING` calendar, sort rows by `StartDate` and stable display/order sequence. Quarter numbers may stay the same or move only through `1 -> 2 -> 3 -> 4`; reject a decrease, skipped quarter, or re-entry into an earlier quarter. Adjustment rows must retain the quarter of their one overlapping standard row. |
| Commitment calendars have no quarters | For `CalendarTypeCode=COMMITMENT`, require `QuarterNum` to be blank/not supplied on every standard and adjustment row. Do not apply the accounting-calendar quarter-required, first-quarter, or quarter-sequence rules. |
| `PeriodSetName` is populated on `GL_PERIOD_SET.csv` and every `GL_PERIOD_DEF.csv` row | Reject a blank header or child `PeriodSetName`, or any child value that differs from the parent. Child periods must resolve to their owning calendar before import. |
| CSV files are UTF-8 without BOM and preserve repository task-template header order | Require every CSV data row to contain exactly the same number of fields as its header, including trailing blank fields. Reject package generation when a row is shorter or longer than its header, or when a BOM, reordered headers, or unreviewed columns are found. |
| Header counts reconcile with generated rows | Require AdjPeriodsNum = adjustment rows, NonAdjPeriodsNum = non-adjustment rows, and TotalPeriodsNum = their sum. |
| Period counts are within calendar-generation limits | Reject more than 53 non-adjusting periods or more than 55 adjustment periods in a fiscal year. |
| Standard-period count matches selected frequency | Reject a generated or supplied definition unless its non-adjusting count is exactly: Monthly 12, Weekly 52, Quarterly 4, Yearly 1, 4/4/5 12, 4/5/4 12, 5/4/4 12, or 4 Week 13. Other requires the explicitly supplied count and rows. |
| Ordinary Other frequency has a positive standard-period count | For an ordinary `ACCOUNTING` calendar with `NonAdjPeriodFreqCode=OTHER`, require `NonAdjPeriodsNum` to be a positive whole number and require exactly that many reviewed manual non-adjustment rows. Reject a missing, zero, negative, fractional, nonnumeric, or mismatched count. |
| Budgetary or federal request is internally consistent | Require the requested calendar type, standard-period count, and adjustment policy to agree. Reject a 14-period federal requirement paired with Yearly frequency; stop as a policy gap when the template or documented rule does not establish the requested budgetary-control option. |
| Budgetary-control-only mode | Require `budgetary_control_only = Yes`, `NonAdjPeriodFreqCode = OTHER`, and a positive explicit number of budget periods. Reject any normal accounting frequency, inferred count, or omitted budget-period count. |
| Budgetary-control-only period count | Accept any positive whole-number standard-period count. Reject zero, a negative value, a fraction, or nonnumeric text before package generation; do not require or default the count to 12 or 24. |
| Budgetary-control-only adjustment policy | Reject a supplied adjustment frequency, adjustment count, or adjustment row. This mode has no user-selectable adjustment-period option; populate a template-required technical value only when the approved template declares one. |
| Budgetary-control-only period naming | Do not apply `MMMYY*` or `PRDNUM*` accounting-calendar naming defaults. Require the template-supported budget naming pattern and a nonblank budget-year number. For the observed budget year 1 example, generated names are `PRD_01-01` through `PRD_24-01`; derive the actual count from the supplied number of periods. |
| Calendar start and latest-year-start dates align | Reject LatestYearStartDate before CalendarStartDate or a date not aligned to the first generated fiscal year. |
| Calendar start or latest-year-start date is blank | Reject the package before ZIP creation. A blank value is not aligned and must never pass readiness. |
| Latest-year-start date disagrees with generated rows | Require `LatestYearStartDate` to equal the latest non-adjusting `YearStartDate` in `GL_PERIOD_DEF.csv`; for a single-year package it equals `CalendarStartDate`. |
| Added fiscal-year boundary is inconsistent | For an extension, require the added fiscal year's first non-adjusting period to start on the calendar day immediately following the prior fiscal year's final non-adjusting period. Do not reset the added year to January 1 unless that is the resulting next day. Require `LatestYearStartDate` to equal that added fiscal year's first non-adjusting `YearStartDate`. |
| Existing calendar is incomplete before a year is added | Before an extension, retrieve every page from `accountingPeriodsLOV` and validate what the endpoint exposes: expected row presence, unique names/numbers, sequential period numbers, continuous non-adjusting dates, standard/adjustment row counts and placement, and the immediately preceding year's final non-adjusting boundary. Cross-check that evidence against the controlled exact-target update source, including quarter and parent-header values the LOV omits. Require the prior final standard boundary to be one day before the new year's first standard period, and validate counts, quarters, adjustment design, and historical-row preservation locally. |
| Calendar package validation | Review the package source and final ZIP; block readiness or import unless the required header dates, generated rows, counts, encoding, and linkage satisfy every rule in this file. |
| Template-column classification | Classify every template column before generating a row as request-derived, documented-default, template-literal, or blank-only. Reject package generation when a column has no classification. |
| Calendar header context and DFF fields | Keep `GL_PERIOD_SET` Attribute1 through Attribute5 and AttributeCategory blank unless the approved template explicitly requires a reviewed value. Never place calendar year, fiscal year, period count, calendar name, or any generated value in these fields. |
| Period context, DFF, and global fields | Keep `GL_PERIOD_DEF` Attribute1 through Attribute8, AttributeCategory, GlobalAttribute1 through GlobalAttribute20, GlobalAttributeCategory, GlobalAttributeDate1 through GlobalAttributeDate5, and GlobalAttributeNumber1 through GlobalAttributeNumber5 blank unless the approved template explicitly requires a reviewed value. Never derive these values from a request. |
| `ReferencedByLedger` | Treat this template column as non-gating informational metadata. Do not look it up, require it, or block preview, approval, or submission when it is unavailable. Keep it blank unless the approved template requires a reviewed literal. |
| Average-daily-balance period duration | When `average_daily_balance_enabled = Yes` is explicitly supplied or reliably setup-derived, reject any standard or adjustment period whose inclusive date range exceeds 35 days. When the signal is No or unknown, do not infer it from `ReferencedByLedger`, do not add a ledger-reference gate, and do not block the current flow solely because the signal is unavailable. |
| Legacy-rules dependency | Permit `LegacyRulesEnabledFlag = Y` only when `LegacyCalendarFlag = Y`. Reject `LegacyRulesEnabledFlag = Y` with a blank or `N` legacy-calendar flag. Defaults of `N` remain valid. |
| Audit and system fields | Keep CreationDate, CreatedBy, LastUpdateDate, LastUpdateLogin, LastUpdatedBy, ConfirmationStatus, PeriodStatus, RequiredPrevPrdNum, RqrdPrevNonAdjEndDate, and CurrentPeriodYear blank unless the template explicitly establishes a required literal. |
| Generated year placement | Permit a requested year only in calendar/period date and year fields: CalendarStartDate, LatestYearStartDate, StartDate, EndDate, YearStartDate, QuarterStartDate, PeriodYear, and FiscalYear. Reject that year in any context, attribute, global-attribute, audit, status, or unclassified field. |
| Template evidence | On the project's first run, use `shared.setup-export.task-level-export` in template-only mode and validate the returned package before persisting it as the project baseline. On later runs, verify and reuse that baseline when task, environment, release, fingerprint, members, and headers remain compatible. For a new calendar, use documented codes/defaults and user inputs and never request a Data Only Export. Permitted updates follow the separate controlled current-value source rule. |
| Immediate import revalidation | Immediately before submission, re-parse the immutable ZIP and revalidate `CalendarStartDate`, `LatestYearStartDate`, header counts, period continuity, adjustment overlap, and `PeriodSetName` linkage. Reject the submission if any value differs from the approved preview. |
| Monthly format allow-list | Permit every documented trusted period-name format for Monthly. Reject a month-based Monthly format when the start date is after day 28; use one of the four documented period-number formats or change the start date. |
| Adjustment row overlaps exactly one related non-adjusting period | Reject an adjustment row that overlaps none or more than one normal period. |
| Weekly, Quarterly, Yearly, 4 Week, 4/4/5, 4/5/4, or 5/4/4 uses a non-period-number format | Reject it. These frequencies permit only `PRDNUMYYCY`, `PRDNUMYYFY`, `PRDNUMYYYYCY`, or `PRDNUMYYYYFY`. |
| Monthly calendar starts after day 28 and uses a month-based format | Reject it; use a documented period-number format or change the start date. |
| Monthly uses an alternate format | Permit it only when explicitly requested, in the documented trusted format list, and consistent with the fiscal start-day rule. |
| Default period-name format is omitted by the user | Apply `MMMYYFY` for Monthly and `PRDNUMYYFY` for Weekly, Quarterly, Yearly, 4 Week, 4/4/5, 4/5/4, and 5/4/4; do not reuse a conflicting format from a prior export. For Other, block and ask the user for the naming convention. |
| Period-name header and detail rows disagree | Reject the package when `PeriodNameFormatCode` or `SamplePeriodName` conflicts with `PeriodName` or `EnteredPeriodName`. Permit a non-default format only when the user explicitly requested it and it is allowed for the selected frequency. |
| Calendar-year versus fiscal-year naming is inconsistent | Reject a `CY` format when any standard or adjustment name uses a fiscal-year token, or an `FY` format when any name uses a calendar-year token. This check is mandatory when the fiscal year crosses a calendar-year boundary. |
| First-period and generated-name reconciliation | Require `FirstPeriod` and `SamplePeriodName` to match the earliest non-adjusting period generated from the fiscal start date and selected naming format; reject a next-year first period or a name/case/separator mismatch. |
| Generated adjustment naming | Require every generated adjustment name to be `<two-digit PeriodNum>_<base name rendered for that adjustment row>`. For example, `MMMYYFY` produces `04_Mar-27`; `PRDNUMYYFY` produces `07_7-27`. Do not reuse an adjacent standard name or substitute a generic prefix. |
| Beginning-and-end adjustment naming | For monthly `1_BEGIN_1_END`, require opening adjustment as period 1 on fiscal start, normal fiscal months as periods 2?13, and closing adjustment as period 14 on fiscal year end. Apply the generated-adjustment naming rule. |
| Other frequency has reviewed manual names and rows | Do not auto-generate standard names or boundaries for an ordinary accounting calendar. Budgetary-control-only Other calendars use the separate budgetary naming and period-count rules. |
| Other frequency header naming | Require nonblank `PeriodNameSeparatorCode` and `SamplePeriodName` even though the UI hides the period-name-format region. For custom names, use the first reviewed manual period name as `SamplePeriodName`; reject a blank separator or sample name. |
| `OTHER` adjustment frequency on a generated calendar | Do not confuse this with `NonAdjPeriodFreqCode=OTHER`. Retain the selected frequency's standard rows and validate the requested count, appended adjustment rows, final-standard-period end date, sequential numbering, inherited year and quarter, and header counts against the canonical generic adjustment geometry. |
| Weekly 365-day design is requested | Generate 52 non-adjusting weekly periods; use a reviewed year-end adjustment row rather than a 53rd standard week. |
| Weekly fiscal year is added to an existing calendar | Treat 52 seven-day non-adjusting periods as a 364-day fiscal year. Derive the added fiscal-year start from the day after the preceding year's final non-adjusting week, then generate the 52 consecutive weeks from that date. |
| Weekly calendar with `1_YEAR_END` adjustment is requested | Require exactly 52 non-adjusting weekly periods and exactly 1 adjustment period. Reject 53 non-adjusting weekly periods plus an adjustment period before ZIP generation or import. |
| Weekly calendar with `1_BEGIN_1_END` adjustment is requested | Require exactly 54 rows: opening adjustment as period 1 on the fiscal-year start date, 52 non-adjusting seven-day weeks as periods 2 through 53, and closing adjustment as period 54 on the final standard week's end date. Compute that boundary as start date plus 363 days, disclose it in the preview, and do not request confirmation unless the user explicitly supplied a conflicting end date or requested a 53rd standard week. Require each adjustment to overlap exactly its adjacent standard week. |
| Weekly calendar with `QUARTERLY` adjustments is requested | Require 52 continuous seven-day standard weeks and four single-date adjustment rows placed after each group of 13 standard weeks. Validate the sequence, quarter inheritance, and dates against the reviewed weekly quarterly geometry. |
| 5/4/4 calendar with `1_BEGIN_1_END` adjustment | Require exactly 14 rows: opening adjustment 1 on fiscal start; twelve 5/4/4 standard periods 2 through 13; and closing adjustment 14 on the final standard-period end date. |
| 5/4/4 calendar with no adjustment | Require exactly twelve non-adjusting 5/4/4 rows, numbered 1 through 12. Do not add an adjustment merely because Fusion recommends one. |
| 5/4/4 calendar with `1_YEAR_END` adjustment | Require exactly twelve standard rows followed by one one-day year-end adjustment as row 13 on the final standard-period end date. |
| 5/4/4 calendar with `2_YEAR_END` adjustment | Require exactly twelve standard rows followed by two one-day year-end adjustments as rows 13 and 14 on the final standard-period end date. |
| 5/4/4 calendar with `1_MID_1_END` adjustment | Require standard rows 1 through 6, a one-day adjustment row 7 at the second fiscal-quarter end, standard rows 8 through 13, and a one-day year-end adjustment row 14 on the final standard-period end date. |
| 5/4/4 calendar with `1_MID_2_END` adjustment | Require twelve 5/4/4 standard periods, one one-day adjustment after the second fiscal quarter, and two one-day adjustments on the final standard-period end date. Each must overlap exactly one standard period and numbering must remain sequential. |
| 5/4/4 calendar with QUARTERLY adjustments | Require twelve 5/4/4 standard periods and one one-day adjustment at each fiscal-quarter end. Each adjustment must overlap exactly one standard period and numbering must remain sequential. |
| Adjustment-frequency row shape | Reject a package whose adjustment row count, numbering, or dates do not match the selected adjustment frequency. Do not substitute `1_YEAR_END`, `1_BEGIN_1_END`, and `OTHER` for each other. |
| Multiple calendar definitions are requested | Validate names, sources, counts, dates, and options independently. Reject only the invalid definitions and return an entity-specific error for each; never merge fields or report a single ambiguous batch result. |
| Existing-calendar deletion is requested | Reject before lookup, package generation, UI navigation, or submission. |
| Existing-calendar description is changed | Permit only through an FSM package submitted by the mandatory Data Loader workflow after exact identity resolution, immutable preview, and explicit update approval. Update description only; preserve `UserPeriodSetName`, `PeriodSetName`, all child parent keys, and all period rows. |
| Existing-calendar display name is changed | Reject it. Preserve `UserPeriodSetName`; do not generate or submit an FSM rename package. |
| Existing-calendar period-name format is changed | Permit only while adding a new fiscal year through FSM/Data Loader. Validate the requested format against the frequency allow-list; require immutable preview, explicit update approval, generated added-year rows consistent with that format, and unchanged historical rows/names/dates/boundaries. |
| Existing-period UI-editable core-field update is requested | Permit `PeriodNum`, `QuarterNum`, `StartDate`, `EndDate`, and `AdjustmentPeriodFlag`. Block `PeriodName` and `EnteredPeriodName` changes for an existing period through FSM CSV: Fusion treats a changed `PeriodName` as a new row (which conflicts on period number), and an `EnteredPeriodName`-only change does not rename the displayed period. Resolve every original row from fully paginated `accountingPeriodsLOV` and retain its original `PeriodNameId` for eligibility matching. Include every row whose number, quarter, boundary, or flag must change in the affected set. First run a fully paginated exact `ledgersLOV` query. If ledgers exist, call `accountingPeriodStatusLOV` per ledger with the OAuth bearer token and `REST-Framework-Version: 9`, retrieve every page, automatically filter the history to the immutable affected `PeriodNameId` set, and retain every matching `ApplicationId` row. Every matching row must be `ClosingStatus=N`. A successfully completed query with no matching affected-period row, including a completely empty result for one ledger, means no status is instantiated for that ledger/period and is eligible; record that explicit empty outcome rather than synthesizing `N`. Other ledgers may still have matching all-`N` rows. Full unrelated history is normal and is ignored after pagination; do not pause or ask the user to isolate it. Cross-check ID matches with the original composite identity and use that exact identity only as a fallback when `PeriodNameId` is unavailable; fuzzy matching is forbidden. A call with no captured HTTP response/status is not an empty result: retry the explicit request with the required framework header. If the exact ledger result is zero, query `accountingPeriodStatusLOV` directly for every affected original name/year/number/date identity, resolve every returned LedgerId, and require no row attributable to the target calendar. Zero direct rows mean no status instantiated, not `N`. Ambiguous identity, inaccessible or truncated pages, inconsistent evidence, or a target-calendar non-`N` row blocks. Repeat the same deterministic branch immediately before submission. |
| Existing-period proposed rows are validated | Compare the complete existing calendar with the proposed delta. Require unchanged `PeriodName` and `EnteredPeriodName`; `StartDate <= EndDate`; unchanged `PeriodYear`, parent, header dates/counts, frequency, and adjustment policy; sequential unique period numbers beginning at 1 and not exceeding total periods; valid quarter range/first-quarter/fiscal sequence rules; continuous non-adjusting dates with no gap or overlap; and each adjustment overlapping exactly one standard period. An adjustment-flag edit is allowed only when the final standard/adjustment counts and selected adjustment policy remain unchanged and valid. If an edit would require `CalendarStartDate`, `LatestYearStartDate`, `YearStartDate`, `QuarterStartDate`, period year, header count, frequency, or adjustment-policy changes, block rather than expanding the authorized fields. |
| Existing-period FSM parent row | Require exactly one `GL_PERIOD_SET.csv` parent row with the immutable existing header values needed by Fusion: calendar identity, security/legacy flags, standard and adjustment counts, calendar/latest-year dates, calendar type, frequency, adjustment policy, name-format code, separator code, total count, and sample period. Do not submit a header-only or identity-only parent row: child rows will either be skipped for a missing parent or fail validation because required header attributes are null. Preserve every header value; do not use this row to change the existing calendar definition. |
| Existing-update source isolation | Require the retained FSCR creation package or full data export to match the target task, environment, and release. Require exactly one exported parent whose `UserPeriodSetName` and `PeriodSetName` both match the exact LOV identity, and require every retained child to link to that parent. Reject a missing target, duplicate/ambiguous parent, approximate match, cross-calendar child, or any attempt to use unrelated exported values. |
| Description-only update source use | Require the complete current parent carrier even though `accountingCalendarsLOV` exposes the current description. Change only `Description`; preserve every other parent value and emit no period data changes. |
| Period-name-format plus new-year source use | Require the complete current parent and exact historical rows. Preserve all existing periods and parent attributes except the explicitly approved format and required latest-year extension values; generate only the new fiscal year's rows. |
| Existing-period update is ready for approval | Immutable preview must list the original and proposed values for each affected row, every unchanged protected field, and either the compact filtered ledger/application eligibility matrix or the exact zero-ledger result plus direct-status receipts and returned-ledger ownership resolution. Each ledger/period outcome is either every matching application row at `N` or an explicit `NO_STATUS_INSTANTIATED` backed by a successful complete empty/matchless query. The matrix must include `PeriodNameId`, period name, `LedgerId`, `ApplicationId` and `ClosingStatus` when returned, original dates, retrieval time, required-header evidence, and per-ledger pagination receipts. Full unrelated ledger history may remain diagnostic evidence but is not preview content or a reason to pause. Include complete-calendar validation, package hash, and post-load verification plan. Require explicit update approval before Data Loader submission. |
| Existing-calendar protected fields are changed | Reject a request that changes calendar start date, non-adjusting frequency, adjustment policy, `UserPeriodSetName`, `PeriodSetName`, parent linkage, period year, header fields, either existing-period name field, or a period attribute outside number, quarter, start/end dates, and adjustment flag. Additional Information/DFF values require a separately validated context/segment contract. Do not convert a protected update into a create or generic FSM import attempt. |
