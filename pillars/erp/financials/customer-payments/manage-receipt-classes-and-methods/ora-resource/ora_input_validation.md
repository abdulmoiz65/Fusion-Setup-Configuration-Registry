## Scope and evidence boundary

These rules normalize and validate one or more customer requests for `AR_MANAGE_RECEIPT_CLASSES_AND_METHODS`. They use the exact task-level FSM template/current export, Oracle 26C guidance, and the reviewed implementation sources. They do not authorize a Fusion import, a direct REST write, or any update to `AR_RECEIPT_*` tables.

The task package is one hierarchy:

1. `AR_RECEIPT_CLASS`
2. `AR_RECEIPT_METHOD`
3. `AR_RECEIPT_METHOD_ACCOUNT`
4. `AR_CC_ERROR_MAPPINGS`

## Supported request boundaries

| Operation | Static/offline handling | Runtime status |
|---|---|---|
| Create receipt class with methods | Normalize the complete parent/child design and build only from an exact task template | Candidate; controlled import evidence is still required |
| Create or add a receipt method | Require one exact parent class and the complete method design | Candidate; controlled import evidence is still required |
| Add a remittance bank account | Require one exact parent method plus target-valid BU, bank account, currency, dates, primary choice, and applicable GL accounts | Candidate; target reference evidence is mandatory |
| Add a card error mapping | Require one exact automatic card-processing method and the complete mapping | Candidate; conditional applicability must be proven |
| Update an existing row | Require a fresh current export, exactly one target, explicit changed fields, and preservation of all omitted values and children | Ready only for exact single-row updates under controlled import, zero-warning, and fresh-export reconciliation gates; process 207503/export 207508 qualify this guarded path |
| End-date a method or method account | Require exactly one target and an explicit end date not before its start date; encode the business lifecycle action as a narrow baseline-preserving `EndDate` update | Ready as an exact create/update package operation under the normal controlled gates |
| Hard delete, rename, or move a child to another parent | Do not generate a candidate | Unsupported |
| Mixed create and update in one package | Validate each operation and its dependencies independently; preview and persist all rows atomically or generate nothing | Supported for any valid mix of task-owned create and update operations across multiple hierarchy branches; no exact-shape allowlist applies |
| Bulk requests | Accept a table or workbook only when every row identifies its operation and hierarchy; preview all rows together and never drop an invalid row | The adapter imposes no row-count or shared-parent restriction; actual Fusion ZIP/service limits still apply |

## Accepted business labels and codes

## Consolidated clarification enforcement

Evaluate every requested class, method, and remittance-account operation before
asking the customer anything. Return one `FOLLOW_UP_REQUIRED` question grouped
by hierarchy level and containing all currently knowable missing material
choices. A missing value at one level must not hide missing values at later
levels. Do not generate a blueprint, preview, or ZIP until the consolidated
finding is empty.

For account creation, require separate satisfied target evidence for `BuName`,
`BankAccountName` (including bank, branch, ownership, currency, and effective
status), `CurrencyCode`, and `AccountingCombinations`. The accounting evidence
may state that particular roles are not applicable only when that conclusion is
supported by the selected class/method design. A value copied from this task's
current export is not cross-task eligibility proof.

The task-local adapter enforces the core create choices declared in
`e2e-adapter.json`. Conditional fields remain governed by the selected business
branch above and must be included in the same follow-up question when
applicable.

Observed export codes are candidates, not an exhaustive lookup contract. Accept a business label only when it maps to exactly one source-supported code.

| Area | Observed/source-supported values | Handling |
|---|---|---|
| Creation method | MANUAL, AUTOMATIC, BR, BR_REMIT, NETTING, ORA_NETTING | Ask when the business request does not identify one exact applicable method |
| Remittance method | NONE, STANDARD, FACTORING, STANDARD_AND_FACTORING | NONE is documented for manual receipts only; enforce the selected creation-method branch |
| Confirmation | Y or N | Require an explicit business choice for new automatic classes; do not infer from creation method |
| Clearance | Export values N, S, Y | Do not translate a business clearance label to these codes without exact source evidence for the target release |
| Payment type | CASH, ACH_BANK_ACCOUNT, CREDIT_CARD, NONE | Require consistency with the payment channel and creation method |
| Payment channel | BANK_ACCT_XFER, CREDIT_CARD, BILLS_RECEIVABLE, or blank | Require only when applicable; blank is not a generic default |
| Primary/override/boolean flags | Y or N | Reject true/false, 1/0, and localized text after normalization if an exact Y/N mapping was not confirmed |
| Currency | Target-valid ISO currency code or ANY when explicitly supported | Never default currency from the environment, BU, ledger, or first existing row |

## Many-record rules

| Rule | Requirement |
|---|---|
| One logical row | A row identifies one operation and its complete class/method/account/error-mapping hierarchy |
| Row errors | Report row-level blockers; do not silently drop a row or build a partial package |
| Atomic preview | Show all normalized operations, ordered qualified phases, created/updated entities, preserved children, warnings, and the stable business-design SHA-256 before the single flow confirmation; disclose each immutable candidate SHA-256 at its execution gate |
| Confirmation invalidation | A changed operation, target key, business value, default, preservation instruction, environment, task, release, or incompatible schema requires a new flow preview and confirmation; refreshed evidence, process IDs, source hashes, and regenerated candidate bytes do not invalidate the flow confirmation when the stable business-design hash is unchanged |
| Runtime boundary | Static validation may continue, but live import stays blocked until the owning Run Book/Data Loader gate is satisfied |
| Package operation count | Apply no adapter-defined numerical limit. Keep all valid task-owned create and update operations in one candidate unless Fusion reports an actual ZIP/service limit. |
| Multiple parent branches | Allow methods, accounts, and mappings under different exact parent classes and methods in the same candidate. Require every parent to exist in the fresh baseline or earlier in the same candidate graph. |
