## Hierarchy and lifecycle rules

| Rule | Enforcement | Applies When | Failure behavior |
|---|---|---|---|
| Exact hierarchy | Each method has one class; each account or error mapping has one class/method parent in the fresh baseline or an earlier create in candidate dependency order. | Every request | Block before preview and identify the orphan, ambiguous parent, or ordering violation. |
| Import ancestor context | Every child row carries all existing ancestors in the applicable parent CSVs. Context rows copy fresh-baseline non-audit values exactly and blank service-owned audit fields. | Every method, method-account, or card-error candidate | Fail candidate validation if any ancestor is missing or altered; a child-only package is never import-ready. |
| Metadata sequence | Current-data exports may vary positive unique business-object node sequences without schema drift; template metadata must retain the canonical parent-before-child order. | Source validation and build | Reject duplicate/invalid sequences and any noncanonical build template; do not reject an otherwise exact current export solely for a different valid order. |
| Create collision | A create for any task business object requires zero exact, case-preserving baseline matches for its complete business key. | Create | Stop before preview and ask whether the customer intended an update; do not transform the operation. |
| Update target | An update requires one exact current baseline match and explicit changed fields. | Update | Stop on zero/multiple matches or an empty patch. |
| Preserve state | Omitted fields, siblings, translations, flexfields, and children remain unchanged. | Update/end-date | Block if the builder cannot reconstruct the complete affected hierarchy. |
| Unsupported lifecycle | Hard delete, rename, and child reparenting do not generate a ZIP. Valid task-owned create and update operations, including `EndDate` updates, may be combined without count, entity-mix, or shared-parent restrictions. | Applicable operation | Explain the unsupported lifecycle request and preserve all state. |
| Effective dates | EndDate is blank or on/after StartDate; overlapping duplicate effective records are not introduced. | Method/account lifecycle | Block and show the conflicting dates. |

## Receipt class processing rules

| Rule | Requirement | Source boundary |
|---|---|---|
| Explicit processing design | New classes require an exact creation method and explicit confirmation, remittance, and clearance behavior. | Oracle task guidance and ReceiptClass implementation evidence. |
| No remittance | No Remittance is allowed only for a compatible manual-receipt design. | Oracle task guidance. |
| Automatic clearing | A design relying on automatic clearing must select compatible automatic clearance behavior and its prerequisites. | Oracle 26C automatic-clearing guidance. |
| Factoring | Factoring values require a factoring-compatible remittance design; do not apply them to an incompatible class. | Oracle 26C remittance guidance. |
| Bills receivable | BR or BR_REMIT choices require the applicable bills-receivable behavior and dependencies to be explicit. | Source implementation evidence; unsupported combinations remain blocked. |
| Enum mapping | N, S, and Y clearance codes and other non-obvious enum codes are emitted only after the exact release mapping is proven. | Current export is observational evidence, not a complete semantic contract. |

## Receipt method and account rules

| Rule | Requirement | Failure behavior |
|---|---|---|
| Method effective start | Every new method has a valid explicit StartDate. | Ask for the date. |
| Automatic method consistency | Payment type, channel, maturity/creation rules, debit authorization, and funds-capture choices are mutually compatible and supported by target prerequisites. | Block and show the conflicting choices or missing evidence. |
| Account completeness | Every account row identifies an exact BU, bank account, currency, start date, and primary choice. | Stop before preview. |
| Currency coverage | A remitting method has at least one remittance account for each required currency. | Block and list uncovered currencies. |
| Primary account | Exactly one applicable primary account exists per currency and effective period. | Block on zero or multiple primary accounts. |
| Accounting roles | Cash, remittance, clearing, factoring, short-term debt, bank charges, and risk accounts are supplied only when applicable and validated against target accounting evidence. Before ZIP creation, every populated `*CcidSegments` display value must resolve uniquely to the exact target-native 30-slot LF-delimited vector with 30 LF terminators, including the terminal LF. | Block; never synthesize account segments or write a hyphenated display string directly to the task CSV. |
| Account overrides | Override behavior must be explicit and compatible with the bank-account and method design. | Ask one business-language question. |

## Card error mapping rules

| Rule | Requirement | Failure behavior |
|---|---|---|
| Applicability | A mapping belongs to a compatible automatic credit-card receipt method. | Block mappings on incompatible methods. |
| Exact error identity | Category and error code are explicit and do not collide with an existing exact mapping. | Block create collision or ambiguous update. |
| Recovery action | Primary action is explicit; subsequent action and number of days are present when required by that recovery design. | Ask for the missing recovery behavior. |
| Observed codes | CLR PAY INFO, REAUT REC, RET, REV REC and observed transaction categories are candidates only. | Do not map prose to a code when more than one behavior could apply. |

## Candidate package invariants

| Invariant | Enforcement |
|---|---|
| Task scope | Preserve the exact metadata and four registered CSV member paths; no unrelated setup data. |
| Template fidelity | Preserve encoding, delimiter, quoting, header order, line endings, required empty members, and `ASM_SETUP_CSV_METADATA.xml` byte-for-byte from the genuine template-only export. Never replace template metadata with current-export process metadata. |
| Audit safety | Generated service-owned audit columns are blank. |
| Date serialization | Every populated candidate `date` field, including preserved and ancestor-context values, is canonical `YYYY-MM-DD`; conversion and validation finish before the output archive is opened. |
| Determinism | The same normalized blueprint and source artifacts produce byte-identical ZIP content and SHA-256. |
| Independent validation | Reopen and validate the produced ZIP against the exact template, current export, blueprint, and rule plan before handoff. |
| Complete preview | Show environment, release, task, all operations and ordered phases, hierarchy, dates, processing choices, bank/accounting references, preserved values, warnings, row counts, evidence hashes, and stable business-design hash; require one standalone confirm after the final consolidated preview. |
